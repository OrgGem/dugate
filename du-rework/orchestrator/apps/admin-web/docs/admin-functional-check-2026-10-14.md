## Functional findings

1. **Tenant bootstrap ID blocks scoped Admin operations.** `/admin/api/tenants` returned one bootstrap sentinel tenant, `000…001`. It was selected in the navigation, but strict RFC UUID checks rejected it for Connector actions and scoped parity routes. Runtime tracing showed the API-key list/issue path returned 404 in the BFF before the upstream API-key handler, and the typed Profile connector catalog also returned 404. Secret listing returned HTTP 200 with zero entries.

   Secret creation exposed the same sentinel mismatch at a later layer: the shared `SecretCatalogCreateSchema` and BFF accept the UUID-shaped tenant value ([secret-catalog.ts](/D:/Git/dugate/du-rework/orchestrator/packages/contracts/src/secret-catalog.ts:309), [secrets.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/src/app/admin/bff/secrets.ts:242)), but the backup snapshot write gate requires UUID version and variant bits ([backup-effect-fence.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/src/modules/maintenance/backup-effect-fence.ts:56), [backup-effect-fence.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/src/modules/maintenance/backup-effect-fence.ts:730)). The fake secret create therefore returned `409 INVALID_ARGUMENT`, “Backup snapshot write identity is invalid.” The gate runs before the catalog insert ([secret-catalog-store.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/src/modules/secrets/secret-catalog-store.ts:331)). This is a validator/fixture inconsistency, not evidence of a bad secret value. Use a valid tenant identity in a future check; do not alter existing tenant or API-key IDs as part of this report.

2. **The new-profile name can diverge from the key used for Save.** The Create Profile form records a target `profileName` and calls `getProfile` for it ([profiles-screen.tsx](/D:/Git/dugate/du-rework/orchestrator/apps/admin-web/src/features/profiles/profiles-screen.tsx:1147)). For a new `document-core` profile, it seeds the endpoint row from the selected endpoint action ([profiles-screen.tsx](/D:/Git/dugate/du-rework/orchestrator/apps/admin-web/src/features/profiles/profiles-screen.tsx:1198)); the generic draft seed also prefers the manifest action name ([profiles-screen.tsx](/D:/Git/dugate/du-rework/orchestrator/apps/admin-web/src/features/profiles/profiles-screen.tsx:2387)). On save, that row name becomes the upsert URL’s `profileKey`, while the refresh still targets the original `loadedAs.profileName` ([profiles-screen.tsx](/D:/Git/dugate/du-rework/orchestrator/apps/admin-web/src/features/profiles/profiles-screen.tsx:1310), [profiles-screen.tsx](/D:/Git/dugate/du-rework/orchestrator/apps/admin-web/src/features/profiles/profiles-screen.tsx:1349), [profiles-screen.tsx](/D:/Git/dugate/du-rework/orchestrator/apps/admin-web/src/features/profiles/profiles-screen.tsx:1421)). The browser draft showed target `codex-ui-check-20261014` and row `analyze`, matching this source path. No save succeeded, so persistence under either name is unverified. The UI should make the resource name and endpoint/action name explicit and ensure the save and subsequent reload address the intended resource.

3. **Connector capability state is incomplete.** The check showed management and provider test enabled, but `credentialWorkflow` disabled. The effective configuration lacked `DU_VAULT_KV_OPTIONS`, `DU_VAULT_KV_TOKEN`, and `DU_CONNECTOR_INITIAL_BINDINGS`; no credential values were printed. This state is independent of the tenant-ID failure; resolve tenant selection first, then separately verify the connector’s credential workflow composition and intended capability gates. The checked tenant value prevented validating connector/profile attachment end to end.

## Migration source audit and recommendation

Orchestrator applies sorted, pending migration files one at a time, with each file and its ledger insert in a transaction ([migrations.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/src/db/migrations.ts:36), [migrations.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/src/db/migrations.ts:181)). Its ledger stores sequence and filename, not a checksum ([migrations.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/src/db/migrations.ts:69)). The current object-drift guard checks declared tables and indexes, not full SQL content or schema state ([migrations.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/src/db/migrations.ts:105)). `migrationStatus()` is sequence-based ([migrations.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/src/db/migrations.ts:324)); filename/orphan checks run in `verifyMigrations()`, which the CLI calls after applying pending files ([migrate-cli.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/src/migrate-cli.ts:42)). Thus changed historical SQL can be skipped, and stale ledger history can be detected only after other pending files have already been applied.

Connector keeps a hard-coded ordered list of migration versions, skips versions already in `connector_schema_migrations`, and wraps each migration plus ledger insert in a transaction ([pg-client.ts](/D:/Git/dugate/du-rework/orchestrator/services/connector/src/db/pg-client.ts:43)). It has no content checksum, file discovery, status/verify command, or migration lock. The project-level `migrate` command runs the Orchestrator CLI only ([migrate.cjs](/D:/Git/dugate/du-rework/orchestrator/scripts/migrate.cjs:19)); normal Connector startup runs its own migrations ([composition.ts](/D:/Git/dugate/du-rework/orchestrator/services/connector/src/composition.ts:274)). `AUTO_MIGRATE` governs Orchestrator boot and defaults to false ([main.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/src/main.ts:596)); it does not govern Connector startup.

Recommended behavior: checksum each migration and make status/verify report pending, edited, renamed, removed, and unregistered files across both engines. Serialize apply operations per database. Automatically apply only new forward migrations; when an applied file’s checksum changes, fail closed with a diagnostic and require a new migration or an explicitly reviewed repair rather than replaying old SQL. Define a reviewed baseline for existing ledger rows that have no checksum. Make the dev migration step report both Orchestrator and Connector state before services start.

Existing evidence is limited: Orchestrator migration integration tests are gated by `DU_LIVE_INFRA=1` ([migrations.test.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/tests/migrations.test.ts:27)); its concurrency case follows tests that already migrate the database ([migrations.test.ts](/D:/Git/dugate/du-rework/orchestrator/services/orchestrator/tests/migrations.test.ts:123)). Connector’s durable migration test is gated and calls migrate twice sequentially ([durable-integration.test.ts](/D:/Git/dugate/du-rework/orchestrator/services/connector/tests/durable-integration.test.ts:3)). The migration audit itself was read-only and ran no migration tests. Separately, startup applied the one pending Orchestrator migration `0068` and passed verification before launching the local source services. The startup observation that only Orchestrator migration `0068` was pending and that health probes returned 200 does not demonstrate content-drift detection, concurrency safety, or Connector migration readiness.
