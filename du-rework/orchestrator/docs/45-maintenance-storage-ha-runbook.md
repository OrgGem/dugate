# Maintenance, storage generations, and replica rollout

This runbook covers the ORV14 maintenance controls. Actions use a preview followed by a version-checked confirmation, and durable work is polled by job ID. Use only the internal Admin plane and the platform maintenance role. Preserve preview IDs, job IDs, and audit evidence with the change record; never put credential bytes, provider payloads, or secret values in a reason or operator note.

## Queue admission and recovery

Read the queue inventory before changing admission. Pause prevents new claims while already accepted work can finish its lease, heartbeat, checkpoint, and completion path. Drain requests an observed worker acknowledgment and waits for durable active leases and fresh process evidence. A timeout remains DRAINING; an expired lease, stale heartbeat, UNKNOWN provider result, or missing counter is not proof of zero work. Resume is a separate previewed action and only applies to the selected scope. Retrying a failed delivery or task is allowed only when durable evidence proves the side effect was not sent; UNKNOWN effects remain held for reconciliation.

Create a queue-action preview, inspect its scope, current control revision, eligible work, and reason, then submit the preview ID with its expected version. Poll the returned durable action/job result until it is terminal. Preserve per-item outcomes, including PARTIAL and UNKNOWN; do not submit a second retry to make an uncertain outcome disappear.

## Retained storage generations

Storage generations are immutable. New artifact writes select the active generation once and persist that generation ID with the artifact or upload session. Reads, multipart completion, replay, ingestion, and cleanup resolve the pinned generation, including after a later generation is activated or the process restarts. The generation history endpoint is available at internal `GET /api/internal/maintenance/storage-generations` and returns newest first.

Stage an S3 generation with its approved endpoint, region, bucket, path-style choice, URL TTL, and exact managed-secret reference plus owner tenant UUID. The reference is an immutable `secretId@revision`; the service resolves that exact retained version for verification and at runtime. Keep the reference when editing a generation so the browser never needs secret bytes. PostgreSQL staging uses the minimal backend-specific request and does not accept S3 endpoint, bucket, or credential fields.

Test a staged generation before activation. The test writes a bounded encrypted probe object and sidecar, reads the exact versions, checks hashes and decryptability, then deletes those exact versions. A failed, interrupted, or uncertain test is not passing evidence. Activate with the observed control revision only after every check passes. Roll back by selecting a previously tested retained generation with a fresh compare-and-set version. Do not revoke or replace a secret version while an active or retained generation still depends on it.

## Cleanup and maintenance jobs

Preview retention, cache, orphan, and multipart cleanup before starting a durable job. The preview lists bounded candidates and their reference, state, age, and eligibility evidence. Execution rechecks eligibility and references immediately before each exact-version delete. Active operations, human-wait data, pinned artifacts, current generations, uncertain writes, and objects protected by a concurrent reader remain protected. Jobs persist per-item outcomes and resume from their journal after restart; UNKNOWN external effects are reconciled before another attempt.

Expired-lease and failed-delivery recovery follows the same rule: no automatic retry when the provider or destination may already have received the request. Use only the job's explicit safe-recovery action after the outcome is known.

## Two-slot rollout

A rollout manifest is a root-owned, digest-pinned deployment input. It pins both slots, exact image digests and Compose files, service/runtime identities, direct per-slot control endpoints, fixed serving-ingress probe, and the fixed reload command. Admin requests carry only a service, desired release, scope, and reason; they cannot select a process, path, executable, container argument, or credential.

The dedicated Host runner first prepares and health-checks the spare slot, then records a durable CUTOVER handoff. In the supported Host deployment, only the root-pinned Host controller identity claims and completes that handoff; the web process and retiring source replica do not run privileged deployment commands. The controller verifies the actual fixed-ingress response identifies the expected slot, runtime identity, revision, and image. Only then does it drain the old replica. Retirement requires a fresh exact-process DRAINING acknowledgment and authoritative zero work from every applicable source. A missing acknowledgment, stale observation, UNKNOWN provider invocation, active dispatch, active maintenance command, or nonzero lease leaves the old replica running and the job DRAINING/PARTIAL. Never force-stop a replica to make a rollout finish.

Orchestrator and Connector have HTTP serving probes. Worker replicas do not; replace them through the manifest-pinned process identity with a fresh worker control acknowledgment, SDK active-task count, and durable lease count. Do not use a synthetic Worker HTTP endpoint or infer process readiness from its database row alone.

The trusted service runtime requires all of these Orchestrator variables together: `DU_ORCHESTRATOR_RUNTIME_IDENTITY`, `DU_ORCHESTRATOR_RUNTIME_SLOT`, `DU_ORCHESTRATOR_RUNTIME_REVISION`, `DU_ORCHESTRATOR_RUNTIME_IMAGE_DIGEST`, and `DU_ORCHESTRATOR_SERVICE_RUNTIME_CONTROL_TOKEN`. Connector runtime control requires `CONNECTOR_RUNTIME_SLOT`, `CONNECTOR_RUNTIME_IDENTITY`, `CONNECTOR_REPLICA_ID`, `CONNECTOR_RUNTIME_REVISION`, and `CONNECTOR_RUNTIME_IMAGE_DIGEST` together. Values must match the trusted manifest and exact running process. Do not reuse admin, invocation, usage, or cost-control credentials for runtime control.

Run privileged maintenance from a separate Host deployment using `DU_MAINTENANCE_EXECUTION_ROLE=host`, `DU_MAINTENANCE_HOST_IDENTITY`, and the digest-pinned `DU_MAINTENANCE_BACKUP_MANIFEST_PATH` / `DU_MAINTENANCE_BACKUP_MANIFEST_SHA256`. The Host identity must equal both the manifest's `hostId` and `isolatedHost.hostRunnerIdentity`. The backup manifest pins the separate rollout manifest by path and SHA-256; those pins must match `DU_MAINTENANCE_MANIFEST_PATH` / `DU_MAINTENANCE_MANIFEST_SHA256`, and its six replica identities and direct Connector control endpoints must match the configured rollout manifest. Start the built Host entrypoint (`node dist/maintenance-host-runner.js`) as its own service. It uses the existing durable maintenance and rollout jobs and does not open an HTTP listener. The web role serves previews and job polling from safe manifest projections; it must not receive the Docker socket, secret files, bundle tools, database passfile, or recovery-key registry.

## Backup and isolated restore rehearsal

The configured backup target is the named platform target. Bundle creation runs only from the Host role and acquires durable admission, dispatch, provider-issuance, Connector invocation-polling, artifact-mutation, configuration-write, and usage-delivery fences. Every replica must provide a fresh process acknowledgment and authoritative zero active work; unknown permits, stale owners, and unresolved external commands block the snapshot. The bundle captures both database planes and exact artifact ciphertext/sidecar versions into an immutable encrypted bundle with checksums, bounded sizes, source cluster identities, and version/key-reference inventory. A fence failure or uncertain command does not produce a verified bundle.

Restore accepts only a new isolated database pair and a separately staged S3 generation. It does not change production ingress or switch the active storage generation. The Host restore adapter creates new isolated databases, validates the component and artifact bytes before writes, remaps artifacts to exact new storage object versions, pre-seeds the restored runtime control rows as DRAINING with no prior process acknowledgment, reconciles counts and key references, then requires a real isolated process probe. The final restore result records `cutover: NOT_PERFORMED`.

The Connector restore process uses `CONNECTOR_ISOLATED_RUNTIME_MODE=restore-rehearsal` together with all five exact Connector runtime-control variables above. It requires its matching pre-seeded DRAINING row before opening its listener, skips database migrations and control registration, starts no usage outbox dispatcher, and performs no background Vault renewal. It admits only reads and the authenticated `POST /internal/admin/runtime-control/observe` probe; invocation, provider-test, polling, delivery, and control-resume mutations stay disabled. The observation reports a fresh process acknowledgment separately from unresolved historical invocation counts. It does not clear UNKNOWN records or infer zero from lease expiry.

The isolated probe must use the restored process and staged dependencies with source databases, source Catalog keyrings, source Connector recovery registries, source Transit endpoints, source artifact Transit, and source Vault unavailable. Every required encryption family needs an exact independently retained key or authorized version-pinned reader, followed by real decrypt/read evidence. A reference list alone is not key portability proof. A synthetic cutover rehearsal must use a new isolated blue/green manifest, distinct fixed ingress, and the same trusted rollout prepare, candidate handoff, ingress verification, drain, and rollback paths. Do not run a customer or production cutover as part of this rehearsal.

## Evidence and failure handling

Retain the source-manifest digest, runtime image digests, scoped preview and job identifiers, bounded item evidence, observed control revisions, fixed-ingress result, storage generation IDs, bundle digest, and isolated probe evidence. Omit secrets, decrypted values, object keys in Admin-visible evidence, and provider request or response bodies. Keep IMPLEMENTED, VERIFIED, and ACCEPTED status separate; an owner smoke or synthetic fixture does not replace independent verification.
