# PROFILE-CALLBACK-20261006 - delivery mode and outbound authentication

Status: SPECIFIED / TODO. User request 2026-10-06; plan intake only, not implemented or dispatched. Existing coordinator assigns named owners and non-overlapping leases. Reuse P2-08, profile publication, Portal, egress and SEC-ENC work; no second dispatcher/store/SDK repo.

## Contract and processing flow

External submit callback.url -> authenticated profile/endpoint resolution -> immutable admitted policy revision -> terminal operation -> durable encrypted delivery -> Orchestrator webhook dispatcher -> authenticated external HTTP POST -> delivery receipt/retry -> Portal.
Orchestrator owns delivery; Connector and workers need no new callback responsibility.

Each tenant/profile revision/endpoint (canonical action or endpointSlug mapped by contract owner) has a versioned callback policy. Endpoint policy overrides profile defaults; absent policy preserves existing notification-only behavior. Public callers supply destination URL, not credentials, token endpoint or policy overrides. No callback URL means no delivery; disabled policy produces an explicit documented submission decision, never silent acceptance of an ignored requested callback.

Modes: notification_only uses existing event envelope; notification_with_result adds a versioned structured result and artifact descriptors. Freeze response/error schema and result projection matching authorized result API. Define behavior for failure/cancel/timeout, unavailable/expired result and oversized result. Bound JSON/body size; oversized/binary artifacts use authenticated result/download references with documented expiry, never silent truncation, raw storage URL or embedded arbitrary file bytes. Capture result consistently at terminal transition, including deferred result resolution, without extending retention. Manual resend cannot bypass expiry. Existing notification consumers remain compatible; mode opt-in per endpoint.

Policy snapshot pins tenant/profile/endpoint/revision/mode/auth reference/destination authorization. Credentials remain secret references, resolved with rotation/revocation semantics; security disable/revocation and current egress restrictions apply even to admitted old policies. Credential-bearing delivery destinations must match administrator-approved exact origins and optional path constraints. Never attach profile secrets to arbitrary caller-supplied callback hosts. Redirects disabled for authenticated callback/token requests; no credential forwarding to another origin. Preserve DNS-pinned SSRF checks and platform egress restrictions for both destination and token URL.

## Authentication configuration

Select none, configured_headers or oauth2_client_credentials. Existing HMAC delivery signature remains independent. Nonsecret additional headers may accompany OAuth2; reject conflicting Authorization headers and reserved signing/content/host/length/hop-by-hop headers, duplicates, CRLF and unbounded values. Secret header values are Vault/managed-secret references, write-only in Portal, never browser readback/log/plaintext DB. Define allowed names, example Authorization or X-API-Key, and optional validated prefix; no user-controlled script/template execution.

OAuth2 server-to-server default: grant_type=client_credentials; HTTPS token URL, client_id, client_secret reference, client_secret_basic or client_secret_post (one method), scope, optional explicitly supported provider audience/resource and bounded allowlisted extension form parameters. Provider extensions are not universal OAuth requirements; reject overrides of reserved grant/client credentials/scope fields and arbitrary URLs. Token request is application/x-www-form-urlencoded POST; validate status, bounded JSON, access_token, Bearer token_type, expires_in and provider behavior when lifetime omitted. Missing lifetime means no indefinite caching: obtain a token for the delivery or require documented provider lifetime policy. No password/implicit grant. Authorization-code or private-key JWT support requires a separately specified provider use case, not invented generic fields.

Send Authorization: Bearer <access_token> on callback. Cache in process memory only, scoped tenant/auth-policy revision/credential generation/token endpoint/client/scope/audience/resource. Renew before expiry with bounded clock skew; single-flight acquisition and bounded retries. Client credentials normally reacquires a token, does not rely on refresh_token. On an invalid-token 401 invalidate exact cache entry and reacquire/retry at most once within delivery budget using unchanged deliveryId; no refresh loop or automatic retry on generic 403. Restart reacquires tokens. Invalid credentials/token outage fail closed, no unauthenticated fallback. Token/secret never in URLs, delivery payloads, durable retries, audit or error strings. Key rotation/revocation invalidates cache. TLS required for external credential-bearing callbacks/token URLs; user internal DU HTTP exception remains unchanged.

Standards: https://www.rfc-editor.org/rfc/rfc6749 sections 2.3, 4.4 and 5; https://www.rfc-editor.org/rfc/rfc6750 sections 2.1 and 3.
