# Admin UI cho toàn bộ cấu hình Orchestrator — review và backlog (2026-10-02)

**Mục tiêu đã yêu cầu:** Admin cấu hình và kiểm tra **mọi cấu hình vận hành của DUGate qua UI**, gồm OIDC, user/role, profile, API key, Connector, business/workflow, bảo mật, giới hạn và cấu hình triển khai. UI phải hiển thị nguồn giá trị, revision, trạng thái áp dụng và người thay đổi. Một thao tác Save chỉ được báo thành công khi hệ thống đã lưu và áp dụng theo đúng loại cấu hình; cấu hình cần rollout phải hiện `pending activation` cho tới khi rollout được xác nhận. Đây là backlog **SPECIFIED** sau review source, chưa phải bằng chứng implementation/verification/acceptance.

## Tiến độ triển khai 2026-10-02

- API key: Admin shell đã nối form issue/revoke đến `POST /api/v1/admin/actions`, kiểm tra role và CSRF, sinh key ngẫu nhiên trong BFF và hiển thị raw key duy nhất trong phản hồi `no-store`. Dispatcher giữ hợp đồng hiện hành cho các API client; đường BFF không gửi idempotency key. Đây là phần triển khai, **chưa có test/acceptance**.
- Connector: form rotate credential và readiness probe đã nối action API với role/CSRF; rotate cần Vault workflow được cấu hình và hiện chưa thể dùng trên deployment nếu GET không trả secret slot. Readiness chỉ kiểm tra sức khỏe dịch vụ, chưa xác nhận credential/provider. Connector GET vẫn là projection từ URL cấu hình, chưa phải revision ledger; ACUI-06 còn mở.
- Profiles/Connectors chỉ cho Admin đọc trong shell trong khi BFF còn dùng platform bearer. POST section chưa có handler trả 405, không còn báo lưu giả. Cần tenant-aware BFF trước khi mở lại quyền operator.
- ACUI-02/03/04/06/07/08/09/10 và phần còn lại của ACUI-05 vẫn **chưa triển khai**; không coi các form và endpoint scaffold là bằng chứng chức năng. `tsc --noEmit` của Orchestrator đã chạy thành công; chưa chạy test chức năng.

Plan này cụ thể hóa `ORCH-PAR-01/02/03/04/05/06/10`, `LOCAL-00..06`, `OIDC-*`, `P6` và `ADM-UX`; không tạo cổng release mới. Phần bắt buộc trước cutover được `ORCH-PAR-00` ghi vào dependency register. Các mục thuộc scope release phải đạt `G-ADMIN-OPS`, `G-SEC`, `G-LOCAL-ADMIN`, `G-COMP` liên quan rồi mới xét P8-08/G6. ## Nguyên tắc cấu hình chung

1. **Một catalog cấu hình có schema:** mỗi setting có `id`, service, scope (`global|tenant|business|profile|user`), kiểu và validation, quyền đọc/ghi, nguồn hiện hành, secret policy, `effectiveRevision`, `desiredRevision`, thời điểm áp dụng, dependency và rollback. UI lấy catalog từ API, không hardcode một danh sách env rời. Tạo inventory từ `main.ts`, `oidc-boot.ts`, `document-core/src/config.ts`, `connector/src/entrypoint.ts`, `.env.example`, các bảng policy và Connector revision; đánh dấu rõ item đã quản lý được.
2. **Ba cơ chế áp dụng:** cấu hình nghiệp vụ lưu versioned trong PostgreSQL và có hiệu lực với request mới; secret được nhập một lần rồi lưu tại Vault/secret manager, UI chỉ thấy ref/masked metadata; cấu hình hạ tầng hoặc process (DB URL, Redis, bind port, S3 endpoint, TLS, worker concurrency, auth bootstrap) được UI **staging** qua deployment adapter, validate và rollout/restart có kiểm soát. Nếu chưa có deployment adapter, UI phải ghi `unmanaged / requires deployment action`, không cho Save giả. Bootstrap đầu tiên phải có CLI/secret file một lần để Admin có thể đăng nhập trước khi dùng UI.
3. **Read/mutation contract thống nhất:** Admin session local/OIDC → BFF/shell với principal + tenant server-side (mutation thêm CSRF) → typed Admin API → service/DB/Connector/Vault/deployment adapter → audit cùng transaction hoặc outbox → read-after-write xác nhận revision/effective state. BFF không dùng platform `ADMIN_TOKEN` để đọc hộ operator/viewer. Dùng `expectedRevision`/CAS, idempotency key, tenant fence, phân quyền phía server, validation theo schema và lỗi có thể sửa trên form. Không chuyển `ADMIN_TOKEN`, Vault token, API key raw đã cấp hoặc provider secret vào browser/HTML/log.
4. **Phân quyền:** `admin` quản lý IdP, role, user, key, credential và global setting; `operator` chỉ được thay các policy tenant được cấp; `viewer` đọc metadata đã che bí mật. Matrix cụ thể do `LOCAL-00`/security ký; UI ẩn nút là trợ giúp, API vẫn từ chối độc lập. Cần chống tự khóa hết admin: staged OIDC change có test-login, xác nhận từ phiên admin khác hoặc break-glass đã kiểm tra, rollback timeout và revoke session khi role/mode đổi.

## Thứ tự triển khai

1. `ACUI-00` + `LOCAL-00` khóa catalog, role matrix, config apply contract và bootstrap. `ACUI-01` làm BFF/CSRF/notification dùng chung; quyền/CSRF phía server hoàn thành trước mutation mới.
2. `ACUI-02/03` để admin tự quản IdP và user; đồng thời `ACUI-04/05/06` theo file lease riêng cho profile/key/Connector. `server.ts`, `shell-router.ts`, migrations và shared contracts chỉ một writer mỗi thời điểm; module và renderer độc lập có thể làm song song.
3. `ACUI-07/08/09` nối business, policies và deployment. Hoàn thành hành trình Admin config→public submit→worker/result trước `ACUI-10`; test chi tiết được tách packet sau từng vertical slice, không chặn implementation độc lập.
4. `ACUI-10` xác nhận toàn bộ config trong catalog có UI và hiệu lực thật. Item chưa có adapter hoặc không có receipt vẫn `[ ]`; không gọi mục tiêu “mọi config qua UI” hoàn thành từ một vài màn đã render.
