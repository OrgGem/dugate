# Profile control plane implementation plan

> **State: IMPLEMENTATION AND REMEDIATION COMPLETE (ACCEPTED).** All eight remediation findings (PC-R01 through PC-R08) and Wave 3 audit findings are resolved, verified, and officially signed off by independent review (Codex Reviewer). Group-root profile control plane, zero-key CRUD, root grant ledger, canonical lock ordering (`root -> key -> grant`), resolution fingerprinting, workflow execution pins, and parameter partitioning are fully proven across offline and live PostgreSQL 16 suites. Antigravity coordination is complete; ready for deployment and cutover.

## Goal and boundaries

Make a profile group the durable configuration root. The group owns business/function selections and current authorization mode. Existing child profile IDs and immutable revisions remain the endpoint configuration and in-flight execution pins. A group can be read and edited with zero active API keys. API-key grants are separate mutable access state, and rolling back configuration never restores a revoked grant.

The work covers `du-rework/` Orchestrator contracts, migrations, service/auth paths, Admin BFF and Workbench, plus worker/Connector consumers only where an explicit wire or policy change requires it. Connector continues to own provider credentials and recipes. Orchestrator owns API-key authentication and profile grants, including Workbench and Connector-probe authorization. Runtime API v1 remains the normative worker boundary; SDK-free workers remain supported.

This plan does not create a second business/template registry, a new user role model, a provider-side model enforcement feature, or a deployment claim. Workflow selections use the existing workflow registry and revision. Legacy standalone profile self-service remains supported under an explicit mode. Group children reject direct legacy mutation.

## Settled data and authorization model

1. **Group root and config revisions.** Keep `profile_groups.active_revision` as the configuration CAS pointer. Add `auth_mode='API_KEY'`, `auth_authority` with `CHILD_PROJECTION | GROUP_GRANT`, and `access_version bigint NOT NULL DEFAULT 1`. Existing groups start as `CHILD_PROJECTION`; new v2 groups start as `GROUP_GRANT`, including groups with zero keys. Cutover is one-way per group and occurs only after inventory gates pass. Config revisions contain business/version, manifest digest, function selectors, child profile ID/revision, policy and connector pins. Remove key selection from v2 revisions. Make historical `api_key_id` nullable; retain the old value for audit only. Store the Admin actor separately using the existing Admin identity format; new group writes never require an arbitrary active API key as author.
2. **Key modes.** Add an explicit key mode with values `GROUP_MANAGED`, `LEGACY_STANDALONE`, and `UNMANAGED_LEGACY`. A missing or unknown value after migration is an authorization error. `GROUP_MANAGED` is authorized only by a current root grant and cannot use child-membership fallback. `LEGACY_STANDALONE` retains direct profile membership/self-service semantics, including when all historical membership rows are revoked. `UNMANAGED_LEGACY` is reserved for a key proven to have never had a profile membership or group association and used by the legacy no-profile path. Zero active memberships alone is not proof. Ambiguous inventory rows remain on their old fenced authority and block conversion; never classify them as unmanaged to make migration pass.
3. **Root grant ledger.** Add `profile_group_api_keys(group_id, tenant_id, api_key_id, state, granted_at, granted_by, revoked_at, revoked_by)`. Enforce `(group_id, tenant_id)` and `(api_key_id, tenant_id)` composite tenant-safe foreign keys (adding the key pair uniqueness only if the existing schema lacks it). Keep revoked rows as tombstones and make each managed key ID permanently associated with at most one group (unique across active and revoked rows). Add an active lookup index. Grant/revoke increments `profile_groups.access_version`; config publish/rollback does not. Grant mutations use expected access version and an idempotency key.
4. **Child author metadata, defaults and constraints.** Relax `profile_bindings.api_key_id`, `profile_names.api_key_id`, and `profile_group_revisions.api_key_id` to nullable historical author references; preserve old IDs. Add `profile_bindings.request_defaults jsonb NOT NULL DEFAULT '{}'`; existing/v1 revisions read as `{}`, and v2 config validates the typed per-field values against the pinned manifest. Every child revision copy, group revision, rollback and read path preserves that field. The sealed operation input pins resolved request values; the child profile revision plus immutable manifest digest pins the exact config and source-resolution contract used for retry. Replace the old all-row name uniqueness with a legacy partial unique index for standalone names and a group-scoped unique index for grouped children. Add a `groupOwnerId` append operation that reads tenant from the locked group, records the Admin actor separately, and never creates an ACTIVE `profile_api_keys` membership for a group-managed key. New grouped appends do not accept `apiKeyHash`. Group children remain protected from direct old API-key attach/upsert/self-service mutations.
5. **Key state transitions.** Global key revoke changes `api_keys.status` and revokes every active root grant in the same transaction, incrementing each affected access version; all public authentication stops immediately. Root grant revoke changes only that group grant and access version, leaving the API key status unchanged. A rollback only moves the config revision pointer and cannot reactivate a grant. Rotation creates a new key ID and copies only the current same-group grant (or, for legacy modes, the exact existing legacy memberships); it never adds functions or profiles. A never-associated `UNMANAGED_LEGACY` key can rotate while preserving that mode. A standalone key with only revoked membership tombstones remains `LEGACY_STANDALONE` on rotate.
6. **Key issuance.** New group keys are created by the group-key operation and granted atomically. Return the raw key once with `Cache-Control: no-store`; persist only hash/prefix/note. Existing issue actions may not infer a group or silently attach child memberships. `identity.issue`/`apikey.issue` routes must reject grouped child profile IDs; use the root grant operation instead.
7. **Transaction and lock order.** Apply one lock order to config writes, group grant/revoke, key issue/rotate/global revoke, public admission, idempotent replay and retry: pre-read affected group IDs without locking; lock affected group roots in sorted ID order; lock sorted business/version/selector rows; lock sorted API-key rows; then lock grants/tombstones, child active pointers/revisions, and operation/idempotency/task/outbox rows. Re-read associations and expected revisions/states after locks; compare-and-set before commit. Legacy standalone paths with no group lock business/selectors before key rows. Global revoke enumerates candidate roots before locks, then revalidates after acquiring roots and keys; a concurrent grant must see a revoked key and fail. No path may lock a key and then a group. Never authorize from a preflight-only read.

### Route authorization and operation ownership

| Request class | Authorization rule after cutover |
|---|---|
| New public action, catalog/preflight, and Connector/provider probe | Require ACTIVE presented key. `GROUP_MANAGED` resolves a current root grant and the unique matching active group member; no child fallback. Grant revoke denies new admission/probe. |
| Existing operation/result/status/artifact/download/upload reads | Preserve existing ACTIVE key, tenant, and exact stored owner-key checks. A different key on the same group cannot read or upload to the operation. Group grant revoke does not retroactively revoke an active original owner's reads; global key revoke blocks authentication everywhere. Do not rewrite operation/upload owner IDs during group conversion. |
| Fresh retry | Admin-only; retain original operation key owner. Require that original key ACTIVE and, for a managed operation, current matching group grant, enabled endpoint and current business/version readiness. Reauthorize before idempotent/coalesced replay and before insert. |
| Global key revoke | Mark key inactive and revoke all current group grants transactionally; every route still first requires ACTIVE key status. |

V1 public request and response bodies stay unchanged. For `GROUP_MANAGED` keys, existing v1 action/catalog/preflight routes use the root-grant resolver and current group/member selector at admission; the pinned manifest/profile-resolution capability determines semantics, never a client route or body field. V1 does not require a fingerprint and resolves current configuration at admission. If a root grant is absent, the matching active member is absent, or a selector matches multiple active members, deny the request; never fall back to child membership or choose arbitrarily. Legacy standalone and `CHILD_PROJECTION` groups retain their existing v1 behavior until conversion.

V1 `/api/v1/admin/profile-groups` is read-only compatibility after cutover. A read projects the singular `apiKey` only if exactly one active root grant exists; zero or multiple grants return `409 PROFILE_GROUP_V2_REQUIRED` and direct callers to v2. V1 POST/PUT/rollback and child attach/upsert/self-service mutations for a `GROUP_GRANT` group or its children return `409 PROFILE_GROUP_V2_REQUIRED`; they may not alter the root grant ledger or write child-membership authorization. Before cutover, the existing `CHILD_PROJECTION` writer remains available. Do not loosen `.strict()` v1 parsing to silently accept v2 fields.

`resolutionFingerprint` is a deterministic SHA-256 digest of canonicalized server-derived refs plus normalized submission identity: tenant, authenticated/explicit owner key ID, group ID/revision/access version, child profile IDs/revisions, business version/manifest digest, function selector, tenant-default revision, connector binding revisions, workflow revision/digest where applicable, and a digest of normalized request data. It is a concurrency guard, not a bearer credential or authority token. The server computes it for v2 profile preview and Workbench preview, and recomputes it for v2 profile operations and Workbench submit; the client cannot select the resolver version or any snapshot ref. V1 public requests do not carry it and resolve current config at admission. A mismatch for a new v2 submission returns 409 `PROFILE_CHANGED` before durable operation/task/outbox creation. Submit separately rechecks current key status, current root grant, mode, tenant, endpoint enabled state, and local-user assignment inside the write transaction. Idempotency lookup occurs only after current authorization: an exact replay by the original owner with the same scope, request digest, and original fingerprint returns its pinned operation despite later config drift; a changed request or fingerprint under the same idempotency key conflicts. A new submission with a stale fingerprint returns 409. Do not add a signing secret for this check.

## Manifest parameter and lock resolution

1. Keep `inputSchema`, `outputSchema`, and `profileSchema` independent. Overlap is allowed and intentional, including `example-review.enableReasoning` and `lc-checker.maxConcurrency`. Do not mechanically move or rename fields.
2. Add an optional immutable manifest capability `parameterResolution: { version: 2, fields: { <property>: 'requestDefaults' | 'profileSettings' }, applyTopLevelDefaults: boolean }`. Absence means v1 semantics exactly. Each mapped property has one declared source; the server never infers it from schema overlap. Include the capability in the manifest digest and function catalog.
3. V2 endpoint config stores both `profileSettings` and `requestDefaults` as per-field `{value,isLocked?}` records using the existing `ProfileParameterValue` contract. `profileSettings` remains only in the pinned profile policy and uses existing profile merge/lock behavior; never inject it into request input. `requestDefaults` is validated against manifest fields mapped to that source. For an unlocked request default, explicit client input wins; otherwise its configured value fills the absent mapped property. A locked request default rejects any client-supplied value, including an equal value, and fills the property when absent. If neither client input nor configured request default supplies the field and top-level defaults are enabled, `inputSchema.properties.<name>.default` fills it. There is no deep merge. The resulting request `parameters` object is carried in the existing Runtime API v1 task input; `profileSettings` remains in the existing profile snapshot. The existing SDK and SDK-free workers therefore receive the values through existing fields, with no new required Runtime wire field or SDK dependency. Preserve explicit `null`, `false`, `0`, `''`, empty arrays and objects. Defaults under nesting, `$ref`, combinators or another unsupported location are rejected at publication only when this capability is enabled; the schema remains usable under v1.
4. At v2 publish, normalize each stored field's `isLocked` as `explicit isLocked ?? mapped schema.defaultLocked ?? false`; source mapping selects the relevant schema and prevents inference where `inputSchema` and `profileSchema` overlap. Keep stored legacy `true` and `false` behavior intact. Public client input for any locked mapped field is rejected even when equal to the stored value. Admin provider-test accepts an explicitly supplied model only when it equals the effective locked model. The worker SDK's provider model continues to come from the existing pinned `profile.policy.parameters.model`; a trusted handler's invoke options continue to take precedence because model resolution fills only an absent option, as in [`task-context.ts`](../orchestrator/packages/worker-sdk/src/task-context.ts). A request input property named `model` filled from `requestDefaults` remains action input; it affects provider model only if the business handler explicitly maps it to invoke options. Provider-side model enforcement is separate scope.
5. Test v1 manifests/operations byte-for-byte for absent/explicit/null/falsy values. Add v2 cases for each source, intentional overlap, absent-only defaults, top-level-only rejection boundaries, shallow replacement, default lock normalization, locked same-value public rejection, equal provider-test acceptance and trusted handler precedence.

### PC R01 Explicit key mode controls fallback

**Evidence:** [`profiles.ts`](../orchestrator/services/orchestrator/src/modules/profiles/profiles.ts), `selectActiveRow` around lines 530–535, returns `legacy` when no membership rows exist. The non-group branch of [`submission.ts`](../orchestrator/services/orchestrator/src/modules/operations/submission.ts), around line 454, still reaches that resolver. Both key issue paths permit a standalone key without assigned profiles. Rotation of a standalone key whose memberships are all revoked produces a replacement without membership history and exposes the same fallback.

**Fix scope:** Make explicit `key_mode` authoritative at every admission/discovery fallback. `LEGACY_STANDALONE` with no eligible membership is denied; only a verified `UNMANAGED_LEGACY` key may use unmanaged behavior. Preserve mode and effective denial across rotation; do not infer new entitlement from missing membership history. Reconcile both issue and rotation APIs.

**Regression gate:** Exercise both lifecycle entry points with an empty-profile standalone key and with a rotated tombstone-only standalone key. Public action admission and discovery deny unassigned functions, and no operation/task/outbox is created. An explicit unmanaged key retains only the intended legacy behavior; assigned standalone and group-managed keys keep their scoped behavior.

### PC R02 Pin selected workflows into execution

**Evidence:** [`submission.ts`](../orchestrator/services/orchestrator/src/modules/operations/submission.ts), around lines 1162–1165, fingerprints `workflow: null`; `submitProfileV2` around lines 2054–2065 does not forward `workflowSchemaPin`. Save-time validation does not supply the execution pin or recheck a subsequently retired workflow.

**Fix scope:** Resolve the selected workflow from the existing registry during preview and admission; include its identity/revision/digest in the fingerprint and pass the validated pin into workflow compilation. Persist the workflow identity and sealed recipe carrier on the operation, deliver the compiled workflow to execution, and preserve/reseal these pins on retry. Keep ordinary action functions unchanged.

**Regression gate:** A real v2 workflow preview/submit persists the selected registry slug/revision/digest and produces the expected compiled payload and recipe authorization. Retiring the selected revision between preview and submit denies fresh admission with zero durable execution rows. Changing the selected workflow invalidates the preview. Retry retains the original workflow/recipe snapshot and follows current retry authorization.

### PC R03 Serialize retry authorization and revocation

**Evidence:** [`retry.ts`](../orchestrator/services/orchestrator/src/modules/operations/retry.ts), around lines 84–89, 186–198 and 372–398, checks key/group/grant without retaining their authorization locks through insertion. [`profile-groups.ts`](../orchestrator/services/orchestrator/src/modules/profiles/profile-groups.ts), `revokeGroupGrant` around line 1861, uses a group-root lock that retry does not acquire. Revocation can commit between the final authorization read and the retry insert.

**Fix scope:** Apply the universal sorted root → selector → key → grant → operation/task lock order to retry, including reauthorization before coalesced replay. Do not fix this by adding a group lock after an already-held operation lock. Pre-read identities, acquire locks in order, re-read ownership/current authorization and original pinned execution, and hold the required locks to commit.

**Regression gate:** Use two real PostgreSQL connections and deterministic barriers, rather than sleeps. When revoke wins, retry must deny and create no execution rows. When retry wins, revoke waits for that serialized admission and invalidates later attempts. Repeat for global key revoke, endpoint removal/disable and the active-retry replay branch; preserve the unknown-provider-outcome guard and show no deadlock or partial outbox/task writes.

### PC R04 Fingerprint the complete defaults snapshot

**Evidence:** [`submission.ts`](../orchestrator/services/orchestrator/src/modules/operations/submission.ts), around line 1114, uses only `tenantDefaults.aiRevision`. Tenant prompt settings publish an independent `promptRevision`. Publishing prompts after preview can therefore leave the fingerprint unchanged while execution receives different prompts.

**Fix scope:** Extend fingerprint reference contracts and calculation to include both settings revision streams and their existing snapshot/digest identity where applicable. Bind the fingerprint to the same tenant-default snapshot and connector/prompt references that admission seals; revalidate changes at the transactional boundary rather than loading an unverified replacement snapshot after fingerprint comparison. Update public v2 and Workbench consumers together, with an explicit reload/preview-again path for older fingerprints.

**Regression gate:** Preview, publish only prompts while AI revision stays unchanged, and submit: return a stale-resolution conflict with no operation/task/outbox. Also cover AI-only changes, no-defaults/null snapshots, unchanged exact replay, and a settings update between fingerprint validation and durable admission. The accepted fingerprint and stored revision/digest fields must identify the same snapshot.

### PC R05 Use root grants throughout Connector tests

**Evidence:** [`probe-authorization.ts`](../orchestrator/services/orchestrator/src/modules/connectors/probe-authorization.ts), around line 30, still joins active `profile_api_keys` for public readiness. [`provider-test.ts`](../orchestrator/services/orchestrator/src/modules/connectors/provider-test.ts), around lines 204 and 296, retains child-membership checks for local authorization/reservation. Provider-test admission in [`submission.ts`](../orchestrator/services/orchestrator/src/modules/operations/submission.ts) also calls the legacy profile resolver. New managed keys lack these memberships, and conversion tombstones them.

**Fix scope:** Migrate readiness, provider-test admission, reservation and local-user validation to the shared authority-aware resolver. Recheck current root grant, selected active child configuration, connector binding/revision and existing actor/tenant assignment fences before reservation. Preserve standalone behavior and the explicit equal-locked-model provider-test rule; do not reintroduce child membership as managed authorization.

**Regression gate:** Test newly issued managed keys and converted groups with no active child memberships. Their configured Connector readiness and permitted provider tests succeed; revoked grants, disabled endpoints, unbound Connectors and cross-tenant probes deny. Exercise both platform Admin and existing local-user fences. Ensure denial occurs before provider invocation/reservation side effects and that legacy standalone probes retain their previous scope.

### PC R06 Preserve locks during value edits

**Evidence:** [`profile-group-editor.tsx`](../orchestrator/apps/admin-web/src/features/profiles/profile-group-editor.tsx), around line 434, replaces a request-default entry with `{ value }`. It discards an existing explicit `isLocked: true`; when the schema does not default to locked, backend normalization subsequently unlocks the field.

**Fix scope:** Preserve the full per-field metadata when editing the value. Any explicit lock-change control must be distinct from value editing and match the existing authorization model. Keep unset, explicit null, false and zero semantics intact during load/edit/save.

**Regression gate:** Load a locked request default with no schema `defaultLocked`, edit only its value, save and reload: it remains locked. An actual submit supplying that field is still rejected, including a same-value override. Cover unlocked entries, schema-derived locks and explicit false/null/zero values. Include a UI interaction test, not only a handcrafted save-body test.

### PC R07 Render only the declared parameter source

**Evidence:** [`profile-groups.ts`](../orchestrator/packages/contracts/src/profile-groups.ts), `ProfileGroupFunctionSchema` around line 70, omits `parameterResolution`. [`profile-group-editor.tsx`](../orchestrator/apps/admin-web/src/features/profiles/profile-group-editor.tsx), around lines 596 and 618, renders all profile-schema fields into policy settings and all input fields into request defaults. For example-review V3, editing visible `Profile settings.enableReasoning` saves a value that the resolver ignores because its declared source is `requestDefaults`. Request-default controls are also offered for v1 manifests where that bag is inert.

**Fix scope:** Carry the immutable capability/mapping through registry discovery, contracts, BFF and client types. Filter each editor section by the declared source; preserve intentional v1 schema overlap and do not silently enable v2 semantics for old manifests. Hide or clearly disable unsupported/inert request-default controls. Backend validation must reject misplaced v2 values rather than silently accepting ignored configuration.

**Regression gate:** With the real opt-in example-review manifest, `enableReasoning` appears only in its effective request-default editor; changing it alters preview and pinned execution input. Profile-only settings remain in the policy snapshot. A capability-free v1 manifest keeps its legacy editor/merge behavior and exposes no misleading v2 control. Use the real catalog/resolver contract in an integration test; a capability-free stub cannot prove this mapping.

### PC R08 Reauthorize managed v1 replay

**Evidence:** [`submission.ts`](../orchestrator/services/orchestrator/src/modules/operations/submission.ts), around lines 1427–1453, returns the existing idempotent operation before managed admission authorization. Global authentication only checks ACTIVE key status/mode, so root-grant revoke alone does not prevent a successful v1 submit replay.

**Fix scope:** Reauthorize managed v1 requests before both the fast replay path and the transactional replay/create path. Preserve exact same-owner/request replay across allowed configuration drift and keep conflict behavior for changed requests. Do not change historical result/status/download ownership: an active original owner may still read an old result after grant revoke, even though submit/retry admission is denied.

**Regression gate:** Accept a managed v1 submission, revoke only its root grant, then repeat the same idempotency key/body: submit must deny without creating rows. Separately verify the original active owner can still read the historical result, global key revoke denies both operations, authorized replay across permitted config drift returns the original pin, and changed-body replay conflicts.
