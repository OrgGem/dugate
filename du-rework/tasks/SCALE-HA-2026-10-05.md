## 0. Bối cảnh và vì sao cần packet này

Kiến trúc hiện tại đã đúng 3 việc khó nhất (đối chiếu `architecture/12-flows-and-data.md` §2–§3, `packages/contracts/src/queue.ts`, `packages/worker-sdk/src/worker.ts:268-296`, `services/orchestrator/src/modules/queue/dispatcher.ts:28-87`):

- PostgreSQL là sự thật (operation/task/outbox trong 1 transaction lúc submit); BullMQ chỉ là kênh delivery phát lại được.
- Claim là fencing authority (409 busy / 410 terminal dừng an toàn; lease epoch + heartbeat; stale report bị từ chối).
- Dispatcher multi-replica an toàn (`FOR UPDATE SKIP LOCKED` + `claim_until`/`dispatched_at` + jobId deterministic dedup).
- Worker stateless, không giữ DB credential, giao tiếp qua runtime API + artifact grant + S3.

Vì vậy mô hình "thêm worker là thêm throughput" và "N orchestrator sau LB không sticky" **đúng về thiết kế**, nhưng review code + tài liệu capacity (`architecture/07-capacity.md`, `architecture/06-aws-deployment.md`, `infra/deployment-architecture.md`) cho thấy còn ~8 điểm nghẽn: thêm replica lúc này chỉ **chuyển bottleneck** sang DB pool, Redis, migration race, provider quota hoặc drain/health cấu hình sai. Mỗi mục dưới đây có đủ 4 phần: hiện trạng (file:line), phân tích (vì sao nghẽn), giải pháp, acceptance đo được.

Công thức sizing nền (từ `architecture/07-capacity.md` §Công thức, giữ nguyên, không phát minh số mới):

- `N_worker >= ceil(λ × T / (c × u))`, với λ = jobs/s, T = thời gian giữ slot, c = slots/EC2, u = utilization mục tiêu (vd 0,7). T là thời gian **giữ slot thật**, không phải wall-clock cả operation nếu job yield khi chờ provider/children.
- `slots <= floor((RAM khả dụng − overhead) / peak RSS mỗi task)` rồi benchmark lại. Parser CPU/RAM là trần cứng.
- Token quota: `λ <= token_budget_per_minute / (60 × expected_tokens_per_job)` (cộng retry headroom; quota theo provider account/model, không nhân theo số Connector replica).

## 1. SCALE-01 — DB pool / connections (P0, blocker HA)

| Phân tích | Mỗi orchestrator replica giữ tới 10 connections; tổng = `N_orch×10 + N_conn×pool + worker-infra + migration/verify CLI`. | Giải pháp | (a) Tính toán connection budget: `PG max_connections >= N_orch×pool + N_conn×pool + headroom(migration/verify/backup)`; (b) Bật PgBouncer transaction-pooling trước primary (hoặc giảm `max` mỗi replica + tách role platform/connector đã có trong topology); (c) Review index cho sweep path: outbox predicate (`dispatched_at IS NULL`, `claim_until`, `due_at`), lease sweep, queue-integrity SQL (`runtime.ts:80-103`) — verify bằng `EXPLAIN` trên dữ liệu thật; (d) Không dùng read replica để "scale writes". |
| Acceptance | Budget connections ghi thành bảng (N_orch/N_conn × pool + headroom) khớp `SHOW max_connections`; soak 1→2→4 replicas không chạm `too many connections`, commit latency p95 không tăng quá ngưỡng P8-05 chốt; `EXPLAIN` các sweep query dùng index (không seq-scan toàn bảng outbox/tasks). |

| Giải pháp | (a) Chọn 1 backend cho smoke: managed ElastiCache/Valkey với stable failover endpoint **hoặc** self-hosted có replication/fencing/runbook split-brain — ghi TLS/IAM/SG/persistence/failover settings; (b) `noeviction` cho DB/prefix chứa queue + quota; memory/latency/persistence-lag alarm; (c) Failover rehearsal: kill primary, đo reconnect BullMQ/ioredis, verify dispatcher + quota bảo thủ sau counter loss (không mặc định `used=0`), session vẫn valid cross-replica; (d) Nếu chọn cluster-mode: chứng minh BullMQ/client đã pin tương thích **trước** bật failover tự động. |
| Acceptance | Failover drill có log: RPO/RTO đo được, 0 logical task đã accepted bị mất (DB truth/outbox recovery, cho phép duplicate delivery), quota không vượt cap sau failover, p95 queue-wait không vỡ ngưỡng P8-05. |
| Phụ thuộc | DATA-00 (cluster mode decision), DEP-01, P8-06. |
