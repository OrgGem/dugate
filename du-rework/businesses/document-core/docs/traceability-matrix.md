# Requirements Traceability & Authorization Matrix (P0-01)

## 1. Overview & Baseline Scope

This document establishes the bidirectional traceability matrix mapping high-level business requirements (**BR-01 through BR-12**) from [docs/01-product-scope.md](../../../docs/01-product-scope.md) to system use cases (**UC-01 through UC-08**), architectural mechanisms, and automated test catalog identifiers across `@du/document-core`, `@du/document-kit`, and `@du/example-review`.

It clearly distinguishes:
- **`[VERIFIED]`**: Implemented in codebase and proven by automated passing test suites.
- **`[PARTIAL]`**: Implemented baseline in place, but awaiting upstream platform integration or running with explicitly documented test shims.
- **`[PLANNED - PENDING PLATFORM]`**: Architectural guarantees targeted for platform lane completion (R08-01 fail-closed auth LANDED, W13-C child/wait continuation LANDED, W11-C1 canonical invocation hash LANDED; remaining PLANNED: artifact TTL sweep/quotas, UC-07 v1/v2 drain breadth, operator runtime endpoints).

## 3. Actor & Authorization Matrix (Planned Controls vs Verified Facts)

The architecture defines five distinct actors with strictly separated boundaries.

> [!IMPORTANT]
> R08-01 token separation + fail-closed API-key scoping are **LANDED and VERIFIED** (server.ts requireAdmin/requireRuntime + boot guard; runtime.test.ts R08-01 trio; unknown x-api-key rejected, no dev fallback). Worker package boundaries and lack of direct database credentials are **VERIFIED facts**.

| Actor | Identification Mechanism | Permitted Operations | Explicitly Forbidden Operations | Implementation Status |
|---|---|---|---|---|
| **API Client** | `X-API-Key` header | - Submit operation for allowed actions in profile<br>- Poll operation status<br>- Fetch final operation result & usage<br>- Request operation cancellation | - Access other tenants' data<br>- Call administrative endpoints (`/api/v1/admin/*`)<br>- Claim tasks or report task progress<br>- Direct provider connector invocation | **`[PARTIAL]`**: Client submission, polling, result fetching verified in E2E. fail-closed API-key scoping LANDED (R08-01: unknown/revoked keys denied, no dev fallback; runtime.test.ts R08-01 trio). |
| **Administrator** | Bearer Admin Token (`ADMIN_TOKEN`) | - Create/rotate/disable connector configurations<br>- Create/edit profiles and action limits<br>- Enable/disable business versions<br>- Trigger maintenance sweeps | - Bypass audit logs<br>- Expose raw connector decryption keys via public API<br>- Inject arbitrary unvalidated code into worker queue | **`[PARTIAL]`**: Admin version enablement verified in E2E. non-interchangeability LANDED (server.ts boot guard + enable-rejects-runtime-token test). |
| **Operator** | Scoped Operator Credential | - Read system health, queue depths, error rates<br>- Inspect dead-letter queues and failed operations<br>- Trigger manual replay of failed operations | - Modify production connector credentials<br>- Alter business profile permissions | **`[PLANNED]`**: No service runtime route/test; operator scope is admin view-model nav only (admin-view-model.test.ts navigation visibility); service endpoints PLANNED. |
| **Business Developer** | Repository Access & Manifest Registry | - Author business definitions using `@du/worker-sdk`<br>- Define manifest, actions, input/output schemas<br>- Publish independent worker container images | - Write platform code (`services/*`)<br>- Access production database directly<br>- Import internal service packages into business | **`[VERIFIED]`**: Enforced by ESLint and architectural boundary tests (`tests/package-boundary.test.ts`). Worker has zero platform DB dependencies. |
| **Worker Identity** | Bearer Runtime Token (`RUNTIME_TOKEN`) scoped to business | - Claim assigned queue tasks (`POST /tasks/:id/claim`)<br>- Send heartbeats & lease renewal<br>- Request upload/access grants for artifacts<br>- Request short-lived connector invocation grants<br>- Report durable checkpoints and terminal status | - Call admin APIs (`/api/v1/admin/*`)<br>- Claim tasks outside assigned business queue<br>- Direct DB access (worker holds zero DB credentials)<br>- Direct blob storage write without runtime grant | **`[VERIFIED]`**: Worker interacts exclusively via `TaskContext` HTTP facades. Lease fencing verified on checkpoints and artifact writes. |
