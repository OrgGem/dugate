# Trusted isolated restore runtime probe

The maintenance host runner uses `createTrustedIsolatedRestoreRuntimePorts({ manifestPath, expectedManifestSha256 })` with `createTrustedIsolatedRestoreProbe`. The runtime-port factory reads the existing digest-pinned maintenance manifest through `readTrustedIsolatedRestoreRuntimeManifest`; its launch, health, control, source-isolation, database, application, and recovery readers are concrete host-side implementations. A missing or invalid manifest, protected file, executable pin, transport, or key pin fails closed.

The host runner is the only component allowed to execute the pinned Docker, namespace, nftables, libpq, and restore-reader tools. The serving web process must not receive the Docker socket or host database credentials. Database names in the restore plan are passed through the configured libpq service entries; they are not interpreted as connection URLs.

Each target runtime is a new UID:GID 1000 process on the pinned image and runtime identity. The launcher starts it with no network, a root-owned CID file, and read-only mounts for its per-run configuration and protected secrets. Before opening the start gate, the host checks the actual container identity, applies the digest-pinned nftables rules in that container's network namespace, verifies the resulting native nft JSON, and attaches only the pinned target network. The policy requires a default-drop output chain and exact destination-IP/port denial rules for every pinned source endpoint. The probe then tests each endpoint from inside both target runtimes. Any successful connection or HTTP response means that source is reachable and fails the probe.

The probe requires fresh authenticated DRAINING control acknowledgements tied to each actual process boot, actual LIVE/dependency evidence, disabled external effects, and zero process-owned active work. It retains durable unresolved invocations, UNKNOWN usage deliveries, and historical effect-permit holds as evidence; it does not clear or reinterpret those records. It performs a final fresh health, control, work, and source-denial read after recovery work.

Recovery readers independently inspect the restored target databases and storage generation. They reconcile database and object-version counts; authenticate and decrypt artifact objects and their exact sidecars with the pinned artifact Transit versions; open secret-catalog revisions and current values with the pinned local recovery keys; authenticate Connector invocation envelopes with the local Connector KEKs; authenticate legacy Connector credentials with the pinned AES key; open each metadata Transit envelope using its producer slot and AAD; and read each pinned Vault KV2 version. The application reader performs an actual login and history request, selects a restored READY artifact owned by the configured API key, and downloads it through the target runtime's local application route. Evidence includes bounded counts and hashes, not plaintext secrets or credentials.

Commands, streams, rows, and downloads have fixed bounds and cancellation. On all launch or probe failures, cleanup is restricted to the full container ID captured by the per-run CID file and verified by Docker inspection; it stops, waits for stopped state, and removes only that owned container. Uncertain ownership or failed cleanup returns a cleanup error.

Focused owner tests cover strict nft rule validation, exact source endpoint binding, availability of the concrete ports, manifest-digest fail-closed behavior, metadata producer AAD for every stored slot (including wrong-AAD rejection), slow recovery beyond 60 seconds with fresh observations at read time, and stalled iterator/owned-process teardown. These checks do not establish a real deployment's Docker, database, Transit, Vault, object-store, or source-off behavior. The independent host verification must exercise the separately configured host executor and actual isolated targets before the probe can be treated as deployment evidence.
