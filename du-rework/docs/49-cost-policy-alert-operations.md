# Cost policy and alert operations

This guide describes the additive Admin Usage cost controls and owner inbox. It preserves the existing public billing and usage APIs. The browser uses the authenticated Admin BFF, which forwards tenant-scoped requests to the internal cost-control and cost-alert routes.

## Usage ledger

Usage summary and event pages continue to use the existing tenant and role scope. Event search is bounded by a server cursor and page size; CSV export includes the current queried page only. New invocation events show persisted attempt, API key, profile and revision, business/version/action, step, Connector revision, reservation group, bound capability, frozen price snapshot, budget pins, and trust state. Older events without cost provenance remain visible as BASIC history. Pending and unpriced costs are explicit; missing cost is never presented as free usage.

Each usage event can expand its financial adjustment detail. It shows the current server-projected initial, gross, refunded and net amounts, eligibility blockers, original immutable attribution and accounting-window pins, plus the paged append-only decision history. Only a current platform Admin can prepare a correction or refund. A correction replaces the gross charge; a refund is a positive credit delta. The review step pins the current adjustment revision, bounded reason and a selected existing READY evidence artifact. The browser never enters a raw artifact UUID or calculates resulting net; the service checks the artifact's same-tenant storage pins again when recording the decision. A recorded adjustment preserves original units, price/provenance and effective event time, with the administrative recorded time shown separately.

The ledger keeps the original computed charge immutable and displays it separately from the server-returned direct-root accounting envelope: current gross, refunded and net amounts, root event, adjustment revision and semantics. The Usage summary and ledger consume the server projection used by the monetary readers; the browser does not reprice events or derive net, and original units remain counted once. Missing envelope fields and BASIC/unpriced history remain unavailable rather than becoming zero. The Usage CSV contains the current queried event page only and exports the server-provided initial/gross/refunded/net values and root/revision/semantics. Adjustment history has its own export for the current bounded server page, including correction/refund kind and amount, original effective UTC versus recorded UTC, authority, opaque actor ID and evidence-proof status. CSV fields are escaped and formula-protected; neither export claims to contain all matching history. Incomplete historical object proof remains explicitly marked and does not become eligible through display or export. Existing tenant and role scope continues to apply: scoped readers can see only authorized financial history, while only a currently authorized Admin can write; alert-inbox enrollment or recipient status is not a finance-write prerequisite.

Provider-reported cost is displayed separately as an unverified diagnostic, with a difference only when both it and a computed cost are present. It never controls adjustment eligibility, budget admission or the server-projected adjustment totals. BASIC, unpriced, unsettled or otherwise ineligible roots remain read only; no zero amount or missing evidence is fabricated to enable an adjustment.

## Budget and price revisions

Budget and price changes start as immutable drafts. Review, publish, retirement, and rollback use the existing revision-head compare-and-swap and idempotency contracts. The Usage form exposes integer token and micro-USD thresholds, UTC daily/monthly windows, enforcement policy, status, and guided tenant API key/profile/business selectors. It shows the proposed diff before saving. Existing used and held quota remains part of the policy calculation; editing a revision does not reset it.

Guided scope catalogs load one bounded page at a time, support server-side text search and keyset continuation, and filter profiles by the selected API key and businesses by the selected profile. Tenants with more than 1,000 keys or profiles can keep searching and paging without loading the full catalog into the browser.

Budget notification channel IDs stay opaque in `BudgetConfig`. The separate alert binding identifies the local tenant Admin or an eligible external platform OIDC Admin and the channel revisions for one exact published budget revision. Local owners continue to resolve through the current local Identity row. External owners use a server-generated opaque recipient ID bound to the exact verified issuer and subject; issuer, subject, email, and browser-supplied identity fields are never accepted as an owner credential. An external platform Admin selects the budget tenant explicitly and receives only its own inbox entries for that tenant.

External recipient registration is available only to the signed-in platform OIDC Admin. Registration pins that opaque recipient and its authorization version to the current server session. A bounded recipient catalog supports search and cursor paging; it returns a safe display label and opaque ID, not IdP identity claims. Directory disable, re-enable, and terminal revoke use an audited version compare-and-swap. These actions fence the cost-alert recipient and inbox only; they do not disable ordinary OIDC Admin login or application access. Role/scope changes observed on a later verified login advance the recipient authorization version and invalidate earlier alert pins. A verified login never silently re-enables a disabled or revoked recipient.

Bindings require a budget revision with a persisted publication timestamp. Draft and review revisions cannot be routed; previously published revisions remain addressable for settlement events that still use their frozen policy pin.

The current channel catalog provides the first-party `Tenant Admin inbox` (`tenant-admin-inbox-v1`, revision 1). This route does not accept browser-supplied destinations, commands, or credentials. The channel is backed by a durable owner-scoped inbox that only the current enabled and version-matched recipient can read or acknowledge. Historical alerts retain the recipient and channel revisions selected when they were enqueued. If an external recipient is disabled, revoked, or has a stale authorization version before delivery, the delivery is durably held with an explicit reason; it is not redirected to another recipient and is not reported as delivered.

## Trust and admission

`block-new-invocations` requires a verified upper bound for the request and price, plus bounded committed usage and unresolved reservations. If any part is unsupported, preflight fails closed with `BUDGET_BOUND_UNSUPPORTED` before provider send. The Admin view describes the configured block policy and its concrete trust limitation without claiming remaining hard-cap capacity. An operator who explicitly configures `alert-only` may admit a best-effort request; the stored evaluation records the reason and can produce a trust-gap alert.

## Alert lifecycle

Usage enqueues threshold, limit, and trust-gap facts from the authenticated reservation preflight and final usage settlement transactions. A configured `block-new-invocations` policy still fails closed before provider send when upper-bound trust is unavailable; an alert is not used to weaken a requested hard cap. The enqueue port accepts the caller's existing PostgreSQL transaction, re-derives the quota scope from the pinned immutable budget revision, and compares its canonical key with the producer's key. Source-event and window uniqueness make retries idempotent. The transaction stores frozen evaluation, trust, operation, task, invocation, usage-event, budget-revision, owner, binding-revision, channel-revision, and window references; it does not send a notification.

The delivery worker claims due rows with `SKIP LOCKED` and a fenced 60-second lease. It rechecks the frozen recipient inside the delivery transaction, writes the inbox row, and marks delivery complete atomically. Failed attempts retry at 5 seconds with exponential backoff capped at 5 minutes, for at most 8 attempts. An expired lease records an UNKNOWN attempt and is safely retried. A no-longer-current recipient is held without inbox insertion or rerouting. Alert history includes bounded delivery and attempt status. The owner inbox is separately cursor-paged and supports an idempotent read acknowledgement.

The worker batches at most 25 deliveries per scheduled pass, with the server runner polling every 5 seconds. Apply migrations `0059_cost_alert_delivery.sql` and `0061_cost_alert_oidc_recipients.sql` through the normal orchestrator migration path before enabling external recipient registration and delivery.

Computed usage cost comes from validated measured units and the frozen price snapshot. A provider-reported amount, when present, is labeled unverified and shown only as a diagnostic; it does not replace computed cost or affect budgets, admission, settlement, or alert evaluation. Legacy events without trustworthy cost provenance remain nullable/BASIC history rather than being shown as zero-cost usage.
