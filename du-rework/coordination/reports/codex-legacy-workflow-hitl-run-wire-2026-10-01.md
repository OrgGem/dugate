# Legacy workflow run wire and HITL pause/resume characterization

Date: 2026-10-01  
Scope: Read-only characterization of legacy workflow submission, progress/result polling, Human-in-the-Loop pause/resume, and child-operation visibility, compared with the current Orchestrator wire. No source or test files were changed; no tests were run; no COMP row or gate was changed.

Paths below use repository-root `app/**` and `lib/**` for legacy, and `du-rework/**` for Orchestrator.

## 1. Workflow run path and accepted request fields

`POST /api/v1/docs/workflows` reads a `multipart/form-data` body. The required discriminator is the trimmed string form field `process`; it is looked up as `SERVICE_REGISTRY.workflows.subCases[process]` (`app/api/v1/docs/workflows/route.ts:16-29`; registry declaration `lib/endpoints/registry.ts:373-400`). The registered values are `disbursement`, `lc-checker`, and `doc-compare`. At least one non-empty file is required. `normalizeFiles` accepts repeated `files[]`, plus `source_file`, `target_file`, and `file` file fields (`route.ts:31-35`; `lib/endpoints/runner.ts:36-53`).

For the **disbursement** example, the recognized form fields are:

- `process=disbursement` (required).
- One or more files using `files[]`, `source_file`, `target_file`, or `file` (required; non-`File` and zero-byte values are discarded by `normalizeFiles`).
- `resolution_data` (optional string workflow variable; it is the only parameter on the disbursement registry entry, `lib/endpoints/registry.ts:380-386`, copied from the form at `route.ts:38-43`).
- `apiKeyId` (optional profile/API-key selector read by the route at `route.ts:50-77`; it is not included among the workflow variables).

`lc-checker` and `doc-compare` have no registry-declared extra form parameters (`registry.ts:390-400`); the route still requires at least one file. The workflow registry entries have `connections: []`, so `process` is not expanded by the endpoint registry into a declarative connector list. The route creates a single placeholder pipeline entry `{ processor: 'ext-classifier', variables }` and `endpointSlug = workflows:${process}` (`route.ts:38-47`). `submitPipelineJob` marks this as a workflow job (`lib/pipelines/submit.ts:337-343`); the worker resolves the job name through `WORKFLOW_REGISTRY` (`lib/pipelines/workflow-engine.ts:415-423,429-470`).

For disbursement, the registered handler's actual four logical steps are: per-file `ext-classifier` classification, per-file `ext-data-extractor` extraction, `ext-fact-verifier` cross-check, and `ext-content-gen` report generation (`lib/pipelines/workflows/disbursement.ts:90-101,158-168,211-224,237-254`). The first two fan out per file and are awaited with `Promise.all`; the latter two run as single sub-operations. The step sequence lives in the handler implementation, not in `SERVICE_REGISTRY.connections`.

Schema-driven workflows use the separate `POST /api/v1/docs/workflows/schema` route. Its required field is `schemaSlug`; optional `input` is a JSON string parsed into a value that the route types and spreads as a record (it checks JSON parsing but does not separately enforce object shape); files are optional; and `apiKeyId` is also read (`app/api/v1/docs/workflows/schema/route.ts:4,17-23,39-48,59-79`). The route loads and validates the saved schema, then places `{ schemaSlug, ...input }` into the placeholder pipeline variables and sets `endpointSlug = workflows:schema:${schemaSlug}` (`:25-33,50-56`). The worker recognizes `pipelineVars.schemaSlug` and loads that schema (`lib/pipelines/workflow-engine.ts:439-448`). `runWorkflowFromSchema` orders nodes by `schema.flow`, executes contiguous non-human blocks through `runSchemaDag`, and pauses on a `human` node (`lib/workflow-builder/run-schema.ts:31-55,57-82`). This is a schema-provided node flow rather than the three named code handlers.

## 2. Submission response and operation polling

On successful submission, the dedicated legacy workflow route returns **202**; it does not implement a 200 sync branch. Its fixed response body is `name: operations/{id}`, `done: false`, and `metadata: { state: 'RUNNING', workflow: processName, progress_percent: 0, progress_message: 'Initializing workflow...' }`, with `Operation-Location: /api/v1/operations/{id}` (`app/api/v1/docs/workflows/route.ts:99-116`). The schema workflow route likewise returns 202 with `workflow: schemaSlug` and `Initializing schema workflow...` (`app/api/v1/docs/workflows/schema/route.ts:95-109`).

That immediate response is not the later `formatOperationResponse` body. A subsequent `GET /api/v1/operations/{id}` reads the row from the database and formats it (`app/api/v1/operations/[id]/route.ts:14-37`). The formatter's base body has `name`, `done`, and metadata fields `state`, `pipeline`, `current_step`, `progress_percent`, `progress_message`, timestamps, and `pipeline_steps` (`lib/pipelines/format.ts:17-31`). The parent workflow's pipeline is the placeholder; `pipeline_steps` is parsed from the persisted `stepsResultJson`.

During execution, `updateProgress` writes the supplied percent/message and serializes the workflow's current `stepsResult` (`lib/pipelines/workflow-engine.ts:206-214`). A mid-run poll therefore sees the last persisted progress write and step results, not a live in-memory mutation. Until a step has appended and persisted its result, the parent `pipeline_steps` can still be empty or contain only earlier completed steps. On the disbursement HITL pause, the immediately preceding step-2 progress write is the end of the `[30,55]` band; the later waiting poll retains that percent and exposes the saved first two step records.

## 3. Legacy pause and resume wire

`pauseWorkflow(ctx, message, currentStep)` updates the parent operation to exact state `WAITING_USER_INPUT` and `done=false`; it writes `progressMessage=message`, `currentStep`, and `stepsResultJson`. The same update stores the workflow context's accumulated input/output usage and cost columns (`totalInputTokens`, `totalOutputTokens`, `totalCostUsd`); no values are repeated here. For schema-driven workflows it wraps the saved step array with `_nodeResults` when present (`lib/pipelines/workflow-engine.ts:247-268`). The update does **not** set `progressPercent` to 100 and does not assign a new percentage; the last stored percentage remains. The source explicitly records that waiting is not completion (`:267-268`).

The poll response still uses the formatter's normal body: `done:false`; metadata state `WAITING_USER_INPUT`; `current_step`; the retained `progress_percent`; the pause message as `progress_message`; and the saved parent `pipeline_steps` (`lib/pipelines/format.ts:17-31`). There is no separate wait-id or input-schema object in this legacy response.

Legacy `POST /api/v1/operations/{id}/resume` parses JSON, loads the operation, and proceeds only when its state is `WAITING_USER_INPUT` (`app/api/v1/operations/[id]/resume/route.ts:17-32`). There is no `expectedStateVersion` field read, no state-version comparison, and no compare-and-swap condition in this route. A human edit is optional: if `body.step` is set and `extracted_data` exists, the route finds that step record and replaces `extracted_data`, marking `is_human_edited=true` (`:48-59`). It re-serializes `stepsResultJson`, preserving the schema `_nodeResults` wrapper when present (`:75-81`).

On successful resume, the route writes `state='RUNNING'`, `progressMessage='Đang tiếp tục luồng xử lý do người dùng xác nhận...'`, and the updated `stepsResultJson`; it does not update `progressPercent`, `currentStep`, or `done` in that update (`:83-88`). It then enqueues `pipeline:{endpointSlug}` and returns HTTP 200 with `{ success: true, message: 'Resumed successfully' }` (`:90-98`). The workflow context reloads `currentStep`, `stepsResult`, and schema `_nodeResults`; the handlers use that checkpoint to skip completed steps and continue from the saved index (`lib/pipelines/workflow-engine.ts:376-400`; `lib/pipelines/workflows/disbursement.ts:61-82,94,158,211,238`; `lib/workflow-builder/run-schema.ts:36-55`).

## 4. Multi-file work and child-operation visibility

Each `enqueueSubStep` creates a separate operation row and BullMQ pipeline job, waits for completion, then returns the child operation/result to the parent handler (`lib/pipelines/workflow-engine.ts:112-203`). The child row is inserted with `deletedAt: new Date()` (`:128-138`). The history list filters to `deletedAt IS NULL` (`app/api/v1/operations/route.ts:37`), and direct operation GET returns 404 when `op.deletedAt` is set (`app/api/v1/operations/[id]/route.ts:20-25`). Thus clients do not retrieve the child operation row directly through the legacy operation list/detail routes, even if they know its id.

The parent view is the client-visible summary: workflow handlers append `WorkflowStepResult` records, which can include `sub_operation_id` and per-file `sub_results` (`lib/pipelines/workflow-engine.ts:22-32`; examples in `lib/pipelines/workflows/disbursement.ts:131-151,192-208`). `formatOperationResponse` exposes the saved array as `metadata.pipeline_steps`, and also includes it in terminal result bodies (`lib/pipelines/format.ts:20-31,37-40,59-64`). Child ids can therefore appear as references inside the parent step data; that does not expose the child's separate operation row.

## 5. Rework counterpart and observed delta

The active rework public submission surface is `POST /api/v1/businesses/{id}/actions/{action}` (`du-rework/services/orchestrator/src/server.ts:1730-1743`); the inspected `server.ts` does not contain the legacy `/api/v1/docs/workflows` `process` route or the named legacy workflow registry. Its operation states include `WAITING_CHILDREN` and `WAITING_INPUT` (`packages/contracts/src/operations.ts:11-24,39-48`).

- **Child-task wait:** runtime fan-out records task dependencies and moves the parent task and operation to `WAITING_CHILDREN`; the operation state version increments (`services/orchestrator/src/modules/runtime/runtime.ts:684-721,858-867`). When the join advances, the parent returns to queueing through the runtime continuation path (`:1399-1512`). Child status is available through the runtime-authenticated `GET /api/runtime/v1/tasks/{id}/children`, which calls `getChildren` (`server.ts:1676-1683`; `runtime.ts:873-903`). This is task-graph join state, not a legacy-style child `operations` row.
- **Human wait:** the worker runtime opens a typed wait with `waitKey`, `inputSchema`, optional `uiSchema`, `contextRef`, and optional `expiresAt` (`packages/contracts/src/runtime.ts:147-160`). It inserts a `human_waits` row and moves the task and operation to `WAITING_INPUT` (`runtime.ts:906-990`). Migration `0005_continuation.sql:9-28` defines `operation_id`, `task_id`, `wait_key`, unique `wait_id`, input/UI schemas, context reference, status, response reference, expiry, and indexes enforcing one open wait per task.
- **Rework resume:** `POST /api/v1/operations/{id}/resume` resolves the caller tenant and calls `runtime.resumeOperation` (`server.ts:2097-2105`). Its required JSON fields are `waitId`, `input`, and numeric `expectedStateVersion` (`runtime.ts:1000-1012`). The method locks and checks the operation version and tenant, locks the matching wait, and validates the input against the saved schema. For a fresh answer it requires an open wait and a `WAITING_INPUT` task; an already `ANSWERED` wait follows the replay return path (`:1017-1064,1090-1097`). On success it marks the wait `ANSWERED` with `response_ref`, queues the task with the resume payload, inserts an outbox dispatch, and updates the operation to `QUEUED` with an incremented state version (`:1073-1081,1099-1135`). The endpoint returns 202 for a new resume and 200 for a replay (`server.ts:2101-2104`).
- **Waiting operation view:** public GET maps the operation row through `toOperationView` (`server.ts:1806-1841`). A waiting row is returned with its actual `state` (`WAITING_INPUT` or `WAITING_CHILDREN`) and `stateVersion`, but `progress` is `{ percent: 0, message: state }` (`modules/operations/facade.ts:32-49`). The active mapper does not attach a wait object; while the contract has an optional `wait` field on `OperationDetail`, the live GET uses `toOperationView` (`packages/contracts/src/operations.ts:232-251`; `server.ts:1832-1841`).

Observed behavior absent from the other implementation is limited here to the compared workflow wire: legacy has the `process` multipart endpoint, the named code-driven workflow handlers, progress-bearing `pipeline_steps`, and its `WAITING_USER_INPUT`/step-edit resume request; no matching process route, legacy child-operation projection, or same resume wire was found in the active rework server. Rework has explicit operation/task `WAITING_CHILDREN`, persisted `human_waits` records, version-checked wait answers, and outbox continuation; those records and state transitions are not part of the inspected legacy workflow path. This is a behavior comparison only; it does not select a side or propose a change.
