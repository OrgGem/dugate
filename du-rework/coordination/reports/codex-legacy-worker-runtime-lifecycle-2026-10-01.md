# Legacy Worker Runtime: Retry, Pause, Shutdown, and Lease Recovery

Read-only characterization of the legacy worker process and the Orchestrator runtime paths. This compares implementation behavior; it does not recommend a change.

## 1. Legacy worker wiring and events

- worker.ts constructs two BullMQ workers over the shared processJob function: the pipeline worker uses WORKER_CONCURRENCY, default 5; the workflow-steps worker uses SUBSTEP_WORKER_CONCURRENCY, default twice the pipeline concurrency (10 when both variables are absent) (worker.ts:32-34, 62-84). Both use a 30,000 ms stalled check interval and maxStalledCount 2 (worker.ts:65-70, 78-83).
- The failed listener logs job/attempt/error information. When attemptsMade is at least job.opts.attempts (fallback 3), it emits a second structured console.error tagged “DLQ” with job ID/name, operation ID, error, and stack (worker.ts:93-107). This is a log, not a transfer to a dead-letter queue; the queue module defines only pipeline and workflow-steps queues and sets removeOnFail:false, retaining failed jobs for inspection (lib/queue/pipeline-queue.ts:15-16, 27-35, 57-65). BullMQ emits the failed event after moveToFailed (node_modules/bullmq/dist/cjs/classes/worker.js:709-710).
- The “DLQ” log predicate reads attemptsMade, not stalledCounter; a stall-limit failure is a distinct path and does not itself transfer a job to another queue (worker.ts:94-100; node_modules/bullmq/dist/cjs/classes/job.js:91-96; node_modules/bullmq/dist/cjs/commands/moveStalledJobsToWait-9.lua:75-107). CLAUDE.md calls this “max 2 retries before DLQ” (CLAUDE.md:177), but the configured 2 is maxStalledCount, queue attempts are 3, and the code’s DLQ label is only a console log (worker.ts:68-69, 81-82; lib/queue/pipeline-queue.ts:29-34; worker.ts:98-107).
- The stalled listener only prints a warning that the job will be re-queued; it contains no database write (worker.ts:110-112). BullMQ’s stalled script increments its separate stc field and requeues; when the counter is greater than maxStalledCount it records a deferred failure, then the next worker activation fails the job (node_modules/bullmq/dist/cjs/commands/moveStalledJobsToWait-9.lua:69-107; node_modules/bullmq/dist/cjs/classes/worker.js:663-664, 709-710).

## 2. Three distinct retry/recovery mechanisms

| Mechanism | Actual behavior |
|---|---|
| BullMQ stalled detection | maxStalledCount:2 is configured per Worker, separate from queue attempts (worker.ts:62-83). The installed BullMQ version stores stalledCounter separately from attemptsMade (node_modules/bullmq/dist/cjs/classes/job.js:91-96); its stalled script increments the stalled counter, not attemptsMade, and does not reset attemptsMade when it requeues (node_modules/bullmq/dist/cjs/commands/moveStalledJobsToWait-9.lua:75-107). With the configured limit, exceeding two stalls sets deferredFailure; BullMQ still moves the job to wait, then fails it when picked up again (same Lua file:96-107; worker.js:663-664, 709-710). |
| Queue-level processor attempts | Both queue factories set attempts:3 and exponential backoff with a 5,000 ms base delay; removeOnFail:false retains terminally failed jobs (lib/queue/pipeline-queue.ts:27-35, 57-65). BullMQ increments attemptsMade on processor failure and uses attemptsMade + 1 against opts.attempts to decide whether to retry (node_modules/bullmq/dist/cjs/classes/job.js:514-524, 574-581). A stalled requeue is not a queue-attempt reset or an ordinary processor retry. |
| recover-stalled database safety route | POST selects operations with state RUNNING, done:false, and createdAt older than its threshold, then sets done:true, state:FAILED, errorCode:STALLED, errorMessage, and clears progressMessage (app/api/internal/recover-stalled/route.ts:21-22, 33-58). This is a separate database row flip, not BullMQ requeue logic. |

The Worker failed listener itself does not update an Operation row; it only logs (worker.ts:93-108). Separately, runPipeline catches ordinary step execution errors, writes done:true/state:FAILED, and returns through its catch/finally rather than rethrowing to BullMQ (lib/pipelines/engine.ts:450-486). Code-driven workflow exceptions likewise go through failWorkflow, which writes FAILED, and are caught by runWorkflow (lib/pipelines/workflow-engine.ts:274-292, 467-472). Thus these caught failures generally do not consume queue retries. If an error escapes those handlers or the worker disappears before they write, BullMQ can retry/fail the job without the failed listener changing the database row; an otherwise-RUNNING row can remain so until another writer, including recover-stalled, acts (worker.ts:93-112; app/api/internal/recover-stalled/route.ts:33-58).

**MUST-NOT-REPLICATE:** recover-stalled terminalizes any selected old RUNNING/done:false row as FAILED based on createdAt; its selection and update do not check whether the BullMQ job is still active or the pipeline is still executing (app/api/internal/recover-stalled/route.ts:33-58). Therefore a still-processing operation can be marked terminal by this route. This is the observed behavior; no remedy is proposed here.

## 3. Pipeline checkpoint on retry

- runPipeline reads currentStep as resumeFromStep. When it is above zero and stepsResultJson parses, it restores completed step results before that index, restores chained text and the last completed step’s pipeline_state_snapshot, and starts the loop at resumeFromStep (lib/pipelines/engine.ts:227-248, 281-283). A retry therefore skips indices below the persisted currentStep and runs that step and later steps again.
- Each successful step’s result and snapshot are persisted to stepsResultJson (lib/pipelines/engine.ts:365-374, 391-394). Since currentStep is written before invoking the step, a failure/crash during that step leaves the retry starting at that same index; prior successfully persisted steps are skipped (lib/pipelines/engine.ts:285-297, 365-394).
- At each attempt’s step start, progressPercent is recalculated as round(i / pipeline.length * 100) and written with currentStep (lib/pipelines/engine.ts:281-297). A retry does not blanket-reset progress to zero: it writes the start percentage of the resumed step again; only a run beginning at step index zero writes zero.

## 4. Heap monitoring and pause semantics

- WORKER_MEMORY_THRESHOLD defaults to 0.90; the monitor compares process heapUsed with V8 heap_size_limit every 10 seconds (worker.ts:124-142). Above the threshold it calls pause() on both Worker instances; at or below threshold × 0.85 it resumes both, which is 0.765 (76.5%) with the default threshold (worker.ts:131-140).
- This pauses the pipeline and workflow-steps workers, not the Queue objects (worker.ts:133-139). BullMQ’s default pause marks the worker paused and waits for current jobs to finish; it does not abort in-flight processors (node_modules/bullmq/dist/cjs/classes/worker.js:725-745). New work is paused for that Worker; in-flight work continues to completion.
- CLAUDE.md says “resumes at 75%” (CLAUDE.md:176); the code’s default-derived threshold is 76.5%, not 75% (worker.ts:124, 136-140).

## 5. Shutdown

- SIGTERM and SIGINT both call shutdown; it closes pipelineWorker and stepsWorker concurrently, then calls process.exit(0) (worker.ts:146-154). The call supplies no timeout and no force argument.
- BullMQ Worker.close defaults force to false and waits for current jobs to finalize before closing worker Redis connections (node_modules/bullmq/dist/cjs/classes/worker.js:798-845). Therefore in-flight jobs are drained; a job that never settles can keep shutdown waiting, as no timeout is configured in shutdown (worker.ts:146-150).
- The shutdown function explicitly closes only the two Worker instances; it does not call close() on the Queue or QueueEvents singletons created by the queue module (worker.ts:146-150; lib/queue/pipeline-queue.ts:25-49, 55-78). The process exits after the Worker closes complete.

## 6. Workflow HITL wait and re-entry

- pauseWorkflow persists done:false, state:WAITING_USER_INPUT, the message, currentStep, and stepsResultJson, then sends a PAUSED webhook (lib/pipelines/workflow-engine.ts:246-272). Webhook done is true only for SUCCEEDED or FAILED, so PAUSED reports done:false (same file:295-303).
- pauseWorkflow does not enqueue its parent again; a workflow handler returns after invoking it, and runWorkflow awaits that handler (lib/pipelines/workflows/disbursement.ts:204-208; lib/pipelines/workflow-engine.ts:467-472). The observed parent re-entry path is POST /api/v1/operations/{id}/resume: it accepts only WAITING_USER_INPUT, changes the row back to RUNNING, then adds a pipeline job (app/api/v1/operations/[id]/resume/route.ts:31-33, 83-98). No automatic requeue from the PAUSED webhook/state write is present in these paths (workflow-engine.ts:246-272).

## 7. Rework lease-recovery counterpart

- Public operation requests resolve the presented active API key to its database tenant; the public resume route passes that resolved tenantId into runtime.resumeOperation (du-rework/services/orchestrator/src/server.ts:2097-2103, 4182-4194). Runtime worker claim/heartbeat routes authenticate the worker business, and heartbeatTask checks business identity, lease epoch, active lease, and RUNNING state (server.ts:1589-1622; modules/runtime/runtime.ts:157-170, 353-400).
- sweepExpiredLeases scans expired RUNNING task leases under non-terminal operations. With retry budget remaining it increments lease_epoch, clears the lease, returns the task to READY, and writes a deduplicated task.dispatch outbox event (modules/runtime/runtime.ts:1140-1175, 1192-1223). Epoch fencing rejects a late worker’s stale heartbeat/write with LEASE_LOST (runtime.ts:163-165, 353-374). On exhaustion it marks the task FAILED with error_code LEASE_EXPIRED and, unless child-join reconciliation handles it, marks the operation FAILED with the same error code (runtime.ts:1224-1243); it does not write CANCELLED as a lease-recovery result (runtime.ts:1155-1171, 1224-1243).
- Production’s recovery timer defaults to 5,000 ms when autoDispatch is enabled (or uses leaseRecoveryIntervalMs); each tick invokes both sweepExpiredLeases and the queue-integrity sweep (server.ts:686-690, 890-903).
- The queue-integrity sweep addresses a different gap: Postgres candidates are READY/QUEUED, leaseless, dispatched rows under non-terminal operations; a live BullMQ job is left alone, a Redis lookup error is unconfirmed, and only a confirmed missing job is CAS-rearmed (runtime.ts:77-100, 1251-1266, 1295-1318). Rework reports counters including rearmed, aliveSkipped, stalled, and unconfirmed (runtime.ts:50-58, 1285-1293). Health states are OK, RECONSTRUCTING, and SUSPECT; the server derives these from rearmed/stalled counts and records queue.integrity_stalled when stalled candidates exist (runtime.ts:60-67; server.ts:651-684). These are queue-health states, not Operation states.
- No Orchestrator/worker-SDK counterpart was found for legacy WORKER_MEMORY_THRESHOLD pause/resume or maxStalledCount settings; the Orchestrator timer shown here runs database lease and queue-integrity sweeps instead (du-rework/services/orchestrator/src/server.ts:688-690, 890-903; compared legacy worker config: worker.ts:62-83, 124-142). Conversely, lease_epoch fencing, LEASE_EXPIRED task recovery, and the queue-integrity health states have no counterpart in the legacy worker’s stalled listener or pipeline queue configuration (worker.ts:88-117; lib/queue/pipeline-queue.ts:25-35; rework runtime.ts:1140-1249; server.ts:651-684).
