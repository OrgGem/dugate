## Findings for the freeze

The legacy API does not have one error serializer. It has (1) title-derived `https://dugate.vn/errors/*` objects from `apiError()`, (2) manually written objects that resemble Problem Details, and (3) ordinary `{ error: string }` JSON bodies. `lib/errors.ts` defines a Problem Details-shaped helper, but a repository search found no caller; the `/api/v1` routes use the other forms.

The canonical rework has a distinct wire contract: the Orchestrator explicitly sets `application/problem+json`, emits `urn:du:error:<lowercase-code>`, and includes `code` plus a correlation ID when available. The legacy code uses HTTPS slug URIs and has no shared `code` or correlation-ID field. Thus even where HTTP status meanings agree, the `type`, machine code, media type, and often body shape are a **MISMATCH** for COMP-02 to resolve.

## Legacy serializer behavior

| Source | Emitted fields and behavior |
|---|---|
| `lib/errors.ts:5-36` | `ProblemDetail` declares `type`, `title`, `status`, optional `detail`, optional `instance`. `createProblemDetail(status, slug, title, detail?)` builds `https://dugate.vn/errors/${slug}` and omits falsey `detail`; it does not set an HTTP header. It is not called by the current API routes. |
| `lib/endpoints/runner.ts:18-28` | `apiError(status, title, detail, type?)` returns `NextResponse.json({ type, title, status, detail }, { status })`. Default `type` is `https://dugate.vn/errors/${title.toLowerCase().replace(/\s+/g, '-')}`; this is derived from display text, not a stable code. A caller can override `type`. It always includes `detail`; it does not add `code`, `instance`, or correlation ID, and does not explicitly set `application/problem+json`. |
| Route literals | Route handlers call `NextResponse.json` directly, with varying field sets and without a shared media-type/error-code helper. Some use `type/title/status/detail`, some add `requested_id`, and some return only `{ error }`. |

The six `/api/v1/docs/{ingest,extract,analyze,transform,generate,compare}` handlers all delegate to `runEndpoint`, so they share its `apiError()` and `submitPipelineJob()` failures. The two workflow POST routes use `apiError()` directly and also return its output from their catches. See `app/api/v1/docs/*/route.ts`, `lib/endpoints/runner.ts:76-283`, and `app/api/v1/docs/workflows/{route.ts,schema/route.ts}`.

## Route-level exceptions to the namespace

- `app/api/v1/operations/route.ts:48` returns `{ error }` for invalid state filters; it does not use `apiError()` or a namespaced `type`.
- `app/api/v1/operations/[id]/resume/route.ts:28-32,101` returns `{ error }` for 404/400/500, including raw `err.message` on 500.
- `app/api/v1/billing/balance/route.ts:20,32` and `billing/usage/route.ts:27,38` use `{ error }` for 401/404/400.
- The `/api/v1/` branch in root `middleware.ts:31-52` strips incoming `x-api-key-id`, `x-user-id`, and `x-user-role`, then passes the request through; it does not provide a common 401 Problem Details response.
- `lib/pipelines/submit.ts:164-173,211-222` contains 402 and dynamic 500/503 `storage-error` responses. `:363-364` emits `queue-full` at 503 with `Retry-After: 30`.

## Canonical wire references

- `du-rework/packages/contracts/src/errors.ts:9-44,82-116`: status/code catalogs, Problem schema, and `problem()` URI format (`urn:du:error:<lowercase-code>`); schema fields include `type,title,status,code` and optional `detail,correlationId,errors`.
- `du-rework/services/orchestrator/src/http/errors.ts:8-27,49-62`: `HttpError.toProblem()` and status helpers (`INVALID_ARGUMENT`, `UNAUTHENTICATED`, `PERMISSION_DENIED`, `NOT_FOUND`, `CAPACITY`, `TEMPORARY_UNAVAILABLE`).
- `du-rework/services/orchestrator/src/http/errors.ts:98-107`: unexpected error body is fixed/sanitized and includes `correlationId`.
- `du-rework/services/orchestrator/src/server.ts:746-760,818-831`: both ingress and request catches explicitly set `content-type: application/problem+json`, serialize `HttpError`, and use the safe 500 problem for unexpected throws.

## COMP-02 freeze decisions this inventory exposes

1. Choose a single legacy compatibility policy for status and body shape. Preserve exact legacy URI slugs where old clients may inspect `type`, or publish a deliberate alias map to canonical codes; do not derive freeze identifiers from human titles.
2. Decide whether legacy responses must retain `application/json` behavior or can use `application/problem+json`; source currently does not explicitly set the latter.
3. Freeze the 400/422 split, including schema validation, forbidden profile fields, connector disabled, and file URL download failures.
4. Decide whether spending-limit rejection is 402 (`CLIENT_QUOTA`-like), and whether queue saturation remains 503 + `Retry-After` or becomes 429.
5. Freeze authorization code names (`UNAUTHENTICATED` vs `INVALID_AUTH`/`INVALID_API_KEY`; `PERMISSION_DENIED` vs `FORBIDDEN`) and 404 resource-specific alias behavior.
6. Use the canonical sanitized 5xx policy for rework. Do not carry forward legacy raw exception text in `detail` or `{ error }` responses.
