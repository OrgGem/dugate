# Legacy connector, profile, override, and schema-builder admin journeys

Read-only source characterization for ORCH-PAR-00. This report describes the checked-in source paths, not deployment reachability or a decision to retain either implementation. No tests were run and no source, test, COMP, ORCH-PAR, or gate rows were changed.

## 1. Connector registration and use

The legacy resource is `ExternalApiConnection`; the UI labels its `endpointUrl` field “URL.” The table’s complete persisted field set is `id`, `name`, `slug`, `description`, `endpointUrl`, `httpMethod`, `authType`, `authKeyHeader`, `authSecret`, `promptFieldName`, `fileFieldName`, `fileUrlFieldName`, `defaultPrompt`, `staticFormFields`, `extraHeaders`, `responseContentPath`, `sessionIdResponsePath`, `sessionIdFieldName`, `timeoutSec`, `state`, `createdAt`, and `updatedAt` (`lib/db/schema.ts:72-98`). There is no separate persisted field literally named `url` or `prompt`: URL maps to `endpointUrl`, while the persisted default prompt is `defaultPrompt`; scoped prompt override is a separate `ExternalApiOverride.promptOverride` (`lib/db/schema.ts:77-98,100-117`; UI URL field at `app/api-connections/page.tsx:592-603`). The admin POST accepts the corresponding registration fields except `id`/timestamps and does not destructure `fileUrlFieldName`; its defaults and required-field checks are at `app/api/internal/ext-connections/route.ts:43-80`, and the inserted fields are at `:93-112`.

## 2. Profile and per-tenant/API-key overrides

The actual `ProfileEndpoint` columns are `apiKeyId`, `endpointSlug`, `enabled`, `parameters`, `connectionsOverride`, `jobPriority`, `fileUrlAuthConfig`, and `allowedFileExtensions` (plus row identity/timestamps). The source names are `parameters` and plural `connectionsOverride`; no `lockedParams` or singular `connectionOverride` columns were found (`lib/db/schema.ts:120-137`). `parameters` stores JSON values with per-value `isLocked`; `defaultLocked` comes from endpoint parameter schema (`lib/endpoints/registry.ts:7-15`; `lib/endpoints/profile-resolver.ts:53-93`).

| Behavior | Observed rule | Evidence |
|---|---|---|
| Profile record scope | Lookup is by `(apiKeyId, endpointSlug)`; exact endpoint slug wins, then it falls back to a service-level slug for that same API key. | `lib/endpoints/profile-resolver.ts:19-45`; unique key `lib/db/schema.ts:134-136` |
| Profile fields and write authority | GET projects enabled/parameters/connectionsOverride/jobPriority/fileUrlAuthConfig/allowedFileExtensions. POST requires the supplied `apiKeyId` and `endpointSlug`; an ordinary assigned user may alter only an existing enabled endpoint’s parameters/routing, while ADMIN writes the full field set (including `enabled`, job priority, file URL auth, extensions). | `app/api/internal/profile-endpoints/route.ts:19-35,88-102,110-167`; authorization check `lib/auth-guard.ts:39-70` |
| Connection-chain precedence | A nonempty profile `connectionsOverride` replaces the registry’s ordered `connections`; otherwise registry connections are used. The resolver supports old string arrays and new step objects; invalid JSON invokes the caller fallback. | `lib/endpoints/profile-resolver.ts:117-141`; consumer `lib/endpoints/runner.ts:209-223`; registry field `lib/endpoints/registry.ts:17-25` |
| Parameter precedence and locks | Start with stored profile values, then accept request form values only for keys in the endpoint schema or stored profile. Effective lock is stored `isLocked ?? defaultLocked ?? false`; a submitted locked key returns HTTP 400 `Forbidden Field` with `type=https://dugate.vn/errors/forbidden-field` and a locked-by-admin detail. | `lib/endpoints/profile-resolver.ts:48-93`; call site `lib/endpoints/runner.ts:187-198`; schema lock source `lib/endpoints/registry.ts:7-15` |
| Prompt precedence | For a connector call, code/workflow `_prompt` wins; otherwise the scoped `ExternalApiOverride.promptOverride`; otherwise `ExternalApiConnection.defaultPrompt`. This is the implemented order (strongest to weakest), despite the UI/profile editor’s broad use of “profile” terminology. | `lib/pipelines/processors/prompt-resolver.ts:21-38`; caller `lib/pipelines/processors/external-api.ts:21-33` |
| Per-connection prompt override scope | `ExternalApiOverride` holds `connectionId`, `apiKeyId`, `endpointSlug`, `stepId`, and `promptOverride`; null step is normalized to `_default`; the unique tuple is all four identifiers. POST verifies profile access and upserts/deletes on that tuple. | `lib/db/schema.ts:100-117`; `app/api/internal/ext-overrides/route.ts:58-82,84-125,133-150` |
| Runtime override resolution | Engine loads overrides by the operation’s API key and endpoint, then selects by connection id + step id (`_default` when absent). | `lib/pipelines/engine.ts:264-279,307-322` |

### Caller-supplied credential/profile identifiers — MUST-NOT-REPLICATE

- The profile test UI writes `__apiKeyId` into its form (`app/profiles/page.tsx:1051-1059`); the internal test route takes that field, requires profile access, then synthesizes `x-api-key-id` for the endpoint runner (`app/api/internal/test-profile-endpoint/route.ts:17-29,57-81`). The guard uses the currently authenticated NextAuth session and allows ADMIN full access; USER requires a matching `UserProfileAssignment` (`lib/auth-guard.ts:45-70`). **MUST-NOT-REPLICATE:** using that client-selected profile id as runtime credential identity (`test-profile-endpoint/route.ts:17-29,57-81`).
- The schema workflow submission routes accept `apiKeyId` from multipart form data and, if absent, select an API key whose role is `ADMIN` as fallback (`app/api/v1/docs/workflows/route.ts:47-85`; `app/api/v1/docs/workflows/schema/route.ts:58-79`). **MUST-NOT-REPLICATE:** form-selected credential identity and implicit admin-key fallback (`workflows/route.ts:47-85`; `workflows/schema/route.ts:58-79`).
- Boundary qualification: ordinary public `/api/v1/` middleware deletes incoming `x-api-key-id` and `x-user-id` before forwarding (`middleware.ts:32-52`). The endpoint runner gives an already-present `x-api-key-id` precedence over resolving the presented `x-api-key` (`lib/endpoints/runner.ts:84-110`); the internal profile-test route synthesizes that header from the submitted `__apiKeyId` after its profile-access guard (`app/api/internal/test-profile-endpoint/route.ts:17-29,57-81`). **MUST-NOT-REPLICATE:** treating that caller-selected identifier/synthesized header as proof of runtime credential identity rather than deriving identity from the presented credential (`test-profile-endpoint/route.ts:17-29,57-81`; `runner.ts:84-102`). The public middleware strip is the observed boundary for the ordinary public route (`middleware.ts:32-52`).
- Profile and override CRUD also take `apiKeyId` from query/body as the target profile resource (`profile-endpoints/route.ts:19-28,110-120`; `ext-overrides/route.ts:21-35,59-82,134-148`). These handlers separately call `requireProfileAccess`; for ordinary users the guard checks the session user’s assignment, while ADMIN is full-access (`lib/auth-guard.ts:45-70`). This describes their resource selection and guard, not credential authentication by API key id.

## 3. Schema-builder and pipeline-mapping journey

The workflow schema is a JSON object with slug/name, optional input schema, typed node array, ordered `flow`, and optional output references; connector nodes name an `ExternalApiConnection.slug` and may carry a node-level `overrideConnector` (`lib/workflow-builder/types.ts:8-20,22-34,45-72,160-175`). Supported node kinds include connector, parallel/join, file parsing/download, callback, archive, human, and input nodes (`types.ts:22-34,148-158`).

The admin API accepts either JSON schema or XML (converted to schema), validates slug/nonempty flow/nodes, unique ids, supported node types, connector slug presence, and flow references, then saves by slug in `AppSetting` under `wb_schema:<slug>`; GET lists/loads, DELETE removes (`app/api/internal/workflow-schemas/route.ts:13-64`; `lib/workflow-builder/interpreter.ts:38-71`; `lib/workflow-builder/loader.ts:10-49`). The schema-run API loads that saved schema and validates it before enqueueing (`app/api/v1/docs/workflows/schema/route.ts:18-34`); `runWorkflowFromSchema` validates and executes the flow (`lib/workflow-builder/run-schema.ts:17-33`).

“Pipeline mappings” is a nested route, `/api/internal/workflow-schemas/pipeline-mappings`, not a standalone `app/api/internal/pipeline-mappings` route. It loads a schema, finds connector nodes, fetches matching legacy connection rows, and projects each node id/connector slug plus connection defaults and that node’s stored override fields (`app/api/internal/workflow-schemas/pipeline-mappings/route.ts:13-50,51-96`). The companion admin PUT finds `(schema slug, node id)` connector node and persists only provided `prompt`, `staticFormFields`, `extraHeaders`, `responseContentPath`, and `timeoutSec` into `node.overrideConnector` (`app/api/internal/workflow-schemas/override/route.ts:9-47`; shape `lib/workflow-builder/types.ts:53-72`). These are schema/node-scoped overrides, distinct from the API-key/endpoint/step `ExternalApiOverride` table.
