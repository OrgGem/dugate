# Legacy workflow `process` names - evidence memo

**Purpose:** decision support for Product Q1. This is a read-only characterization of the legacy repository; it does not select a mapping or define a wire change.

## 1. What the legacy process route accepts

`POST /api/v1/docs/workflows` reads the multipart `process` field, trims surrounding whitespace, and requires a matching key in `SERVICE_REGISTRY.workflows.subCases`. An absent value returns 400, and an unregistered value returns 404 before submission (`app/api/v1/docs/workflows/route.ts:15-29`). The route then builds `endpointSlug = workflows:${processName}` (`app/api/v1/docs/workflows/route.ts:43-48`). The registry has exactly three sub-case keys: `disbursement`, `lc-checker`, and `doc-compare` (`lib/endpoints/registry.ts:373-403`). Lookup is by the trimmed string as-is; the route does not lowercase or alias the value (`app/api/v1/docs/workflows/route.ts:19-29`).

The worker's code-driven `WORKFLOW_REGISTRY` maps those same three names to `runDisbursement`, `runLcChecker`, and `runDocCompare` (`lib/pipelines/workflow-engine.ts:415-425`). Unknown worker names can fall back to loading a persisted schema (`lib/pipelines/workflow-engine.ts:452-465`), but that fallback does not expand the public `process` allowlist: the public route rejects an unknown `process` at `app/api/v1/docs/workflows/route.ts:26-29`.

| Exact legacy `process` | Registered mechanism and execution | Registry / runner evidence |
|---|---|---|
| `disbursement` | Code-driven workflow. Four numbered stages: parallel classify, parallel extract, cross-check, report; it pauses for approval after extraction. | `lib/endpoints/registry.ts:379-387`; `lib/pipelines/workflow-engine.ts:421-425`; `lib/pipelines/workflows/disbursement.ts:39,57,93-101,157-168,207-216,234-259` |
| `lc-checker` | Code-driven workflow. Three stages: parallel OCR, compliance check, report. | `lib/endpoints/registry.ts:388-394`; `lib/pipelines/workflow-engine.ts:421-425`; `lib/pipelines/workflows/lc-checker.ts:26,43,68-82,128-137,168-209` |
| `doc-compare` | Code-driven workflow. Four stages: parallel OCR, table-of-contents extraction, section comparison, report; it checks for two input files. | `lib/endpoints/registry.ts:395-401`; `lib/pipelines/workflow-engine.ts:421-425`; `lib/pipelines/workflows/doc-compare.ts:29,46,51-53,84-96,136-149,164-180,196-224` |

The `connections: []` plus `isWorkflow: true` fields identify these registry entries as custom workflows rather than linear connection lists (`lib/endpoints/registry.ts:379-401`). The stage execution itself is in the three workflow modules cited in the table.

## 2. Separate schema-driven workflow identifiers

Legacy also has a distinct `POST /api/v1/docs/workflows/schema` route. It reads `schemaSlug`, loads a previously stored schema, validates it, and places that slug in the submission variables (`app/api/v1/docs/workflows/schema/route.ts:15-33,39-56`). The loader stores schemas under `wb_schema:<slug>` and retrieves them by that key (`lib/workflow-builder/loader.ts:10-33`); the schema type contains a `slug` and ordered `flow` (`lib/workflow-builder/types.ts:162-170`). At runtime, `runWorkflow` detects `schemaSlug` and dispatches to `runWorkflowFromSchema` (`lib/pipelines/workflow-engine.ts:439-450`); that builder validates and walks the schema flow (`lib/workflow-builder/run-schema.ts:17-34,42-80`).

This schema path has no fixed, code-enumerable slug set: a slug is usable when its schema is stored and valid (`lib/workflow-builder/loader.ts:12-33`; `app/api/v1/docs/workflows/schema/route.ts:19-33`). The docs show example schema slugs `simple-doc-processing` and `disbursement-review` (`docs/workflow-schema-guide.md:383-405,461-475`); the code example and schema route tests also use a schema slug `disbursement` (`lib/workflow-builder/examples/schema-disbursement.ts:1-10`; `tests/workflow-builder/schema-route.test.ts:135-180`). These are `schemaSlug` examples, not additional values accepted as `process` by the other route (`app/api/v1/docs/workflows/schema/route.ts:19-27`; `app/api/v1/docs/workflows/route.ts:19-29`).

## 3. Evidence that a client can call them, and limits on adoption claims

All three registered names are documented as workflow processes at the public API path, with multipart `process` examples: `disbursement` (`docs/API_PROFILES_SPEC.md:332-357`), `lc-checker` (`:406-425`), and `doc-compare` (`:451-468`). The application also has UI callers that submit those exact names to `/api/v1/docs/workflows`: disbursement (`app/doc-pipeline/hooks/useWorkflowPolling.ts:45-60`), LC checking (`app/lc-checker/hooks/useWorkflowPolling.ts:45-61`), and document comparison (`app/doc-compare/hooks/useWorkflowPolling.ts:87-100`). This establishes documented and in-repository client use, not actual external customer adoption.

I found no test invoking the code-driven `/api/v1/docs/workflows` route or submitting a `process` value. The workflow route test present in this area is explicitly for `/api/v1/docs/workflows/schema` and tests `schemaSlug` (`tests/workflow-builder/schema-route.test.ts:1-10,41,111-180`). No production traffic or customer-usage telemetry was inspected, so whether external customers are currently using any of the three cannot be established from this evidence memo.

There is one stale documentation example: the workflow README shows `process=appraisal` (`lib/pipelines/workflows/README.md:293-298`), but `appraisal` is not a registry key (`lib/endpoints/registry.ts:378-402`) and the route returns 404 when a `process` key is unregistered (`app/api/v1/docs/workflows/route.ts:26-29`). Treat this as a docs/code mismatch, not evidence that the process is currently accepted.

## 5. Product options memo (no option selected)

1. **Keep the three legacy names as aliases to same-named business IDs.** This preserves the three documented and UI-submitted values (`docs/API_PROFILES_SPEC.md:334-357,406-425,451-468`; UI call sites in section 3). It gives direct evidence for those three mappings. It does not provide legacy evidence for `simple-extraction`, `multi-step-analysis`, or `transform-compare`; if those are also accepted, their meaning would need a separate product mapping decision (`lib/endpoints/registry.ts:378-402`).
2. **Use only the selected canonical business names.** If canonical names are the three business names supplied in the question, their strings already match the three legacy `process` values, so name-level compatibility for those workflows is preserved by the evidenced mapping (`lib/endpoints/registry.ts:379-401`). This option leaves the resolver-name set unsupported unless Product separately defines it (`lib/endpoints/registry.ts:378-402`).
3. **Accept both the legacy names and resolver names as aliases.** This offers more name coverage, but only the legacy three have demonstrated process semantics; `transform-compare` to `doc-compare` is merely a possible semantic match, and the other two lack a direct registry match (`lib/endpoints/registry.ts:378-402`; `lib/pipelines/workflows/doc-compare.ts:46-53`). The compatibility risk is that clients may assume distinct names mean distinct behavior when no such distinction is evidenced in legacy.

These are options for Product Q1 only. No choice, wire behavior, or route change is made in this memo.
