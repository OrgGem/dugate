# Local Admin authentication cutover characterization (read-only)

Date: 2026-10-01  
Scope: source and test inventory for `LOCAL-00..06`, comparing the legacy NextAuth identity to the current Orchestrator shell/session/auth paths. No tests were run and no source, test, task, or gate files were changed. The status labels below are evidence summaries, not task completion decisions; all LOCAL boxes and release gates remain unchanged.

## Findings in brief

- The legacy application authenticates a database user and carries that user's `id`, `username`, and `role` in its NextAuth JWT/session. Rework does not currently implement a local user/password identity.
- Rework does have OIDC login, an opaque server-side session store (memory or Redis), session expiry/revocation, CSRF checks for cookie-authenticated Admin mutations, and role/action/tenant gates. Those primitives do not supply the missing local-user repository, password verifier, mode selector, bootstrap/reset lifecycle, or local audit actor.
- A separate legacy rework path accepts a shared `ADMIN_TOKEN` at `POST /admin/login`, maps it to `admin` (or a caller-selected lower role using `role:<role>:<token>`), and mints a signed `du_admin` cookie containing a role but no user subject. The standard standalone `main.ts` wiring also does not pass `adminShellCookieSecret`; `attachAdminShell` refuses to mount without both that secret and `adminToken`.
- I found no unverified identity-header path in the inspected auth surfaces. `Authorization` is matched against configured bearer credentials; `x-csrf-token` is checked as CSRF proof; `x-forwarded-proto` affects cookie transport posture only. The shared-token-to-role paths and the legacy-cookie fallback are still MUST-NOT-REPLICATE as local human identity.

## MUST-NOT-REPLICATE paths

1. **Shared `ADMIN_TOKEN` → human-looking `admin` shell role and signed cookie.** `deriveRoleFromToken` maps the raw configured secret to admin and accepts a caller-supplied role prefix around the same secret (`src/app/admin/shell-router.ts:519-540`). `handleLoginPost` reads a generic form field `token`, invokes that mapper, then mints `du_admin` with role-only claims (`:1029-1058,1087-1114`). This must never mint `issuer='du-local'`, a local account session, or a per-user audit actor. The role prefix is also caller-controlled privilege labeling and must not become role authority in a local flow.
2. **Shared bearer secrets → privileged principals.** `resolveAdminPrincipal` turns the shared platform bearer into `role=platform` and tenant bearer values into tenant operators (`src/modules/admin-actions/rbac.ts:30-40`); direct Admin endpoints accept the platform bearer through `assertAdminAuth` (`src/server.ts:2799-2809`). This is credential-based machine/admin authorization, not an unverified header, but must not be treated as an individual local user's identity or used to mint a local session. Its policy/scope is explicitly unresolved at LOCAL-00 (`tasks/ADMIN-LOCAL-AUTH-2026-09-30.md:17,25`).
3. **Legacy role-only `du_admin` fallback into session-authenticated surfaces.** The cookie is signature-verified, so it is not an unverified cookie/header; nevertheless it carries no local subject and is rooted in the shared-token login. The sync action resolver accepts its claims (`src/modules/admin-actions/rbac.ts:236-256`); the async action resolver falls back to it when no `du_session` cookie is present (`:347-378`); the shell also permits it in OIDC coexistence when `du_session` is absent (`src/app/admin/shell-router.ts:1738-1744`). Local-only/both cutover must reject this legacy identity source unless an explicitly signed policy retains it strictly as a separate machine/break-glass plane.
4. **No caller-asserted identity header found in the examined rework paths.** Do not add one: `AdminShellRequest` has no header channel (`src/app/admin/shell-types.ts:47-75`), while the action resolver only trusts a bearer after secret equality and uses CSRF headers solely as proof (`modules/admin-actions/rbac.ts:30-40,357-375`). Forged-header denials are pinned by tests (`tests/admin-shell-session-lifecycle.test.ts:331-391`).

## What would make “adminToken does NOT become local identity” provable

There is currently no local-auth mode or local principal against which to state that negative assertion. After the LOCAL-00 policy and local principal/session path exist, a meaningful regression test should:

1. Start the actual `createApp`/mounted-shell composition with a sentinel `ADMIN_TOKEN` distinct from a seeded local user's password, in `DU_ADMIN_AUTH_MODE=local`, and prove boot does not require OIDC or the machine token (the current `main.ts` omission and `attachAdminShell` dual guard must first be resolved: `src/main.ts:105-129`; `src/app/admin/shell-server.ts:502-506`).
2. Submit the sentinel through the old `POST /admin/login` token field and as `Authorization: Bearer <ADMIN_TOKEN>` at local-user login/protected user routes. Require denial, no `du_admin` cookie, no `du-local` session record, no local identity/audit actor, and zero protected-action side effects. The control must avoid accidentally using the same sentinel as a user's actual password.
3. Prove the positive control: only a valid local username/password resolves an immutable stored user ID and server-side role/tenant, mints an opaque `du_session` whose record has `issuer='du-local'` and `sub=<that ID>`, and creates an audit actor bound to that issuer/ID; no signed role-only `du_admin` is issued.
4. In `local` and `both`, attach a legacy `du_admin` cookie and separately send the shared bearer; assert neither becomes a local user and the mode's explicit machine-bearer policy is enforced. Include stale/expired session, CSRF-missing mutation, account disable/reset/role downgrade, and a two-replica revocation path so fallback cannot resurrect the shared-token identity.

The existing positive test that exact `ADMIN_TOKEN` is accepted as shell role admin (`tests/admin-shell-router.test.ts:78-88,141-160`) demonstrates the opposite behavior in the legacy mode; it is not evidence for the required negative local-mode property.
