## 1. Workflow route trace and exact 503 condition

The workflow paths are already claimed by the compatibility route. This is a mounted-but-unimplemented path, rather than a missing `server.ts` route (`services/orchestrator/src/server.ts:1745-1767`).

| Stage | Current behavior | Evidence |
|---|---|---|
| Request ingress | Multipart `POST /api/v1/docs/...` bodies take the streaming compatibility path; `services/orchestrator/src/server.ts` recognizes the docs path/content type and avoids buffering/parsing it as JSON before route dispatch. | `services/orchestrator/src/server.ts:734-753` |
| Route mount | `services/orchestrator/src/server.ts` invokes `handleLegacyRoute` before canonical routes and returns every non-null compatibility response. `resolvePrincipal` is passed as a lazy callback. | `services/orchestrator/src/server.ts:1745-1767`, especially `services/orchestrator/src/server.ts:1759-1762` |
| Path recognition | `/api/v1/docs/workflows` parses as `{kind:'workflows'}` and `/api/v1/docs/workflows/schema` as `{kind:'workflow-schema'}`. Other docs routes are restricted to known core actions. | `services/orchestrator/src/compat/legacy-http-mount.ts:191-200` |
| Method and placeholder | For either workflow kind, a non-POST method returns 405. For POST, `handleLegacyRoute` immediately returns 503 whenever `docs.kind !== 'action'`, with detail `The legacy workflow facade is not available on this deployment.` | `services/orchestrator/src/compat/legacy-http-mount.ts:391-407` |

**Exact 503 predicate:** the path parser returned `workflows` or `workflow-schema` and the method is `POST`. The branch does not inspect `process`, `schemaSlug`, registered businesses, connector bindings, a workflow dispatcher, or schema interpreter. It returns before calling `request.resolvePrincipal()` and before using `host`; therefore this 503 is not a dynamic “registry missing” check and is not conditional on a specific process. It also means no workflow business is submitted from this path today (`services/orchestrator/src/compat/legacy-http-mount.ts:397-407,410-419`).

The source comment says the mapping table “is not in this repo yet” (`services/orchestrator/src/compat/legacy-http-mount.ts:398-400`), but a helper now exists at `businesses/document-core/src/pipelines/legacy-workflow-mapping.ts:4-5`. That helper is not imported by the Orchestrator compatibility files or `server.ts` (repository search found its production definitions only in document-core and its test call sites). More importantly, its fixed process union/selectors are `simple-extraction`, `multi-step-analysis`, and `transform-compare`; they do not name `lc-checker`, `disbursement`, or `doc-compare` (`businesses/document-core/src/pipelines/legacy-workflow-mapping.ts:4-5,56-88,142-165`). Its schema resolver accepts a caller-supplied registration list and resolves active entries to recipes; it does not load schema registrations or serve an HTTP response (`businesses/document-core/src/pipelines/legacy-workflow-mapping.ts:167-239`). Thus the comment is stale as a broad repository statement, while workflow dispatch for the three landed businesses remains unwired.

## 4. Risks, order, and suggested acceptance fixtures

### Risks

- **D5 file collision:** D5’s current shared changes modify the document-core manifest and worker registration; keep route integration behind its handoff and follow its scope/serialization notes (`businesses/document-core/src/manifest/document-core.manifest.ts:101-111,425-467`; `businesses/document-core/src/worker.ts:50-72,1843-1845,1997-2000`; D5 probe `du-rework/coordination/reports/codex-d5-scope-probe-doc-compare-registration-2026-10-01.md:47-56`). Do not duplicate its mount map or edit the same core files concurrently.
- **Mapping ambiguity:** the live resolver supports `simple-extraction`, `multi-step-analysis`, and `transform-compare`, while the landed packages are named `lc-checker`, `disbursement`, and `doc-compare` (`businesses/document-core/src/pipelines/legacy-workflow-mapping.ts:4-5,56-88`; LC adapter `businesses/lc-checker/src/legacy-facade.ts:24-25`). Picking aliases or supporting both sets changes product compatibility and is not determined here.
- **Schema lookup gap:** `resolveLegacySchemaSlug` validates unique active mappings and executable recipes, but its input is a caller-provided list (`businesses/document-core/src/pipelines/legacy-workflow-mapping.ts:171-239`). There is no current route-side source of that list and the 503 prevents `/schema` from reaching the helper (`services/orchestrator/src/compat/legacy-http-mount.ts:397-407`).
- **Business availability:** LC live registration/activation has not been demonstrated (`du-rework/coordination/reports/tester-p9-02-verify-2026-10-02.md:49`); doc-compare package registration code is visible in the current D5-modified worktree (`businesses/document-core/src/manifest/document-core.manifest.ts:101-111,425-467`; `businesses/document-core/src/worker.ts:50-72,1997-2000`), but D5 handoff/final verification and live platform activation are not established; package handler presence is not proof of enabled/active platform registry state.
- **Connector bindings:** LC requires four named slots in its manifest; disbursement calls four named task values. No connector binding evidence is established by these receipts. A route can be syntactically wired while every workflow fails at provider dispatch.
- **Multi-turn execution:** these are workflow handlers rather than simple one-shot formatters. The LC worker has separate main/OCR/visual handler kinds (`businesses/lc-checker/src/worker.ts:58-63,445-452`), disbursement yields workflow continuations (`businesses/document-core/src/worker.ts:1070-1102`), and doc-compare’s handler entry now appears in the D5-modified worker (`businesses/document-core/src/worker.ts:1997-2000`). Acceptance must include continuation/redelivery behavior; a submit-only green path is insufficient. The legacy route still does not select either workflow (`services/orchestrator/src/compat/legacy-http-mount.ts:397-407`).
- **Compatibility/security boundary:** the workflow route must continue to derive tenant/API-key identity from the platform-resolved principal. The server passes `resolvePrincipal` from `resolveApiKey` (`services/orchestrator/src/server.ts:1759-1762`), and LC’s adapter rejects identity fields from form data (`businesses/lc-checker/src/legacy-facade.ts:55,89-100`). The current 503 returns before principal resolution (`services/orchestrator/src/compat/legacy-http-mount.ts:397-414`); future dispatch must not use that early return as an identity shortcut.

### Recommended implementation order

1. Product/architect answer the process-name and schema-registration questions below; retain COMP-00 ownership of all public wire semantics.
2. D5 must hand off and settle its current document-core changes first; confirm the final manifest/worker registration and verification before any dependent routing code targets doc-compare (`businesses/document-core/src/manifest/document-core.manifest.ts:101-111,425-467`; `businesses/document-core/src/worker.ts:50-72,1997-2000`).
3. Connector owner confirms deployed slot/task bindings for each business/process selected. LC’s registration/activation and deployable image/manifest must be independently established; the offline fake-fetch test is not live registration evidence (`du-rework/coordination/reports/tester-p9-02-verify-2026-10-02.md:49`).
4. One server integrator wires the existing compat mount/host path and process/schema delegation. Keep `services/orchestrator/src/server.ts` serialized to one writer (`services/orchestrator/src/server.ts:1745-1767`); do not introduce a second public route or change contracts.
5. Add offline route/host fixtures, then package and orchestrator typechecks. Only after those are green should a separate approved integration task test live registry, connector and continuation delivery; this read-only packet did not run such tests.

### Suggested offline acceptance fixtures

- **Dispatch table fixture:** for each Product-approved process, assert one internal selection of the expected registered business/action and that an unknown process fails through the existing compatibility error path after the path stops returning placeholder 503. Assert `/docs/{core-action}` continues through the unchanged six-action branch.
- **Schema fixture:** pass an active registered schema mapping to the current resolver, including duplicate slug, retired, missing mapping and non-executable recipe cases; assert the `/workflows/schema` adapter delegates to that same resolver and does not interpret a user slug as code. Pin the response envelope/status from the existing COMP-00 decision before asserting it.
- **Identity fixture:** valid workflow request uses only the server-resolved tenant/API-key; form `apiKeyId`, tenant/user/role fields are refused by the existing LC adapter or the approved common decoder. Assert no client field selects a principal.
- **Response parity fixture:** compare first submit, replay/sync behavior, poll while running, and a waiting/continuation operation against the already-approved legacy wire fixture. Do not introduce a new status, header, DTO or public URL shape in this wave.
- **Multi-turn fixture:** fake connector/artifact/checkpoint ports; exercise child fan-out/join, redelivery, and a waiting continuation through the canonical runtime, ensuring the legacy facade does not project a false terminal result. No DB/Redis/S3/provider required for this fixture.
