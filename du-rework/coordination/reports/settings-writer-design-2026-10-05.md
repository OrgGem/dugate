## Executive finding

The settings catalog is no longer the whole surface: the current tree now has a settings DTO and a BFF route. The write path still fails closed with `SETTINGS_WRITER_DISABLED`, and the platform `GET /api/v1/admin/settings` target is not implemented. Earlier receipts that said there was no settings DTO describe an older snapshot; this report uses direct source at the line references below.

### Contract decisions that must precede implementation

1. **Prompt slot identity:** the current contract defines `extract`, `analyze`, `transform`, `generate`, `compare` (`packages/contracts/src/settings.ts:47-69`). The legacy catalog maps `ai_image_prompt`, `ai_pdf_prompt`, `ai_docx_prompt`, `ai_compare_prompt`, `ai_generate_prompt` (`apps/admin-web/src/features/settings/catalog.ts:43-48`). Freeze an explicit mapping or replacement policy; do not map image/PDF/DOCX prompts to endpoint slots by guesswork.
2. **Storage backend name:** the settings DTO says `local | s3` (`packages/contracts/src/settings.ts:77-86`), while runtime uses `postgres | s3` and defaults to PostgreSQL (`services/orchestrator/src/main.ts:115-124`). Pick the public term and document its relation to the implementation before a read/write round trip is exposed.
3. **TTL meaning:** `packages/contracts/src/settings.ts:72-86` calls `ttlSeconds` an S3 presigned-URL lifetime. The legacy key is `s3_cache_ttl_hours` (`apps/admin-web/src/features/settings/catalog.ts:50-56`). Current single-upload grant TTL is fixed at two minutes (`services/orchestrator/src/modules/artifacts/artifacts.ts:43,151-165`) and multipart session/part URL TTL are separate bounded values (`services/orchestrator/src/modules/artifacts/multipart-service.ts:258-277`). Specify separate fields if both URL lifetime and retention/cache TTL are needed; do not silently map hours to seconds or change grant expiry through a cache setting.
4. **Base URL ownership:** catalog rows assign provider/model partly to tenant policy but assign OpenAI-compatible base URL to a Connector config revision (`apps/admin-web/src/features/settings/catalog.ts:37-41`). Treat the URL as a connector endpoint/binding revision, with URL/egress validation, rather than a second independent copy in a policy row. ACUI-M06 deployment ownership must provide a real source before writes can be enabled.

## 2. Writer A — AI policy and five prompt defaults

### Gap and dependencies

The only `aiDefaults`/`promptDefaults` implementation found is the contract (`packages/contracts/src/settings.ts:39-69,115-122`); profile prompt overrides are a different scope and already have admission-time pinning (`services/orchestrator/src/modules/profiles/prompt-overrides.ts:5-22`; `services/orchestrator/src/modules/operations/submission.ts:332-346,431-437`). There is no general settings row/revision store, no platform route for `/api/v1/admin/settings`, and no consumer resolver that applies these defaults. A write-only endpoint alone would therefore report success without affecting new work.

Dependencies: freeze the prompt mapping above; use the existing PostgreSQL service and transaction conventions; obtain the server-side role/scope policy; and complete the ACUI-M06/Connector source path for base URL. Credentials are deliberately excluded from this policy record and depend on Writer B.

### Proposed implementation boundary

- Store only provider, model, the effective connector-binding revision/reference, and the five agreed prompt defaults in an append-only PostgreSQL policy revision. These are non-secret operational values and may be stored as ordinary DB fields/JSONB under the deployment's normal encrypted-disk/database controls; do not reuse `admin_crypto_config` (that store is specifically wired to `/api/v1/admin/crypto-config`, `services/orchestrator/src/server.ts:219-232`, `services/orchestrator/src/http/routes/admin.ts:660-677`). Keep credentials only as Vault references from Writer B. Reject a base URL with embedded userinfo/credential query fields and use an approved endpoint/egress policy.
- Use a scope-keyed active-revision pointer and optimistic expected-revision/CAS on update. Build a complete candidate by merging omitted partial fields with the current revision, validate the whole candidate, insert it as pending, then atomically activate only if the expected current revision still matches. Do not allow an empty/invalid candidate to clear required fields accidentally.
- **Decision authority:** default to platform-admin-only for platform-wide defaults, enforced on the server after CSRF (the current BFF order is `services/orchestrator/src/app/admin/bff/settings.ts:102-118`). For tenant/business policy, derive scope from the authenticated principal and the approved assignment; never trust a body-selected tenant. Keep tenant-admin editing disabled until the policy owner explicitly approves a field-by-field delegation matrix. Every successful update and rollback must append an audit record with actor, scope, old/new revision IDs, and changed field names, never secret content.
- Resolve and pin the selected policy revision and effective prompt defaults at operation admission beside the existing profile/prompt snapshot (`services/orchestrator/src/modules/operations/submission.ts:332-346,431-437`). Existing operations keep their admitted snapshot. Rollback atomically repoints the active revision to a retained earlier revision; it affects new admissions only. Keep revisions referenced by live operations available.
- Base URL changes must first produce a valid Connector/deployment binding revision; policy activation references that immutable revision. Until ACUI-M06 has a runtime source, the action must refuse the base-URL change rather than writing a DB value nobody reads. If endpoint update spans a separate deployment service, stage policy as pending and activate only after the endpoint adapter reports success; a failed stage leaves the old active policy untouched.

**Smallest useful code unit:** one vertical backend slice consisting of a migration for versioned policy rows/active pointer, a policy service with merge/validate/CAS/rollback, the platform admin route and audit event, plus admission-time resolver/pinning and focused tests. Add the BFF forwarder only after the platform route exists; keep UI capability false until both are composed.

**Offline test conditions:** use a temporary/fake PostgreSQL transaction layer and no provider calls. Cover all five canonical slots, explicit legacy-slot mapping, strict unknown-field rejection, partial merge, required-field validation, platform-admin allow/deny, tenant-scope isolation, stale-CAS 409 with no active change/audit, exactly one update/audit, rollback to a previous revision, and admitted operation snapshots remaining unchanged after a later update/rollback. Test base URL activation against a fake connector/deployment source; failure leaves old active revision. No live endpoint or production DB is needed for this packet.

## 3. Writer B — Vault secret-reference adapter

### Gap and dependencies

The settings read contract exposes only `secretPresent` (`packages/contracts/src/settings.ts:72-86`); the update shape has a generic write-only `storage.secretValue` (`packages/contracts/src/settings.ts:134-152`). The BFF currently refuses before upstream, and there are no settings-specific Vault write/read references. Existing connector workflow proves the desired safe ordering and masked result (`services/orchestrator/src/modules/connector-credentials/workflow.ts:12-30,271-324`), but its validator requires the trusted connector/account path (`services/orchestrator/src/modules/connector-credentials/workflow.ts:185-193,254-269`) and the current Vault policies are limited to `du/connector/*`.

Dependencies: Vault operator approval of a dedicated settings prefix and least-privilege policies, orchestrator machine identity/secrets bootstrap, a pinned reference schema, and a policy/storage revision store that can retain old refs for rollback. Runtime consumers also need an explicitly approved read identity for the new prefix; do not give the writer data-read capability.

### Proposed implementation boundary

- Secret input crosses the write request once and exists only in bounded server memory while it is sent to KV v2. It must never enter PostgreSQL, operation/job payloads, audit details, logs, error strings, retries, browser storage, or read responses. Persist only a validated `{mount,path,key,version}` reference (and a presence bit for reads). Never accept an arbitrary Vault path from the browser: derive a path from server-owned platform/tenant/provider/storage coordinates and validate it against a dedicated settings namespace.
- Keep the current writer's no-data-read model. Use a new narrow policy prefix (proposed `du/settings/...`, exact hierarchy to be approved), with write/create-update and metadata-only permissions for the API writer; grant secret-value read only to the runtime consumer identity that must use it. Do not broaden `du/connector/*` to make settings refs pass, and do not let the UI select a mount/path/key.
- Follow the existing CAS → pending ref revision → explicit activation pattern. Vault success followed by DB failure leaves an unreferenced, non-routable KV version. A failed activation leaves the prior ref active. Rollback switches the active config ref to a retained earlier Vault version; do not destroy old versions while any active or in-flight revision can reference them. Responses and audits may report `hasValue`, ref version, and revision state only.
- Separate the settings request's write-only secret input DTO from read DTOs; a `secretPresent` boolean cannot be client-set. If generic `storage.secretValue` stays in the contract, prove in the server schema/service that it is consumed only by Vault and is stripped before any DB/audit object is constructed. Add equivalent purpose-specific input for provider credentials without ever adding secret fields to `SettingsRead`.

**Smallest useful code unit:** one purpose-scoped `SettingsVaultSecretWriter` adapter over KV2 CAS, its trusted path/ref validator, a staged-ref activation service, and isolated contract/service tests. Reuse transport/error hygiene from `services/orchestrator/src/modules/connector-credentials/vault-kv2-writer.ts`, not connector-only ownership checks or the browser-visible connector action.

**Offline test conditions:** inject a fake Vault writer and fake revision store. Use a synthetic secret sentinel and assert it is absent from SQL arguments, persisted records, result DTOs, audit payloads, logs, errors, job bodies, and retry/idempotency payloads. Cover prefix/path escape rejection, version pinning, CAS conflict, forbidden policy, retryable outage, Vault-write/DB-failure orphan being non-routable, activation conflict preserving the prior ref, presence-only read, and rollback retaining the old ref. No live Vault or real credentials are needed for unit/contract tests; rollout remains gated on the actual Vault owner/policy.

## 4. Writer C — artifact storage configuration generations

### Gap and dependencies

`services/orchestrator/src/main.ts:115-130` reads backend, bucket, region, endpoint and migration flag from process environment once; `services/orchestrator/src/app/bootstrap/create-app.ts:222,268-274` constructs the S3 client at boot. The artifact row pins `storage_backend` and object `storage_version_id`, and the facade pins immutable object versions (`services/orchestrator/src/modules/artifacts/storage-facade.ts:3-11,57-74`), but there is no config-generation ID to say which bucket/endpoint an S3 row belongs to. Changing the env-backed config in place can strand rows or in-flight grants. The existing migration code is specifically PostgreSQL-bytea-to-S3 data movement with integrity checks and CAS (`services/orchestrator/src/modules/artifacts/storage-migration.ts:236-293`), not a storage settings writer.

Dependencies: storage owner approval for bucket versioning, endpoint/region, workload identity/IAM/KMS, backups/retention and canary; a deployment adapter capable of serving an immutable generation to the running service (ACUI-M06 currently addresses connector URLs only); Writer B if static S3 credentials are approved instead of workload identity; and an explicit resolution of the backend/TTL contract mismatches above.

### Proposed generation and activation model

- Add an immutable `artifact_storage_generations` record with generation ID, backend (`postgres`/`s3` canonicalized), endpoint, bucket, region, path-style setting, the approved non-secret TTL/retention parameters, optional Vault credential reference, state (`STAGED`, `ACTIVE`, `RETIRED`), creator/audit metadata and validation result. Store no S3 key material. Keep one active-generation pointer with expected-generation CAS.
- Add `storage_generation_id` to artifact metadata and to the trusted grant/finalize path. New grants pin the generation at grant creation and finalization must use that same generation, even if a different generation activates during upload. Reads resolve the recorded generation and exact object version. Backfill existing rows to the current generation before enabling dynamic switching; preserve the legacy mapping until that backfill is verified. Retain generation credentials and facades while referenced by artifacts, active operations, unexpired grants, or the approved restore window.
- Activation sequence: (1) create STAGED candidate; (2) validate schema, IAM and S3 versioning without mutating the active pointer; (3) run a synthetic canary through grant/upload/finalize/read and verify tenant, size, hash and non-null version; (4) CAS the active pointer; (5) new writes use the candidate while old reads continue through their row-pinned generations. A failed test/CAS leaves the old generation active. Do not copy existing bytes or rewrite artifact rows as a side effect of changing endpoint/bucket.
- Data migration to another backend/bucket remains a separate explicit operation using the existing inventory/copy/verify/CAS flow. Deactivate a prior generation only after references and grants are drained and restore/backups are proven. Rollback resets the active pointer for new writes but keeps both generation resolvers available so artifacts already written to the new generation remain readable. Never claim that switching to PostgreSQL restores S3-only rows; the current runbook explicitly warns it does not (`docs/runbooks/artifact-storage.md:100-118,120-140`).
- Clarify the TTL field split before adding runtime knobs. Current single-upload expiry is two minutes (`services/orchestrator/src/modules/artifacts/artifacts.ts:43,151-165`); multipart has separate session and part-URL TTLs (`services/orchestrator/src/modules/artifacts/multipart-service.ts:258-277`). `s3_cache_ttl_hours` must not silently control grant expiry. A config generation should distinguish grant TTLs from retention/cache lifetime.

**Smallest useful code unit:** generation schema/migration + immutable generation store/CAS pointer + generation-aware facade resolver + artifact/grant metadata pinning + tests. Ship it default-off with the current boot config represented as generation 0/current. Expose Settings write capability only after old-row backfill and multi-generation reads are composed; do not implement a UI toggle that just changes process environment.

**Offline test conditions:** fake generation store, clock, and PostgreSQL/S3 facades. Cover staged validation without activation, failed canary and stale-CAS preserving current generation, grant pinned to generation A while B activates, finalization/read against A, new grant against B, migration preserving original on integrity failure, rollback selecting A for new work while B artifacts remain readable, TTL bounds for single and multipart flows, and reference-aware retirement refusal. No production S3 is needed for these deterministic tests. The live cutover still requires an explicitly approved isolated bucket, real IAM/KMS, versioning, restore rehearsal and non-sensitive canary.
