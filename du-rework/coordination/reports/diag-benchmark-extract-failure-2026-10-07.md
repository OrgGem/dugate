# Diagnostic — r4.1 benchmark extract failure (PROVIDER_UNAVAILABLE)

**Task:** Diagnostic Benchmark Candidate r4.1 Extract Failure (packet from coordinator oc_2 dispatch).
**Owner:** OpenCode 2 (`term_169a5da5`). **Repo scope:** `du-rework` (diagnostic only).
**Date:** 2026-10-07. **Canonical plan:** `coordination/reports/benchmark-execution-results-2026-10-06.md`.
**Compliance:** no product code edited, no images mutated, no commit/push, no task/gate tick.

**Verdict:** Root cause identified with file:line evidence and an offline reproduction.
It is **not** a routing/manifest/orchestrator bug and **not** a mock-provider/network problem.
The connector service fails closed because **invocation-storage encryption is unconfigured in the
r4.1 compose deployment** (`CONNECTOR_INVOCATION_ENCRYPTION_KEYS` is never generated or forwarded),
so the very first step of `/invocations` — the ledger claim — refuses to persist the request and
returns HTTP 502 `PROVIDER_UNAVAILABLE` **before** any row is written and **before** the provider
transport is reached. This is the exact open item already documented in the SEC-ENC-02 receipt §8/§9;
the benchmark was the first live connector-requiring run to hit it.

## 2. Root-cause chain (file:line)

1. **Extract requires a connector; ingest does not.** In the document-core manifest, `ingest`'s
   slots `ocr`/`vision` are `required: false`, while `extract`'s slot `reasoning` is
   `required: true` — `businesses/document-core/src/manifest/document-core.manifest.ts:146-157`
   vs `:184-190`. That is why ingest (local parse) passes and every extract fails.
2. The extract handler invokes that slot: `ctx.connector.invoke('reasoning', …)` at
   `businesses/document-core/src/actions/extract/index.ts:94-100`.
3. worker-sdk POSTs to the connector service: `POST {baseUrl}/invocations` —
   `packages/worker-sdk/src/connector-invoker.ts:150`. A non-2xx response is surfaced as
   `ConnectorTransportError` (`:21-30`); status ≥ 500 maps to `PROVIDER_UNAVAILABLE`
   (`:118-124`), and the connector's own `{error:{code,message}}` is adopted when present
   (`:194-210`). The worker reached the connector service and got a typed 5xx — the binding,
   grant and routing all worked.
4. Connector service route: `POST /invocations` → `runtime.invoke` —
   `services/connector/src/http/server.ts:366-374`.
5. The runtime's **first** step is the ledger claim, before quota/credential/provider I/O:
   `services/connector/src/invoke.ts:65-66` (`const claim = await options.ledger.claim(...)`).
6. The ledger **seals the request before the INSERT**:
   `services/connector/src/db/repository.ts:217-239` (`sealField` → `INSERT … 'IN_FLIGHT'`).
7. With no field crypto configured, `requireCrypto()` throws
   `ConnectorError('PROVIDER_UNAVAILABLE', 'Invocation storage encryption is not configured.', safeToRetry: false)` —
   `services/connector/src/db/repository.ts:80-89`. The throw happens inside the claim
   transaction **before** the INSERT and **before** the provider transport, so the DB keeps
   0 rows and the provider sees 0 calls.
8. The crypto block is resolved only from `process.env.CONNECTOR_INVOCATION_ENCRYPTION_KEYS`:
   `services/connector/src/composition.ts:110-117` →
   `services/connector/src/db/invocation-crypto.ts:468-489`. The accepted JSON shape is
   `{"keyRef":"du-connector-invocation-v1","activeVersion":1,"keys":{"1":"<base64 32B>"}}`
   (`invocation-crypto.ts:321-337`, parser `:338-370`).
9. HTTP mapping: `PROVIDER_UNAVAILABLE` → **502** —
   `services/connector/src/http/server.ts:471-503`.
10. Worker classification: for `ConnectorTransportError`-shaped errors,
    `retryable = !nonRetryableCode && (status === 429 || status === 503)`
    (`packages/worker-sdk/src/worker.ts:538-550`). Status 502 ⇒ **retryable false** ⇒ the task
    fails terminally on the first attempt — matching the log and the fast p50.
11. **Deployment gap (the actual defect):** `CONNECTOR_INVOCATION_ENCRYPTION_KEYS` is
    - not generated by the local env generator — `scripts/docker/init-env.cjs:17-31`;
    - not forwarded to the container — `compose/connector.yml:8-21` (only
      `CONNECTOR_ENCRYPTION_KEY`, the credential cipher, is passed);
    - absent from every `.env*` sample, from `docs/`, and from the benchmark's
      `run-overlay.yml:1-9` (which only adds `PROVIDER_ALLOW_HOSTS` /
      `ALLOW_PRIVATE_PROVIDER_NETWORKS` for the connector).

    Even if a developer put the key into an env file, the compose `environment:` list does not
    forward the variable, so no compose deployment of r4.1 can configure invocation storage crypto.

**Why the symptoms line up:** claim-first throw ⇒ no invocation row; transport never reached ⇒
no provider call; typed 5xx ⇒ `ConnectorTransportError`; 502 ⇒ non-retryable and fast terminal
failure; extract-only (required slot) ⇒ ingest unaffected.

## 3. Cross-reference — this gap was already documented as open

`coordination/reports/sec-enc-02-connector-encryption-2026-10-06.md`:
- §8 (lines 106-111): *"Production boot policy: khi env key unset, invocation writes bị refuse
  (502 non-retryable). SEC-ENC-05 cần thêm boot refusal + env samples để lỗi xuất hiện lúc start
  thay vì lúc invoke."*
- §9 handoff (line 121): *"SEC-ENC-05 (cw1): boot policy + env samples
  (`CONNECTOR_INVOCATION_ENCRYPTION_KEYS`)"*.

So the benchmark did not uncover a new product bug — it **proved the documented gap live**:
offline suites pass because they either inject crypto or assert the refusal, and no earlier live
run had exercised a connector-requiring action after SEC-ENC-02 landed.

## 5. Recommended fixes for the next wave

1. **Deployment wiring (owner: SEC-ENC-05, per the SEC-ENC-02 handoff).**
   - Forward the variable in `compose/connector.yml` (e.g.
     `CONNECTOR_INVOCATION_ENCRYPTION_KEYS: ${CONNECTOR_INVOCATION_ENCRYPTION_KEYS:-}`).
   - Generate a local KEK config in `scripts/docker/init-env.cjs`:
     `{"keyRef":"du-connector-invocation-v1","activeVersion":1,"keys":{"1":"<random base64 32B>"}}`.
   - Add it to `.env.docker.example` / `.env.example` and the docs owner's `docs/08` note.
2. **Boot refusal (owner: SEC-ENC-05).** The connector composition should refuse startup in
   real-data mode when required invocation encryption is unset, so the failure is a red boot
   (health) instead of a per-invocation 502. Keep the runtime fail-closed as defense in depth.
3. **Benchmark preflight (owner: benchmark harness).** Run a connector-live smoke (or capability
   probe) before measurement and assert `connector_invocations ≥ 1` for the connector path;
   treat `PROVIDER_UNAVAILABLE` as an environment failure so it cannot masquerade as a product
   result (today's report required manual forensics to distinguish the two).
4. **Do not work around with plaintext reads.** `CONNECTOR_INVOCATION_LEGACY_PLAINTEXT_READS`
   only opens the read window for legacy rows; writes are refused by design (SEC-ENC-02).
5. **No retry-mapping change recommended now.** 502 non-retryable is intentional for this
   fail-closed configuration error (`safeToRetry:false`); once boot refusal lands the path is
   unreachable. Revisit only if a real provider outage needs retry semantics (out of scope).
