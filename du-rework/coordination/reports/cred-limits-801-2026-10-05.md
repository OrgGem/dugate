## 1. Limitation (a) - timeout was source-only

*Reviewer*: the test only threw `ECONNREFUSED` + SENTINEL; the AbortController was never exercised.
The claim was verified in source - `vault-kv2-writer.ts:92-101` builds an `AbortController` and a
`setTimeout(() => controller.abort(), requestTimeoutMs ?? DEFAULT_TIMEOUT_MS)`, and the bare `catch`
maps the rejection to `VAULT_UNAVAILABLE`/retryable. The old test title claimed "network failure **and
timeout**" while its body never reached the timeout path.

*Now* - `vault-kv2-writer-offline.functional.test.ts` has a real timeout test: the injected fetch
**never resolves on its own** and only settles from a `signal.addEventListener("abort", ...)` handler.
That makes the test structural, not incidental: if the signal were not passed or never fired, the
promise would hang and jest would time out. It asserts `sawSignal === true`, `abortFired === true`,
`elapsed >= 50ms` (fired on the configured 60ms, not the 5s default), `elapsed < 2000ms`,
`{code: VAULT_UNAVAILABLE, retryable: true}`, and that the SENTINEL is in no message.

## 3. Limitation (c) - SQL capture was vacuous

*I probed before fixing*, because the reviewer's stated cause ("makeDb drops binds") did not match what
the data showed. Adding a temporary `expect(sql.length).toBeGreaterThan(0)` returned **Received: 0**.

**The real cause is not the dropped binds.** The G7 chain (upsert -> bootstrap -> rotate -> activate ->
test -> disable) issues **zero SQL**: every collaborator is a fake (Connector service, Vault, revision
store), so nothing ever calls the fake db. `leaks(sql)` and the forbidden-table check were both running
against an empty array.

*Fix, in two parts:*
1. `makeDb` now records binds as well as SQL text (`binds: unknown[][]`), so the harness can see a
   statement's arguments.
2. The vacuous pair is replaced by an **honest, load-bearing pin**: `expect(sql).toEqual([])` with a
   comment - it now FAILS the moment any credential action starts writing to the DB, at which point the
   leak and forbidden-table checks run over real text instead of nothing.

*Plus a harness self-test that proves the detector is real* (a `not.toContain`-style leak test that is
never fed the sentinel proves nothing):
- runs three real statements through `db.tx`, asserts `sql` has 3 entries and `binds` equals the 3 arg
  lists (this is the "capture keeps binds" requirement, now observable);
- **positive control**: `expect(leaks(binds)).toBe(true)` - the detector fires on the injected SENTINEL,
  so every `leaks(...) === false` in the file can no longer be green for free;
- **forbidden-table on real SQL**: `sql.filter(forbidden)` returns exactly the two forbidden statements
  and spares `INSERT INTO api_keys ...` - so the check is load-bearing against captured text, which is
  what the reviewer asked for, on SQL that genuinely ran.
