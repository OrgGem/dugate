## 2. Fix (items 2, 3)

**Item 2** removed `if (!crypto) return value`. `openMetadata` now calls `assertReadableWithoutSeam(value, true)` — the shared rule — before returning verbatim.

**Item 3 — one rule, one code.** `assertReadableWithoutSeam(value, allowPlaintext)` lives in `metadata-crypto.ts` and is called by BOTH the reader (`readStoredText`) and the wrapper (`openMetadata`). The JSON-string-vs-parsed difference is handled inside `looksLikeSealedEnvelope` (which accepts both forms) — it is not left to each caller. A test pins one rule + one error code (`wrapper and reader share ONE rule and ONE error code`).

## 3. The legitimate-sealed-path distinction (item 4)

A **migration/seeding path feeding its first copy** and a **deployment with encryption simply off** both write values that were never sealed. They are not envelope-shaped. They still pass through verbatim — pinned by `the LEGITIMATE no-seam path is preserved` and `the ?? {} callers still work with no seam`.

The envelope-shaped value is the split: a sealed row read by a deployment that cannot open it fails closed. **This is not data-wiping — the row is still in the database.** The value is rejected at read time with `KEY_PROVIDER_FAILED`; the deployment that sealed it (or the key restored) can still read it. Recorded explicitly so "fail closed" is not read as "deletes the row".

## 8. Limitations

- The refactored helper (a concurrent lane's `assertReadableWithoutSeam(value, allowPlaintext)` taking a default-false parameter) is stronger than this packet's minimal split. It was left intact rather than reverted; the wrapper's call passes `true` with the reasoning inline, so the stranded-plaintext behaviour is identical to before.
- The stranded-plaintext path (`assertReadableWithoutSeam(value, true)`) cannot distinguish "never sealed" from "deliberately reading plaintext"; it is the ENC-09 window by design.
- The six `openMetadata` call sites were not each re-tested end-to-end; the wrapper function itself is. A caller that passes the wrong refId will still throw CONTEXT_MISMATCH on valid data — that is a different failure class, owned by the caller, not the wrapper.
