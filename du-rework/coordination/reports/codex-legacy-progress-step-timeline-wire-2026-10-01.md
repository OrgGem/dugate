# Legacy Progress and Step-Timeline Wire (2026-10-01)

## Scope and headline

Read-only characterization of the progress values stored and exposed by legacy pipeline/workflow operations, compared with the current rework operation view, runtime progress endpoint, and persisted task/checkpoint schema. No source files were changed, no tests were run, and no gate or COMP row was changed.

For a normal legacy pipeline, progress is a per-step **start marker**: before invoking step `i`, the engine stores `Math.round((i / pipeline.length) * 100)` and a message naming that step, then sends the same number to BullMQ (`lib/pipelines/engine.ts:281-298`). A running operation's `metadata.pipeline_steps` contains only steps whose processor has returned and whose result has been appended; it does not contain a placeholder/status object for the in-flight or unreached steps (`lib/pipelines/engine.ts:358-394`; `lib/pipelines/format.ts:23-32`). Rework's public operation view currently reports synthetic percent `0` and the state string as its message, and the runtime progress endpoint verifies the lease but does not persist the submitted percent/message (`du-rework/services/orchestrator/src/modules/operations/facade.ts:32-50`; `du-rework/services/orchestrator/src/modules/operations/submission.ts:693-720`; `du-rework/services/orchestrator/src/modules/runtime/runtime.ts:483-492`).

## 1. Legacy write contract

At the beginning of each pipeline loop iteration, the engine computes the exact formula `Math.round((i / pipeline.length) * 100)`, where `i` is zero-based, and the exact message `Đang xử lý bước ${i + 1}/${pipeline.length}: ${step.processor}...` (`lib/pipelines/engine.ts:281-287`). It writes `currentStep`, `progressPercent`, and `progressMessage` to the `Operation` row **before** calling the processor (`lib/pipelines/engine.ts:288-359`). If the queue job exists, it then calls `job.updateProgress(progressPercent)` before the processor is invoked (`lib/pipelines/engine.ts:295-359`). The public status route serializes the database row; it does not read BullMQ job progress (`app/api/v1/operations/[id]/route.ts:18-37`; `lib/pipelines/format.ts:17-32`).

The start-marker formula begins at 0 for the first step and tops out at `Math.round(((N - 1) / N) * 100)` for the last of `N` steps; the percent does not advance on step completion. It jumps to 100 only on successful terminal completion (`lib/pipelines/engine.ts:282-298,365-395,397-414`). Success writes `done: true`, `state: 'SUCCEEDED'`, `progressPercent: 100`, and `progressMessage: null`, then updates BullMQ job progress to 100 (`lib/pipelines/engine.ts:397-425`).

The normal pipeline catch path writes `done: true`, `state: 'FAILED'`, `failedAtStep`, error fields, and the completed-step array, but does **not** set `progressPercent` or `progressMessage`; those remain whatever the last earlier write left in the row (`lib/pipelines/engine.ts:450-465`). The separate invalid-pipeline and deferred-file-URL failure paths also set `done: true`/`FAILED` without setting progress percent or clearing progress message (`lib/pipelines/engine.ts:122-139,142-173`). Deferred URL download sets only `progressMessage` to `Downloading ...` before downloading, leaving the prior percent untouched (`lib/pipelines/engine.ts:142-161`).

## 2. Serialization and `metadata.pipeline_steps`

`formatOperationResponse()` places `op.progressPercent` and `op.progressMessage` into `metadata.progress_percent` and `metadata.progress_message` verbatim; it parses `stepsResultJson` and puts that same JSON value in `metadata.pipeline_steps` (`lib/pipelines/format.ts:17-32`). The formatter does not synthesize one entry per planned pipeline step (`lib/pipelines/format.ts:17-32`).

For a normal external-API pipeline, each appended step result has `step` (zero-based index), `processor`, `output_format`, and `content_preview` (first 500 characters or null); `extracted_data` is present when defined, and `pipeline_state_snapshot` is optional and appears only when pipeline state is non-empty (`lib/pipelines/engine.ts:213-220,365-373`). No `status`, `state`, per-step duration, start timestamp, or completion timestamp is written on these objects (`lib/pipelines/engine.ts:365-373`). The object is appended only after `runExternalApiProcessor()` resolves, so the in-flight step has no entry yet; an unreached step likewise has no placeholder (`lib/pipelines/engine.ts:358-373`). The array is persisted after each successful processor return (`lib/pipelines/engine.ts:391-394`).

Workflow operations use their own `WorkflowStepResult` entries: `step`, `stepName`, `processor`, and optional `sub_operation_id`, `content_preview`, `extracted_data`, `sub_results`, or `ocr_texts` (`lib/pipelines/workflow-engine.ts:24-33`). Those workflow entries also have no duration/start/end fields in the declared type (`lib/pipelines/workflow-engine.ts:24-33`). Schema-driven HITL workflows can store `stepsResultJson` as `{stepsResult, _nodeResults}` rather than a bare array (`lib/pipelines/workflow-engine.ts:248-260`); the legacy formatter passes the parsed JSON through without normalizing that wrapper (`lib/pipelines/format.ts:23-32`).

## 3. Workflow wait state

When a workflow pauses for human input, `pauseWorkflow()` writes `done: false`, `state: 'WAITING_USER_INPUT'`, the wait message, `currentStep`, and the accumulated step results, but does not write `progressPercent` (`lib/pipelines/workflow-engine.ts:246-268`). It then sends the `PAUSED` webhook (`lib/pipelines/workflow-engine.ts:270-271`); the workflow webhook payload computes `done` as `state === 'SUCCEEDED' || state === 'FAILED'`, so `PAUSED` is not done (`lib/pipelines/workflow-engine.ts:295-304`).

The operation row therefore does **not** remain `RUNNING` while waiting: it is `WAITING_USER_INPUT` with `done: false` (`lib/pipelines/workflow-engine.ts:255-267`). Schema-driven execution returns from the workflow handler immediately after the pause, leaving no worker step executing during the human wait (`lib/workflow-builder/run-schema.ts:50-55`; `lib/pipelines/workflow-engine.ts:431-447`). The percent is frozen at the last value written by `updateProgress()`; `pauseWorkflow()` changes the message but not the percent, and no timed progress update is present in the pause path (`lib/pipelines/workflow-engine.ts:206-214,255-271`). The explicit user-input resume route restores `RUNNING` and sets a resume message without setting percent, so the old percentage remains until workflow code next calls `updateProgress()` (`app/api/v1/operations/[id]/resume/route.ts:83-96`).

While paused, the normal operation formatter therefore returns `done: false` and metadata progress/step results but no terminal `result` envelope (`lib/pipelines/format.ts:20-34,35-51`; `lib/pipelines/workflow-engine.ts:255-267`).

## 4. Retry and recovery visibility

The pipeline queue defaults to three attempts with exponential backoff starting at 5 seconds (`lib/queue/pipeline-queue.ts:25-35`). The worker also configures a 30-second stalled check interval and `maxStalledCount: 2` (`worker.ts:62-71`). On a re-entered `runPipeline()`, the engine reads `operation.currentStep`, restores completed entries before that index from `stepsResultJson`, and begins its loop from `resumeFromStep` (`lib/pipelines/engine.ts:226-249,281-284`). The retry writes the same start formula for that persisted index; it does not reset operation progress to zero unless the current index is zero (`lib/pipelines/engine.ts:229-249,281-298`). The completed results remain in the array and a retry appends after its current step succeeds (`lib/pipelines/engine.ts:231-245,365-394`). Processor errors caught by the engine are recorded as terminal `FAILED` and are not rethrown from that catch (`lib/pipelines/engine.ts:450-480`); the configured attempt/backoff policy applies when the worker processor rejects, while stalled-job recovery is separately bounded by the worker settings (`worker.ts:44-58,62-71`; `lib/queue/pipeline-queue.ts:27-35`).

`/api/internal/recover-stalled` is not a resume route. It selects rows only by `state='RUNNING'`, `done=false`, and old `createdAt` (`app/api/internal/recover-stalled/route.ts:33-41`), then sets `done: true`, `state: 'FAILED'`, and `progressMessage: null` without changing `progressPercent` or re-enqueueing the operation (`app/api/internal/recover-stalled/route.ts:48-69`). The status formatter consequently exposes the previous percent, a null message, and a terminal failed envelope (`lib/pipelines/format.ts:17-32,53-70`). The route does not check BullMQ job state before writing terminal fields; the pipeline worker executes its loop separately (`app/api/internal/recover-stalled/route.ts:35-58`; `lib/pipelines/engine.ts:281-359`).

**MUST-NOT-REPLICATE —** The recover-stalled selector can mark an old `RUNNING`/`done=false` operation `FAILED`/`done=true` without checking whether its BullMQ worker is still executing (`app/api/internal/recover-stalled/route.ts:35-58`; `lib/pipelines/engine.ts:281-359`).

The public cancel route also sets `done: true`, `state: 'CANCELLED'`, and a null progress message for any operation not already done, without cancelling/removing the BullMQ job (`app/api/v1/operations/[id]/cancel/route.ts:32-45`; queue worker continues through `worker.ts:44-58` and pipeline loop `lib/pipelines/engine.ts:281-359`).

**MUST-NOT-REPLICATE —** The public cancel route can expose terminal `CANCELLED`/`done=true` while an already-running pipeline worker continues processing (`app/api/v1/operations/[id]/cancel/route.ts:32-45`; `lib/pipelines/engine.ts:281-359`).

## 5. Rework progress and step data

The public rework operation view constructs `progress: { percent: 0, message: state }` in both the general GET facade and the view loaded by submission (`du-rework/services/orchestrator/src/modules/operations/facade.ts:32-50`; `du-rework/services/orchestrator/src/modules/operations/submission.ts:693-720`). The admin operation-section adapter also defaults missing progress percent to 0 (`du-rework/services/orchestrator/src/app/admin/operation-section-data.ts:930-939`). These are the three percent-zero construction/default points; they are not sourced from current task execution progress (`facade.ts:45`; `submission.ts:715`; `operation-section-data.ts:930-939`).

The compat legacy-envelope adapter passes an optional dispatch result's progress percent/message and defaults them to `0`/`null` when absent (`du-rework/services/orchestrator/src/compat/legacy-action-router.ts:292-312`). The runtime progress endpoint reaches `runtime.reportProgress()` (`du-rework/services/orchestrator/src/server.ts:1638-1642`), where the runtime checks task existence and lease epoch, then performs a second task-id query and discards that result; it does not persist `body.percent` or `body.message` to the operation (`du-rework/services/orchestrator/src/modules/runtime/runtime.ts:483-492`).

On the API-key public branch, operation GET resolves the caller's API key and reads via `getTenantOperation(id, tenantId)` before serializing the operation view (`du-rework/services/orchestrator/src/server.ts:1813-1840`). The route also has a separate admin-principal branch; the progress/status view described here refers to the tenant-fenced API-key branch (`du-rework/services/orchestrator/src/server.ts:1815-1840`).

### Persisted per-step timeline

The rework `operations` row has operation state and timestamps but no progress-percent/message or per-step timeline columns (`du-rework/services/orchestrator/migrations/0001_platform_v1.sql:36-55`). `tasks` stores a task key, state, attempt, lease data, result/error refs, and task-level created/updated timestamps (`:70-91`). `step_checkpoints` stores `task_id`, `step_key`, `generation`, `input_hash`, `output_ref`, `status`, and `created_at`; it has no step index, started time, completed time, or duration (`:101-110`). The migration defines `outbox` dispatch records with delivery/claim/dispatch timestamps and attempts, which are dispatch lifecycle fields rather than per-action-step progress (`:113-125`). A `task_steps` table was **not found** in the rework migrations/source search; the table definitions present for this path are `tasks` and `step_checkpoints` (`0001_platform_v1.sql:70-110`).

**Per-step timeline answer: not found.** Step checkpoint rows can record checkpoint key/status/creation time, but the current operation view and runtime progress path do not project an ordered per-step timeline, and the persisted schemas do not define step start/end/duration fields (`0001_platform_v1.sql:36-55,70-110`; `runtime.ts:483-492`; `facade.ts:32-50`).
