# Legacy Parser and Ingest/Extract Routing Characterization — 2026-10-01

Read-only source characterization. No implementation files or gates were changed, and no tests were run.

## 1. Parser registry and live call sites

### Legacy registry

`ParseResult` exposes `text`, `markdown`, and optional metadata (`pageCount`, `sheetNames`, `wordCount`, and an open-ended metadata map); `DocumentParser` accepts a buffer and filename and returns that result asynchronously (`lib/parsers/interface.ts:1-22`). The factory order is Excel then Word; for dispatch it extracts the suffix after the final dot and lowercases it, calls `canHandle`, and returns `null` if neither parser matches (`lib/parsers/factory.ts:9-33`).

| Parser | Exact `canHandle` test | Notes |
|---|---|---|
| `ExcelParser` | MIME is one of `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, `application/vnd.ms-excel`, `text/csv`, **or** extension is `.xlsx`, `.xls`, `.csv` (`lib/parsers/excel-parser.ts:5-12`). | Tested before Word by the factory (`lib/parsers/factory.ts:9-14`). |
| `WordParser` | MIME is one of `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `application/msword`, **or** extension is `.docx`, `.doc` (`lib/parsers/word-parser.ts:9-15`). | MIME and extension checks are alternatives; the parser itself does not inspect `.docm` as a forbidden extension (`lib/parsers/word-parser.ts:9-15`). |
| PDF | No PDF parser is registered. The source comment says `pdfjs-dist` needs browser canvas APIs unavailable in the Node server and PDFs go directly to the External API connector (`lib/parsers/factory.ts:4-7,9-14`). | No match yields `null`, described by the factory as requiring external API (`lib/parsers/factory.ts:24-32`). |

The factory dispatch is based on declared MIME and/or filename extension; it contains no byte-signature test (`lib/parsers/factory.ts:19-32`). In the common pipeline processor, the call passes an empty MIME string, so that path effectively dispatches on filename extension alone (`lib/pipelines/processors/external-api.ts:35-45`).

### Consumers

The only non-test legacy source call sites found by `rg` are:

1. `runExternalApiProcessor`, reached by the main pipeline engine (`lib/pipelines/processors/external-api.ts:21-25,35-65`; `lib/pipelines/engine.ts:339-360`).
2. The schema-workflow `file_parse` leaf (`lib/workflow-builder/real-exec.ts:97-115`). It passes the file MIME hint and `path.basename(p)` into the factory; a miss is represented as `{status: 'no_parser'}`, while a match reads the path and returns parser `text` and `markdown` (`lib/workflow-builder/real-exec.ts:97-115`).

### Upload mapping that constrains normal pipeline inputs

The default upload allowlist is only `.docx` and `.pdf`; `MIME_MAP` has entries only for those two suffixes (`lib/upload.ts:8-15`). The normal upload validator applies NFC normalization, explicitly rejects `.docm`, checks the allowlist, then checks MIME and the 300 MiB per-file cap (`lib/upload.ts:26-71`); `saveUploadedFile` invokes that validator before storage (`lib/upload-helper.ts:29-38`). Therefore the parser registry's `.xlsx`/`.xls`/`.csv` coverage is wider than the default upload surface. A custom extension allowlist can expose unmapped types, but direct File validation rejects a non-empty MIME when the extension has no MIME-map entry (`lib/upload.ts:38-56`); metadata validation for downloaded files only applies its MIME equality check when a mapped expected MIME exists (`lib/upload.ts:78-106`).

## 2. Legacy parser outputs and failure behavior

### Word

`WordParser` calls `mammoth.extractRawText({buffer})`, then assigns Mammoth's `value` to both `text` and `markdown`; it returns Mammoth `messages` in metadata (`lib/parsers/word-parser.ts:17-34`). It does not return Mammoth HTML or a separate table/image representation: the implementation explicitly says a richer HTML-to-Markdown path is only a possible future option and currently uses raw text (`lib/parsers/word-parser.ts:19-26`). The parser has no size/buffer budget check in its implementation; its catch logs the filename and rethrows parsing errors (`lib/parsers/word-parser.ts:17-38`).

In the main pipeline path, a successful parser result's full `markdown` becomes `ProcessorResult.content`, with `extractedData` unset; the engine persists at most the first 500 characters as `content_preview`, but also assigns the full `result.content` to `currentText` for the next pipeline step and ultimately stores it as `outputContent` (`lib/pipelines/processors/external-api.ts:41-56`; `lib/pipelines/engine.ts:365-373,388-394,399-407`). Thus this path is not preview-only, although the step-result JSON contains a preview rather than the full parse result (`lib/pipelines/engine.ts:365-373`). The separate workflow `file_parse` output includes both complete `text` and `markdown` per file (`lib/workflow-builder/real-exec.ts:111-115`).

If Mammoth rejects a corrupt Word file, the parser rethrows (`lib/parsers/word-parser.ts:35-38`); in the main pipeline, the processor catches that error, logs a warning, and continues into the external connector request (`lib/pipelines/processors/external-api.ts:57-65,68-97`).

### Excel / CSV

`ExcelParser` calls `xlsx.read(buffer, {type:'buffer'})` and iterates every `workbook.SheetNames` entry, not just the first sheet (`lib/parsers/excel-parser.ts:14-24`). For each nonempty sheet it renders a Markdown heading and table, treats row zero as headers (filling missing headers as `Col n`), escapes pipes and line breaks, and also emits tab-separated text (`lib/parsers/excel-parser.ts:26-65`). It returns joined/trimmed `text` and `markdown`, all sheet names, and `totalCells` metadata (`lib/parsers/excel-parser.ts:68-75`). Empty sheets are skipped; an all-empty workbook yields empty text/Markdown with sheet names and zero cells (`lib/parsers/excel-parser.ts:22-27,68-75`). Corrupt XLSX errors from `xlsx.read` or conversion are not caught inside this parser and reject its promise (`lib/parsers/excel-parser.ts:14-76`); the main pipeline processor then catches parser errors and falls through to the connector (`lib/pipelines/processors/external-api.ts:57-65`).

## 3. Main legacy decision path and request modifiers

The runner reads multipart form data, selects a sub-case from the service discriminator, loads its connection list (or profile override), maps those connections into pipeline steps, and submits them (`lib/endpoints/runner.ts:84-123,170-177,209-223`). The runner's file normalizer accepts nonempty `files[]`, `source_file`, `target_file`, and `file` values (`lib/endpoints/runner.ts:36-53`). The engine gives original local files to the first pipeline step only; it invokes the same `runExternalApiProcessor` for each connection step (`lib/pipelines/engine.ts:339-360`).

The processor attempts the internal parser only when `ctx.filePaths.length === 1`; a parser match reads the whole path into a `Buffer`, returns parser Markdown immediately, and skips the external call. No match, multiple files, or a parser error falls through to the external connector (`lib/pipelines/processors/external-api.ts:35-68`). Since `filePaths`/`fileNames` are populated from the persisted file records and `file.type` is recorded separately as MIME, but the processor calls `getParserForFile('', fileName)`, the main pipeline's parser selection depends on that filename extension, not upload MIME (`lib/pipelines/submit.ts:222-230`; `lib/pipelines/engine.ts:177-210`; `lib/pipelines/processors/external-api.ts:36-45`).

For local file uploads, `sync=true` changes the submit path to enqueue and wait for the worker; without it the job is async. The sync wait does not change the parser condition (`lib/endpoints/runner.ts:226-246`; `lib/pipelines/submit.ts:369-390`). `output_format` is copied to the operation and processor context, but the internal parser branch does not read it and always returns parser Markdown as content (`lib/endpoints/runner.ts:226-246`; `lib/pipelines/engine.ts:339-350`; `lib/pipelines/processors/external-api.ts:41-56`).

`file_urls` are separate from uploaded local file paths. If the first connector declares `fileUrlFieldName`, submit stores the URL as a remote reference (`lib/pipelines/submit.ts:251-270`); the engine separates those references into `remoteFileUrls`, not `filePaths` (`lib/pipelines/engine.ts:183-195`). The parser gate therefore does not parse a forwarded URL by itself; after a parser miss, the connector URL field is appended (`lib/pipelines/processors/external-api.ts:102-108`). If forwarding is unavailable, sync submit downloads URLs before queueing, while async submit defers download to the worker (`lib/pipelines/submit.ts:273-292,344-350`; `lib/pipelines/engine.ts:142-161`). The downloader chooses `entry.filename`, then a response Content-Disposition filename, then the URL basename, and normalizes it; the returned name is carried into the engine's `fileNames` (`lib/file-url-downloader.ts:181-192,258-264`; `lib/pipelines/engine.ts:185-210`). Those downloaded file paths can satisfy the same one-file parser gate if there is exactly one eligible file (`lib/pipelines/engine.ts:177-210`; `lib/pipelines/processors/external-api.ts:35-45`). If a request combines one parser-eligible local upload with a forwarded URL, the successful local parse returns before connector form construction, so that URL is not appended on that step (`lib/pipelines/processors/external-api.ts:35-65,102-108`).

## 5. Rework `document-kit` counterpart and delta

### Package capabilities

`@du/document-kit` exports format detection, PDF splitting, ZIP extraction, text/Word/Excel/PDF parsers, parser factory/limits, and text conversion, diff, redaction, template and chunking utilities (`du-rework/packages/document-kit/src/index.ts:5-19`). `SupportedFormat` includes PDF, DOCX/DOC, XLSX/XLS/CSV, TXT/MD, several image formats, ZIP and unknown (`du-rework/packages/document-kit/src/types.ts:5-19`). Its parse result carries text/Markdown, required metadata (detected format, parser, provenance, counts, optional pages/sheets/custom metadata) and warnings (`du-rework/packages/document-kit/src/types.ts:37-51`).

`DocumentFormatDetector` checks PDF/PNG/JPEG/ZIP/TIFF signatures and inspects ZIP root entry names for `word/document.xml` versus `xl/workbook.xml`; it then uses extension/MIME for legacy `.doc`, `.xls`, `.csv`, text/Markdown and WebP fallbacks (`du-rework/packages/document-kit/src/formats/detector.ts:11-79,116-148`). Therefore package dispatch uses bytes/container markers in addition to caller declarations, unlike the legacy parser factory (`lib/parsers/factory.ts:19-32`).

`DocumentParserFactory` registers Text, Word, Excel and PDF parsers (`du-rework/packages/document-kit/src/parsers/factory.ts:11-23`), validates buffer options, and sends built-in parsing through a terminable worker with a default 30-second CPU timeout (`du-rework/packages/document-kit/src/parsers/factory.ts:38-63`; `du-rework/packages/document-kit/src/parsers/worker-isolation.ts:5,82-100,139-163`). Before Office dispatch it preflights ZIPs and requires the DOCX/XLSX root marker when the declaration claims Office (`du-rework/packages/document-kit/src/parsers/factory.ts:93-123`). Archive preflight validates path safety, size/count/ratio bounds, decompression size and CRC (`du-rework/packages/document-kit/src/archives/zip-extractor.ts:121-149,212-270,324-356,527-607,667-690`); default archive caps are 50 MiB expanded, 1,000 entries and a 100:1 ratio (`du-rework/packages/document-kit/src/archives/zip-extractor.ts:64-72`).

The rework Word parser extracts paragraphs and Markdown tables from DOCX OpenXML, returns text/Markdown plus counts/parser/provenance/warnings, and falls back to Mammoth raw text when available (`du-rework/packages/document-kit/src/parsers/word-parser.ts:76-101,104-140,143-229`). It runs archive preflight before OpenXML extraction and does not swallow archive-preflight failures into Mammoth (`du-rework/packages/document-kit/src/parsers/word-parser.ts:56-72,76-83`). The Excel parser uses SheetJS and iterates all workbook sheets (`du-rework/packages/document-kit/src/parsers/excel-parser.ts:105-120,122-178`); its XML fallback reads `sheet1.xml` only (`du-rework/packages/document-kit/src/parsers/excel-parser.ts:184-200`). Its CSV path makes Markdown tables and tab-separated text (`du-rework/packages/document-kit/src/parsers/excel-parser.ts:330-367`); corrupt/unsupported binary input is rejected where detected (`du-rework/packages/document-kit/src/parsers/excel-parser.ts:89-103,203-211`). The package also has a PDF parser, while legacy explicitly excludes one (`du-rework/packages/document-kit/src/parsers/pdf-parser.ts:9-15,58-94`; `lib/parsers/factory.ts:4-14`).

The other exported local utilities are `PdfSplitter` (page-expression parsing and PDF slicing; `du-rework/packages/document-kit/src/formats/pdf-splitter.ts:4-10,145-181`), `FormatConverter` (text/Markdown/HTML/JSON conversion; `du-rework/packages/document-kit/src/converters/format-converter.ts:2-34`), `TextChunker` (bounded text chunks; `du-rework/packages/document-kit/src/converters/text-chunker.ts:1-16`), `DiffEngine` (line diff; `du-rework/packages/document-kit/src/converters/diff-engine.ts:3-9,74-81`), `PiiRedactor` (configured built-in regex patterns; `du-rework/packages/document-kit/src/converters/pii-redactor.ts:9-38,47-69`), and `TemplateEngine` (nested placeholder interpolation; `du-rework/packages/document-kit/src/converters/template-engine.ts:1-24`). These are distinct from automatic format/parser dispatch.

## 6. MUST-NOT-REPLICATE observations

- **Unbounded legacy parser read:** the main processor materializes the whole file with `fsPromises.readFile` before calling Word/Excel and has no parser-local size budget (`lib/pipelines/processors/external-api.ts:35-45`). The schema-workflow `file_parse` leaf does the same (`lib/workflow-builder/real-exec.ts:97-113`). Rework also documents that its artifact facade returns the full buffer before parser size enforcement, so that particular retrieval limitation remains visible there too (`du-rework/businesses/document-core/src/pipelines/parser-budget.ts:7-13,398-407,541-548`).
- **Macro / `.docm` gap:** the normal legacy upload validator explicitly blocks `.docm` (`lib/upload.ts:30-36,78-84`), but Word parser dispatch treats a Word MIME as sufficient even when the filename extension differs (`lib/parsers/word-parser.ts:9-15`), and the schema-workflow consumer forwards `file?.mime` into that check (`lib/workflow-builder/real-exec.ts:103-107`). On rework, the reviewed detector/parser/archive path has no explicit macro or `.docm` rejection; its positive DOCX ZIP identity is based on the `word/document.xml` marker, followed by DOCX preflight (`du-rework/packages/document-kit/src/formats/detector.ts:32-52`; `du-rework/packages/document-kit/src/parsers/factory.ts:93-123`). The presence of a macro-specific exclusion was not found in those reviewed document-kit sources.
- **Unconfined workflow path read:** the standard uploaded filename is reduced to `path.basename`, normalized and stripped of filesystem-dangerous characters before being used below the operation prefix (`lib/upload-helper.ts:12-18,40-48`). Separately, schema-workflow `file_parse` takes `file.path` (or a string) as `p`, uses `path.basename(p)` only as the parser/display name, then reads the original `p` directly (`lib/workflow-builder/real-exec.ts:97-113`). This is an unconfined path-input read in that leaf, not evidence that the normal upload filename is concatenated into a path.
- **Parser-error fallback is not preserved in the result:** the common processor logs a native parse failure and continues with the connector request (`lib/pipelines/processors/external-api.ts:57-65,68-97`); a successful external response is identified as `ext:<connector>` rather than carrying the failed native parser outcome (`lib/pipelines/processors/external-api.ts:206-222`). This is observable in logs but not surfaced as a parse-failed status in that processor result. The separate workflow leaf instead records `status: 'no_parser'` on a no-match (`lib/workflow-builder/real-exec.ts:106-115`).
