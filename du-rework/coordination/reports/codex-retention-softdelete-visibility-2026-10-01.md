# Retention, soft-delete, and post-delete visibility characterization

Read-only source characterization for the COMP-00 retention/soft-delete question. This records code behavior on the legacy and rework sides; it does not choose a retention policy, recommend a TTL, or decide which behavior is correct. No tests were run, no product source was changed, and no gate or COMP row was edited.

## 1. Legacy file cleanup and schedule

`lib/cleanup.ts:17` sets `EXPIRY_MS` to 24 hours. `cleanupExpiredFiles` computes `cutoff = now - EXPIRY_MS` and selects operation rows only when all three predicates hold: `createdAt < cutoff`, `filesDeleted = false`, and `deletedAt IS NULL` (`lib/cleanup.ts:40-54`). The age clock is the operation's creation time, not each file's upload time or last access.

For each eligible operation, the cleanup removes the local `OUTPUT_DIR/<operation-id>` directory if present, removes `outputFilePath` from the active storage backend if set, then processes `filesJson` (`lib/cleanup.ts:59-82`). For each uploaded-file entry it decrements `FileCache.refCount` when `fileCacheId` exists; otherwise it deletes `s3Key` from the backend, or removes the local `path` (`:84-108`). It finally sets `operations.filesDeleted=true` (`:111`). It does not delete the `Operation` row. The log's “Deleted ... operations” wording at `:120-122` counts operations whose files were processed; the code path is file cleanup plus a marker update.

The scheduler is started from `app/layout.tsx:4,44`. `ensureCleanupScheduled` is singleton-guarded, runs both file and cache cleanup once 10 seconds after startup, then every six hours (`lib/cleanup-scheduler.ts:11-33`). There is no separate output-only retention timer: `cleanupExpiredFiles` handles both local output directories / `outputFilePath` and uploaded inputs (`lib/cleanup.ts:61-108`). The scheduler's second cleanup, `cleanupExpiredCache`, is specifically for deduplicated S3 `FileCache` objects and rows: default `s3_cache_ttl_hours` is 168 hours (7 days), and a row is eligible only when `refCount <= 0` and `lastAccessedAt < cutoff` (`lib/cleanup.ts:127-150`).

There are also explicit manual triggers. Admin `DELETE /api/settings/cache?target=outputs` invokes the same `cleanupExpiredFiles` predicate (`app/api/settings/cache/route.ts:65-80`); `target=cache` deletes S3 keys and `FileCache` rows with `refCount <= 0`, or, with `expired=true`, applies the TTL and `lastAccessedAt` condition (`:82-106`). The separate `GET /api/cleanup` invokes only `cleanupExpiredFiles` (`app/api/cleanup/route.ts:1-17`). Neither trigger deletes operation rows.

## 2. Legacy operation DELETE and visibility

`DELETE /api/v1/operations/{id}` reads the row, rejects missing/already-soft-deleted rows, applies the route's optional API-key-id check, and updates only `deletedAt = new Date()` before returning 204 (`app/api/v1/operations/[id]/route.ts:40-64`). The row survives. Its `filesJson`, `outputContent`, `outputFilePath`, `extractedData`, and other payload columns are separate persisted columns (`lib/db/schema.ts:23-28`); DELETE does not clear them or set `filesDeleted`.

Afterward, the public operations list includes `deletedAt IS NULL` in its conditions (`app/api/v1/operations/route.ts:35-38`) and so omits the row. GET detail reads by id but returns 404 if `op.deletedAt` is set (`app/api/v1/operations/[id]/route.ts:14-27`); it does not return a deleted flag. The detail formatter places successful `outputContent` inline and emits `download_url` (`lib/pipelines/format.ts:35-50`), but that URL's download handler also returns 404 when the operation is deleted (`app/api/v1/operations/[id]/download/route.ts:19-27`). No separate legacy `/operations/{id}/result` route was found in the inspected route tree; the inline result is part of operation detail. Thus list/detail result content and the referenced download are not reachable through those public routes after soft-delete, although the database row and its plaintext fields remain. The output download handler serves inline content or a stored output file only after its deleted-row guard (`:37-61`).

**Retained-plaintext observation and cross-side label boundary:** DELETE only flips `deletedAt` (`app/api/v1/operations/[id]/route.ts:62`), while the row retains fields including `outputContent`, `extractedData`, and `stepsResultJson` (`lib/db/schema.ts:25-28`); `filesJson` and `outputFilePath` remain stored references (`:23-26`). More specifically, `cleanupExpiredFiles` requires `deletedAt IS NULL` (`lib/cleanup.ts:50-54`), so a soft-deleted row that still has files (`filesDeleted=false`) is excluded from that scheduled 24-hour input/output cleanup. The public 404 behavior above is not a database scrub. I do not label this a cross-side `MUST-NOT-REPLICATE` mismatch: rework has no DELETE path, and its PostgreSQL blob path stores supplied bytes in `artifact_blobs.bytes` (`services/orchestrator/src/modules/artifacts/artifacts.ts:464-486`; `services/orchestrator/migrations/0003_artifacts_grants.sql:8-13`), so the inspected rework source does not establish a corresponding post-delete purge or universal at-rest plaintext prevention.

## 3. Legacy hard-delete paths found

No operator-facing/admin/internal route or script that hard-deletes an existing `Operation` row was found in the inspected `app/api/internal/**`, `scripts/**`, and operation routes. The public DELETE route is the `deletedAt` update above. The one application-source hard delete of an operation row found by searching `db.delete(operations)` is a compensating rollback when a just-created submission is rejected for queue backpressure (`lib/pipelines/submit.ts:353-365`, specifically `:357-359`); it is not a user/admin delete or retention job.

Legacy admin cleanup can hard-delete file objects, but not operation/artifact metadata rows: `target=outputs` invokes the age/predicate-bounded cleanup for both outputs and uploaded inputs (`app/api/settings/cache/route.ts:73-80`, `lib/cleanup.ts:46-54,61-108`); cache cleanup deletes unreferenced S3 objects and `FileCache` rows (`app/api/settings/cache/route.ts:87-106`). The searched internal CRUD delete handlers target other tables (for example API keys, external connections/overrides, workflow schemas); none found targets `operations` or an operation-owned artifact row. Legacy inputs are represented by `filesJson` and/or `FileCache`, not a distinct artifact table in `lib/db/schema.ts:10-48,150-165`.

## 4. Rework retention, row/blob deletion, and sealed objects

### Operation rows and ordinary sweeps

No operation-row retention/deletion statement or operation DELETE route was found in `services/orchestrator/src/**`. Executable SQL deletes found in the Orchestrator modules target Admin idempotency markers and `artifact_blobs`, not `operations` or `artifacts`; `db/migrations.ts:160` also contains a diagnostic example telling an operator to delete a stale `schema_migrations` ledger row, not an application-issued retention query. The lifecycle deadline sweep updates eligible operation state to `TIMED_OUT` and updates task/wait state (`modules/lifecycle/lifecycle.ts:71-103`); it is not row retention. Runtime lease recovery and queue-integrity sweeps recover/update task and outbox state (`modules/runtime/runtime.ts:1141-1251` and `:1252-1338`), not operation/blob retention. The server's periodic recovery hook defaults to 5 seconds when auto-dispatch is on and calls those sweeps plus the multipart hook (`server.ts:686-696,890-903`); the multipart hook is enabled only when the S3 facade is present (`:577-581`).

One separate, non-operation row purge helper exists: `purgeIdempotencyMarkers(db, olderThanMs)` deletes `admin_idempotency` rows older than its argument (`modules/idempotency/idempotency.ts:155-166`). The source comment expressly says it is **not wired to a timer** (`:155-157`); no caller was found in the orchestrator source. It does not delete operation or artifact rows.

### Artifact/session expiry and object deletion

The artifact schema has a generic `expires_at` column and documents states including `EXPIRED` and `DELETED` (`migrations/0001_platform_v1.sql:128-142`), but the inspected orchestrator source has no transition setting artifact state to either value and no `DELETE FROM artifacts`/`DELETE FROM artifact_multipart_parts` retention query. The artifact service rejects a row already marked `DELETED` during access (`modules/artifacts/artifacts.ts:358-380`); that read guard is not a deletion mechanism.

`packages/contracts/src/version.ts:33-38` declares `RETENTION_DEFAULTS` values for submission keys (30 days), staging artifacts (24 hours), active artifacts (30 days), and usage replay (7 days). A production-source search found no consumer of `RETENTION_DEFAULTS`; these declarations do not themselves schedule or execute deletion. `submission.ts:234,330-332` separately inserts `submission_keys.expires_at` with a default 24-hour idempotency TTL, and its replay lookup filters for `expires_at > now()` (`:680-688`); no source purge for expired submission-key rows was found. The offline `tests/unit/br05-artifact-ttl-quota.functional.test.ts:1-38,88-125` contains an in-memory staging-sweep model, not a service/database sweeper or deployment proof. It is not counted as an implemented cleanup path.

Multipart staging has an actual expiry cleanup, distinct from READY-artifact retention. The outer session TTL is 24 hours (`packages/contracts/src/runtime.ts:277`), with the route configuration accepting `MULTIPART_SESSION_TTL_MS` (`services/orchestrator/src/server.ts:4246-4255`) and the multipart service applying its bounded session policy (`modules/artifacts/multipart-service.ts:224-234`). At the recovery interval, `sweepExpiredSessions` selects only multipart rows (`part_count IS NOT NULL`) that are expired `STAGING`, or `ABORTED` while still carrying a provider upload id (`:864-877`). It changes expired staging rows to `ABORTED` (`:883-900`), deletes a committed version if present and/or aborts the provider multipart upload, then clears `multipart_upload_id` (`:1118-1170`). It does **not** delete the `artifacts` row or `artifact_multipart_parts` ledger; the migration defines the latter with `ON DELETE CASCADE`, so it would be removed only if the artifact row were deleted (`migrations/0015_artifact_multipart.sql:70-76`). The normal abort path is similarly limited to STAGING and leaves the row ABORTED (`multipart-service.ts:1088-1108,1122-1170`). Comments distinguish READY public artifacts as live input that is never purged through this abort path (`:1088-1094`).

Public encrypted single-upload initialization also uses the 24-hour session TTL and refuses an expired session at claim time (`modules/public-api/upload-encryption-gateway.ts:37,337-376,740-799`). The multipart orphan query is explicitly restricted to `part_count IS NOT NULL` (`modules/artifacts/multipart-service.ts:870-874`); the inspected source contains no scheduled garbage collector for expired single-PUT staging rows. A 15-minute artifact grant expiry is separately defined in `modules/artifacts/artifacts.ts:30,120-150`; grant expiry constrains access and does not delete the underlying READY blob. Part URL expiry (`packages/contracts/src/runtime.ts:279`) likewise describes a signed URL, not stored-object retention.

For sealed-at-rest public S3 uploads, the gateway writes AES-GCM ciphertext under the artifact key and a separate crypto-manifest object (`modules/public-api/upload-encryption-gateway.ts:286-303,412-520,613-672`), then records the READY artifact's storage version/hash/size (`:678-688`). The successful READY path does not assign a blob TTL or delete the ciphertext/manifest. `deleteWrittenObjects` deletes those objects on an unsuccessful/rolled-back upload path (`:693-709`), and multipart code deletes unpublished or aborted versions (`modules/artifacts/multipart-service.ts:586-603,645-659,1151-1170`); these are failure/staging cleanup, not post-success retention. The decrypt path reads a stored sealed object when serving a still-authorized artifact (`modules/encryption/artifact-read-decrypt.ts:161-221`; public route: `server.ts:2041-2053`). Encryption is conditional on the configured encrypted-upload path; the public encrypted-upload gateway requires S3 (`upload-encryption-gateway.ts:337-351`), while the PostgreSQL artifact path inserts the supplied bytes into `artifact_blobs.bytes` (`modules/artifacts/artifacts.ts:464-486`; migration `0003_artifacts_grants.sql:8-13`). This is not a claim that every rework artifact is sealed.

PostgreSQL artifact blob migration also retains its legacy bytes as rollback material: the migration module states “Keep artifact_blobs intact” and says not to drop them before verified backup and rollback sign-off (`modules/artifacts/storage-migration.ts:65-70`). Its inventory counts retained/orphan blob rows (`:119-129`); no scheduled migration cleanup was found. No in-repository S3 bucket lifecycle/expiration rule was found in the searched service/configuration sources; the deployment architecture notes production bucket configuration and object-version retention were not yet verified (`infra/deployment-architecture.md:78`), so this source reading does not characterize an external bucket policy.

As an adjacent transient-file lifecycle (not operation rows or published artifact blobs), Worker SDK temp workspaces are removed on scoped cleanup and stale orphan sweep. The worker defaults to a 2-hour stale age and a 30-minute interval with startup pass (`packages/worker-sdk/src/artifact-streams.ts:120-128,207-240`; `packages/worker-sdk/src/worker.ts:124-153,213-252`); the sweep protects active/referenced directories (`artifact-streams.ts:250-277,286-320`). This does not provide an operation/artifact database retention policy.

## 5. Rework DELETE surface and post-delete visibility

The Orchestrator server has no `DELETE` handler for operations or artifacts. Its operation list/detail/result/download routes are GET; cancel and resume are POST (`services/orchestrator/src/server.ts:1776,1813-1841,1925-2000,2010-2084,2087-2108`). The admin action resource is POST-only; GET/PUT/DELETE are rejected with 405 (`modules/admin-actions/rbac.ts:392-400`). Its operation actions include cancel, resume, and deadline sweep (`modules/admin-actions/dispatcher.ts:388-470`), not delete. Multipart abort is a staging-session action, not artifact-row deletion.

Consequently, rework has no post-DELETE state for a tenant to observe. With no DELETE mutation, ordinary records remain readable through the normal fences: API-key operations list/detail are tenant-scoped (`server.ts:1791-1803,1832-1840`); a successful operation result emits its result reference and READY artifact download links (`:1926-1984`); and an artifact download requires the caller tenant, a qualifying successful-operation reference, and `state='READY'` (`:2010-2039`). No deleted flag or deletion-dependent invalidation is applied in these handlers because no operation/artifact DELETE path was found. A rework result reference or download URL therefore is not rendered invalid by a DELETE action in this codebase; there is no such action to invoke.
