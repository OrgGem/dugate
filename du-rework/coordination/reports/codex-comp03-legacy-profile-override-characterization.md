# COMP-03 legacy profile and prompt-override characterization

- Scope: read-only source inspection of the legacy DUGate app (`app/`, `lib/`) and the current rework profile/connector/invocation code. No tests were run; no source, test, docs, or plan files were changed; no gate was changed.
- Path convention: unprefixed paths below are legacy files at `D:\Git\dugate`; `du-rework/...` paths are the rework tree.

## Findings at a glance

Legacy separates three mechanisms that should not be collapsed into one COMP-03 policy:

1. `ProfileEndpoint.parameters` supplies per-key parameter defaults and `isLocked` policy; request fields can replace only unlocked fields.
2. `ExternalApiOverride.promptOverride` is scoped by connection + API key + endpoint + step and outranks the connection's default prompt.
3. Workflow-generated `variables._prompt` (including schema `overrideConnector.prompt` and ProfileEndpoint `_workflowPrompts`) outranks both prompt sources above.

The profile/connector implementation in rework currently pins connector bindings to a key/tenant/action/revision, but does not implement the legacy profile parameter/lock model. It also lacks an explicit COMP-03 rejection test for a caller-supplied prompt override. Details and mismatch evidence follow.

## Effective precedence (lowest to highest)

| Layer | Source and scope | Runtime behavior | Evidence |
|---|---|---|---|

| Stored client/profile prompt override | `ExternalApiOverride.promptOverride`, matched on `connectionId + apiKeyId + endpointSlug + stepId`; `stepId` defaults to `_default` | Replaces connection default. The engine first filters rows by operation `apiKeyId` and `endpointSlug`, then keys them by connection and step. | `lib/db/schema.ts:103-116`; `app/api/internal/ext-overrides/route.ts:61-63,112-123`; `lib/pipelines/engine.ts:271-279,316-322`; resolver `:30-37`. |
| Workflow/code-injected prompt | Per-step `variables._prompt`; may be generated from a workflow profile prompt or node `overrideConnector.prompt` | Highest precedence: a string `_prompt` wins over the stored override and connection default, then `{{variable}}` interpolation runs. | Resolver `lib/pipelines/processors/prompt-resolver.ts:22-37`; schema-node injection `lib/workflow-builder/real-exec.ts:60-68`; ProfileEndpoint `_workflowPrompts` load `lib/pipelines/workflow-engine.ts:356-374`. |

Thus, for the specific row named `ExternalApiOverride`, the requested direction is `connection default -> API-key/endpoint/step scoped prompt override`; do not infer that it outranks workflow-generated `_prompt`. For code-driven workflows, `ProfileEndpoint.parameters._workflowPrompts` is converted into builder prompt input and ultimately `_prompt`, so that path is strongest. `prompt-resolver.ts` documents the same order as code `_prompt` > profile override > connector default.

## Rework comparison and COMP-03 mismatches

| Finding | Rework evidence | COMP-03 consequence |
|---|---|---|
| **MISMATCH - profile field/lock policy is not implemented in the current profile service.** Rework `profiles.ts` validates the slot->{connectorId,revision} map, required business/version/action, and binds the immutable row to the active API key's DB-derived tenant; it does not model legacy `parameters`, `isLocked`/`defaultLocked`, allowed profile fields, file URL policy, or priority. Submission validates the action input schema and resolves/pins a binding, but no legacy profile merge/lock decision is present in that seam. | `du-rework/services/orchestrator/src/modules/profiles/profiles.ts:21-50,65-72,96-129,132-160`; submission calls resolveBinding then validates the manifest input at `du-rework/services/orchestrator/src/modules/operations/submission.ts:182-200`. | COMP-03 must not count JSON input validation or connector binding validation as profile/locked-field enforcement. It needs policy-backed validation on submit plus golden cases for absent/default, unlocked override, locked override (including same-value), unknown field, and disabled action before operation/task/outbox writes. |
| **MISMATCH - prompt-override denial is not proven.** Rework `ProfileSnapshot` still has arbitrary `parameters` plus optional `promptOverrides`; the current profile-binding row/service does not validate either. ## Suggested COMP-03 golden negatives (inventory only)

- Same-value locked field and changed-value locked field both return the chosen legacy-compatible denial wire; assert no operation/task/outbox creation.
- Unlocked profile value can be replaced by allowed request input; absent input preserves profile default.
- Unknown/disabled profile parameter fails closed according to the selected canonical policy rather than being silently accepted/ignored.
- Caller-supplied `promptOverride`, `promptOverrides`, or `_prompt` is explicitly denied at the public compatibility/admission boundary; distinguish it from an action-generated invocation `prompt`.
- Cross-key/profile selector supplied in the body cannot alter authenticated apiKeyId/tenant; file URL auth policy is profile/admin-controlled, and metadata encryption remains platform-injected.
- A scoped stored prompt override cannot bleed across connection, API key, endpoint, or step; include exact `_default` behavior and the workflow `_prompt` higher-precedence case.

This is characterization only. No release gate or plan status was evaluated or changed.
