## 1. Delta from PAR00-MAP and method

PAR00-MAP correctly records M02–M05 as largely unresolved, but its M01 statement that the API-key HTML forms have no mutation handler is stale against the current tree. `POST /admin/api-keys/new` and `POST /admin/api-keys/:id/revoke` are intercepted by `handleAdminMutationPost`, which is called before ordinary section dispatch; when `jsonBaseUrl` configures the Admin action adapter, it posts to the real `POST /api/v1/admin/actions` route. Without that adapter the shell handler returns 503. The JSON resource route `/api/v1/admin/api-keys` itself remains GET-only. Evidence: `shell-router.ts:861-907,890,922-944,1846-1866,1901-1905`; `shell-server.ts:364-377`; `server.ts:2351-2392,2558-2568`.

The API-key renderer comment says the platform already exposes `POST /api/v1/admin/api-keys`, but its form actually posts to `/admin/api-keys/new`; in `server.ts` that API-key resource route matches only GET. `api-key-section-renderer.ts:251-265`; `server.ts:2558-2568`.

PAR00-MAP is an aggregation receipt that explicitly says it did not re-verify source (`coordination/reports/qwen-par00-evidence-map-2026-10-02.md`, sections 1 and 5). This report adds the current UI-to-router trace; it does not replace the earlier cross-journey decisions or the Slice E/G legacy evidence. In particular, Slice G remains the existing source for legacy schema/workflow details; this report only records the rework Admin surface delta.

## 3. Candidate handler specs for actual gaps

The following are implementation-ready *decision packets*, not approved route or DTO contracts. Any path and logical field list is a candidate only; PAR-01 owns API wire freeze, and this task does not freeze one.

### A. Profile draft, profile-value diff, publish

- **Current mismatch:** the visible save button posts only slot fields to `/admin/profiles`; it cannot identify its selected business/version/profile from the POST body, and the route returns 405. The currently visible compare control compares schema shape between business versions, not saved policy revisions (`profile-section-renderer.ts:156-168,328-342,362-409`; `shell-router.ts:1668-1681`).
- **Routing candidate:** retain the current shell form target as an HTML adapter and dispatch a new policy action through the existing `POST /api/v1/admin/actions`, or choose an equivalent route after PAR-01. Draft save, policy-value diff/read, and publish are distinct logical operations; names and URL are unfrozen. Existing dispatcher has no corresponding action (`server.ts:2351-2392`; `dispatcher.ts:95-120`).
- **Logical DTO candidate (unfrozen):** selected business/version/profile reference; action/slot value map; operation intent (draft save or publish); and a revision/precondition token to detect stale edits. Diff read would identify the two saved/draft revisions being compared. Do not send caller-chosen actor, tenant, or API-key identity fields. The business/profile ownership model and tenant source must be decided before freezing these fields.
- **Validation:** registered business/version and action/slot membership; schema type/enum/required rules; reject unknown slots and malformed revision tokens; publish only a validated stored draft. Validation must happen before writes. This needs the COMP-01/02 parameter golden set; do not infer rules from the renderer’s widget projection alone.
- **Auth/fence:** Admin action auth and role check before mutation; scope the target from a server-resolved principal/record. If policy becomes tenant-bound, derive tenant scope from the authenticated server-side identity or stored target and fail closed when absent; never use `tenantId`, `apiKeyId`, or `x-api-key-id` as proof of identity. No role matrix is invented here.
- **Audit/idempotency/errors:** draft save and publish plus audit event in one transaction; use the established idempotency facility and bind a replay key to the canonical request, returning conflict for key reuse with different payload. Candidate error classes: unauthenticated/forbidden, not found, stale revision conflict, schema validation failure, and generic sanitized internal failure. Exact envelope is PAR-01 work.
- **Offline test plan:** save a draft, read it back, diff against an earlier revision, publish and verify the selected revision is what admission reads; invalid slot/enum and stale revision leave storage/audit unchanged; cross-tenant or tenantless principal fails closed; injected audit failure rolls back; same-key replay writes one revision; same key with changed body conflicts; unauthorized request returns 401/403 before writes.
- **Classification:** `BLOCKED-COMP-00` (profile ownership, draft/publish lifecycle, golden behavior) + `BLOCKED-PAR-01` (route/DTO). Request a separate implementation lease only after those decisions and the COMP-01/02 golden inventory are signed.

### Shared credential and tenant invariant

For API-key-authenticated requests, current `resolveApiKey` reads only the presented `x-api-key`, hashes it, resolves an ACTIVE row, returns that row’s tenant, and fails closed without fallback (`server.ts:4182-4198`). The Admin action route separately resolves the authenticated Admin principal before dispatch (`server.ts:2351-2392`). Future work must preserve that distinction: an API-key request resolves its credential server-side and tenant-fences the resolved row; an Admin operation authorizes its Admin principal and then resolves/fences the target resource server-side. Do not use request `apiKeyId`/`x-api-key-id` to select the caller’s identity or tenant, and do not add an ADMIN-key fallback.

### B. Connector create, activate, retire

- **Current mismatch:** current UI supports revision selection, credential rotation and a connector probe; it has no lifecycle affordance. Available dispatcher actions stop at credential rotate/revoke/test, and the server GET pane is an honest disabled placeholder rather than a persisted registry (`connector-section-renderer.ts:137-214`; `dispatcher.ts:95-120,677-768`; `server.ts:2512-2555`).
- **Routing candidate:** lifecycle actions could be added to the existing Admin action dispatcher or exposed by a separately approved route. Candidate verbs are create, activate, retire; route/action names remain unfrozen. Do not treat the stale `connector-bindings` renderer comment as a route (`connector-section-renderer.ts:313-319`).
- **Logical DTO candidate (unfrozen):** connector/revision reference, lifecycle intent, and the configuration reference needed by that lifecycle transition. Credential values remain write-only and are not returned in reads. Whether a connector belongs to this platform registry or another service, and what immutable revision identity means, are COMP-00/COMP-10 questions.
- **Validation:** valid registered connector type and capability set; revision/state preconditions; lifecycle transition allowed by the approved model; credential references validated without echoing credential contents. Unknown/foreign target must not disclose existence beyond the approved tenant policy.
- **Auth/fence:** platform Admin authorization for global registry operations unless Product approves tenant-scoped ownership. If tenant-owned, derive tenant scope server-side and fence every read/write. Do not add client identity selectors or an Admin-token fallback.
- **Audit/idempotency/errors:** persist lifecycle transition and audit atomically; require/replay idempotency through the common action facility. Candidate failures: 401/403, 404, transition conflict, 422 validation, sanitized 503. Do not expose provider response or secret material.
- **Offline test plan:** create revision → read it → activate → test/read readiness → retire → verify retired revision is not treated as active; invalid transitions and foreign target produce zero writes; repeated idempotent transition does not duplicate revision/audit; unauthorized request returns 401/403; secret values never appear in response or error.
- **Classification:** `BLOCKED-COMP-00 + BLOCKED-PAR-01 + COMP-10`. Lease request follows ownership/revision decisions; no source lease requested in this inventory task.

### C. Schema catalog

- **Current mismatch:** no schema Admin section, server route, or dispatcher action is present in the inspected rework surface (`app/admin/types.ts:15-22`; `server.ts:2466-2509`; `dispatcher.ts:95-120`). This report does not repeat Slice G’s legacy schema route inventory.
- **Handler spec boundary:** an eventual catalog needs a read/list projection and separately authorized import/validate/publish/version operations. The logical resource includes the legacy-compatible schema slug and a versioned definition, but exact lifecycle, import format, fields, validation limits, and route are intentionally left open to COMP-09/PAR-01. No route or DTO is proposed as settled.
- **Auth/fence, audit/idempotency, errors/tests:** use the signed Admin principal; derive any tenant ownership from server-side auth or the stored schema record; fail closed on missing scope. Mutations need atomic audit and idempotent replay. Candidate offline coverage: create/import → validate → publish → resolve by slug → submit/use → retire/rollback; malformed schema, duplicate slug, unsupported version, invalid graph and unauthorized/foreign access must not alter the active catalog. Exact cases follow COMP-09 semantics.
- **Classification:** `BLOCKED-COMP-00 + BLOCKED-PAR-01 + COMP-09`. The absence of a renderer means this is not currently a dead button, but it remains a named scope gap in the requested inventory.

### D. Copy-once acknowledgement

- **Current mismatch:** renderer submits an acknowledgement form, but no route/action handles it; it reaches the section POST 405. Separately, issue POST already returns the raw key in a one-time HTML response, while the subsequent API-key GET hardcodes `createCopyOnce: null` (`api-key-section-renderer.ts:138-167`; `shell-router.ts:861-872,1668-1681`; `server.ts:2558-2564,4094-4098`).
- **Candidate only:** if acknowledgement is a browser presentation event, it may be local to the one-time response and require no server mutation; if a server transition is required, the rendered `/admin/api-keys/{id}/acknowledge` is only a candidate shell path, and the handler must not store or re-emit raw key material. That decision is open; do not implement a durable ack record based solely on the current renderer.
- **Auth/CSRF/validation:** any server-side POST would need an authenticated Admin session, CSRF proof, and a server-resolved pending window associated with the resource; no caller field may choose an identity. Current form has no CSRF input. Do not persist a raw key or make it retrievable after acknowledgement.
- **Candidate errors/tests:** unauthorized 401/403 and invalid/expired one-time window return a sanitized response; test the issue response once, acknowledge/consume, then verify reload/replay cannot reveal the key, plus CSRF rejection and no secret in logs/errors. Whether that test is meaningful depends on whether the platform chooses a server-side acknowledgement at all.
- **Classification:** `BLOCKED-COMP-00 + BLOCKED-PAR-01` pending product decision on presentation versus persisted state. No handler lease requested until then.

### E. User/key assignment

- **Current mismatch:** display-only key grants are profile bindings by business/version/action, while no local-user-to-key assignment affordance or dispatcher action was found. The existing `profile-bindings` route is not a local-user assignment handler (`api-key-section-renderer.ts:193-220`; `api-key-section-data.ts:75-80`; `server.ts:2200-2268`; `dispatcher.ts:483-538`).
- **Handler spec boundary:** first decide whether PAR-05 means binding a key to business/action (already has a module route) or assigning a local user to a key (not represented in this Admin UI and dependent on LOCAL-00/05). Do not freeze a new endpoint or DTO before that is answered. For any future key-scoped operation, authenticate through the presented credential and `resolveApiKey` plus tenant fencing; never select actor/tenant by caller-supplied `apiKeyId`/`x-api-key-id`, and never fall back to an ADMIN key. The existing profile-binding target pattern using request `body.apiKey` is recorded above as `MUST-NOT-REPLICATE` for new identity resolution.
- **Candidate test plan:** if the scope is user assignment, create/resolve an approved user and key under a tenant, assign, verify allowed use, revoke assignment, verify denied use (401/403 per approved auth contract); unknown user/key and cross-tenant attempts reveal no foreign data; audit is atomic; repeated mutation is idempotent; unauthorized caller produces 401 before writes. Those expected semantics require LOCAL-00/PAR-01 decisions.
- **Classification:** current key→profile binding backend is `READY-MODULE`, but UI editing is absent; user→key assignment is `BLOCKED-COMP-00 + BLOCKED-PAR-01 + LOCAL-00/05` until product defines that concept.
