## Fixture and assertion set for WFA-02

- Named happy paths: three distinct real process fixtures, including `resolution_data=review rules v1` for disbursement; inspect the persisted business/action and root payload to prove no alias to another action.
- Named errors: missing selector, whitespace selector, unknown selector, no file, zero-byte file, and mismatched body `apiKeyId`; assert no operation/outbox/task/artifact publication on pre-admission rejection. One-file `doc-compare` is a distinct asynchronous worker-failure case and must not be tightened to a pre-admission 400.
- Schema happy paths: one input-only schema with no files and one file-backed schema; assert `schemaSlug` trimming, normalized file roles, tenant/schema/revision/digest snapshot, exact 202 header and schema-specific initial metadata.
- Schema errors: missing/unknown slug, invalid stored schema, malformed JSON, non-object JSON, oversized multipart, and no-file schema requiring a file; assert no partial admission on rejection.
- Lifecycle: retrieve each admitted operation through `/api/v1/operations/{id}` and observe real terminal output; exercise a schema `human` node through resume, and cancel a running operation through the existing cancel route.
- Replay: repeat each old workflow request (with and without an `Idempotency-Key`) and assert two new operations, since the legacy workflow handlers did not consume that header.

## WFA-03 interface handoff

Runtime owner proposed and API owner accepts `LegacyWorkflowSchemaPin = { tenantId, slug, revision, digest, schema }` and `resolveLegacyWorkflowSchema(db, { tenantId, slug, revision? })`. For schema admission, API will pass a separate typed workflow snapshot to `SubmitContext`; the submission service must persist it transactionally as the task payload envelope:

```ts
{
  input: {
    variables: Record<string, unknown>,
    artifactIds: string[],
    fileNames: string[],
    artifacts: Array<{ artifactId: string; role: string }>
  },
  legacyWorkflowSchema: LegacyWorkflowSchemaPin
}
```

The schema runner receives `input.variables` as legacy `$input.*` values, and the worker reads only the pinned schema snapshot. The frozen action routes are `document-core/disbursement`, `lc-checker/lc-checker`, `document-core/doc-compare`, and `document-core/schema-workflow`; each uses the registered root handler. The pin is part of the normalized internal request hash and is persisted in the encrypted root-task payload. The public legacy routes intentionally do not pass Idempotency-Key to admission, so every accepted request creates a fresh operation.

## Findings to keep open

- `doc-compare` request admission accepts one normalized file, while its worker fails asynchronously unless at least two exist. This is an explicit parity requirement, not a request to report successful comparison; the HTTP route keeps the old 202 behavior and the worker must carry the terminal failure.
- Schema input previously accepted any JSON value through parsing, while the task explicitly requires object validation. Rejection of array/scalar/null is an intentional hardening exception.
- Old schema lookup was global and mutable and the worker re-read by slug. Tenant-scoped immutable revisions change persistence semantics by design; the admission pin must be proven in runtime tests.
- Old workflow routes allowed selecting an arbitrary API key/profile and used ADMIN fallback. Those insecure identity behaviors are explicitly excluded from parity.
- The old named handlers include parallel provider steps, output/progress persistence and (for disbursement) HITL. The LC legacy OCR→prompt→report flow differs from the new rule-set checker and requires an explicit compatibility branch under the frozen action. Schema node semantics and safe adapters remain runtime-owned and are not proven by this API inventory.
