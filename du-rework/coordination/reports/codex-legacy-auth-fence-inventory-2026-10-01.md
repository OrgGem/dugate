# COMP-00 input: legacy auth and tenant-fence inventory

**Review mode:** read-only source inventory, 2026-10-01. This documents current behavior and defects to avoid; it is not an implementation proposal. No source, test, or gate file was changed.

## Classification

- **HARDENING-CORRECT-IN-REWORK** — a legacy control has a safe property that the rework also enforces.
- **MUST-NOT-REPLICATE** — the legacy behavior omits or weakens authentication, authorization, or tenant scoping.
- **NEEDS-COMP-00-DECISION** — the source shows a contract or role-scope choice that is not inferable from the implementation alone.

## Cross-cutting observations

- Legacy `lib/rbac.ts:9-15` defines `isAdmin` separately, but the analytics route uses the broader `canMutate`; the route therefore treats `USER` as authorized for a global aggregate read. Operation routes do not consult `x-user-role` or RBAC at all.
- Legacy profile-oriented internal routes may receive a client-selected `apiKeyId`, but `requireProfileAccess` checks the authenticated session’s assignment before proceeding. The internal test-profile route also checks this guard before injecting the selected ID into its runner request. `app/api/internal/profile-endpoints/route.ts:21-34,113-120`; `app/api/internal/test-profile-endpoint/route.ts:18-31,61-64`; `lib/auth-guard.ts:45-70`. That scoped internal resource selection is distinct from accepting `x-api-key-id` as a public API credential.
- `app/api/internal/auth-key/route.ts:35-47` hashes the presented raw key, checks active status, and returns the resolved ID. It is a separate key-validation endpoint; it does not make arbitrary `x-api-key-id` headers trustworthy.
- **Constraint for any compatibility note:** a key identity must be resolved server-side from a presented credential using the `resolveApiKey`-style hash lookup. A caller-supplied `x-api-key-id`/form ID, implicit admin-key fallback, or unfenced read is not a credential or authorization proof.

## COMP-00 decision inputs

1. Whether browser-session and anonymous no-key docs submission are intentional legacy contracts; the rework public submit path requires an active API key.
2. Which internal handlers are intended for `ADMIN`, tenant-scoped operators, or any signed-in user. Current legacy routes mix these checks and include gaps documented above.
3. Whether the visible distinction between raw credential resolution and profile-ID selection remains relevant to compatibility. The source has both patterns; only the former is a public credential resolve.

**Disposition:** read-only inventory complete. No source, test, or gate files were modified; no gate was ticked.
