# J01–J03 legacy/rework auth, API-key, and profile-policy characterization

**Scope:** read-only source comparison of the J01/J02/J03 claims in `coordination/reports/qwen-admin.md` §66.2–66.4. No tests were run; this is a route/source inventory, not deployment evidence or a gate decision. No source, test, plan, or gate files were changed.

## Findings in brief

- **J01 — partly present, not a drop-in identity match.** Legacy Admin login is NextAuth Credentials/OIDC, with a JWT session carrying the database user's `id`, `username`, and `role`. `GET /api/internal/auth-key` is not an Admin login: it validates an API-key secret and returns the database-resolved `apiKeyId`. Rework has a real OIDC flow and opaque server-side sessions, but also accepts the shared `adminToken` at `POST /admin/login` and mints an `admin` role cookie from it. Therefore the §66 fixture “prove `ADMIN_TOKEN` does not become local identity” is **not satisfied by the current local-token path**; retain it as a MUST-NOT-REPLICATE/cutover requirement. OIDC persistence is Redis-backed only when selected/configured; source presence alone is not two-replica deployment proof.
- **J02 — control-plane create/revoke is present; Admin HTML parity is not.** Legacy POST creates a server-generated raw key, stores only SHA-256, and returns raw once; PUT rotates; DELETE hard-deletes. Rework has HTTP-reachable `apikey.issue`/`apikey.revoke` actions and GET list/detail. But `apikey.issue` accepts a caller-supplied raw key rather than generating one, there is no `apikey.rotate` or `apikey.activate` action, and the Admin HTML create/revoke forms have no matching mutation handlers. The renderer comment claiming a `POST /api/v1/admin/api-keys` route is stale: the server route at that path is GET-only.
- **J03 — narrow profile-binding parity, not legacy policy/override parity.** Rework supports immutable API-key/business/version/action revisions with connector revision pins and a manifest-driven profile editor. It does not model the legacy per-user API-key assignments or per-key/per-endpoint `parameters`, `isLocked/defaultLocked`, `connectionsOverride`, `jobPriority`, `fileUrlAuthConfig`, `allowedFileExtensions`, or per-connection/endpoint/step prompt overrides. Section 66 is right to keep J03 cutover-required, but `apikey.bind-profile` must not be counted as equivalent to the legacy policy/override surface.

### Identity and fallback behaviors that must not be replicated

1. **Do not treat request fields as caller identity.** Legacy `apiKeyId`/`userId` values in query/body/form select a target resource; the authorization principal still comes from `getServerSession`, and profile access compares DB assignment against `session.user.id` (`auth-guard.ts:45-70`). Preserve the fence and add negative fixtures for foreign/unassigned IDs. The test endpoint's injected `x-user-id` is session-derived only after that guard (`test-profile-endpoint/route.ts:28-32,61-64`).
2. **Do not accept `x-api-key-id` as an authentication substitute.** Legacy `/auth-key` resolves its response ID from the key hash; rework public API resolution similarly requires an `x-api-key`, hashes it, and requires ACTIVE status (`server.ts:4183-4193`). Missing credential must deny, never become an unscoped/default identity.
3. **Do not turn a shared admin bootstrap token into a per-person local identity or infer role from a caller label.** Current rework local login does exactly mint an admin-role cookie from `adminToken` (`shell-router.ts:519-540,1029-1124`); if retained for bootstrap, keep it isolated as a service/admin credential and do not count it as a human identity plane. OIDC role mapping must remain claim-derived/default-deny.
4. **Do not let an absent/invalid session or tenant fence fall through to admin.** Legacy Admin guards require a session and exact ADMIN role. Rework `du_session` invalid/dead resolution denies without `du_admin` resurrection (`rbac.ts:341-379`); operator actions require server-held tenant (`dispatcher.ts:203-216`). Keep these as explicit negative fixtures.
