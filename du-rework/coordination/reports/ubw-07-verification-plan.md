# UBW-07-PRE — Independent Functional and E2E Verification Plan

## Purpose and evidence boundary

This report turns Section 6 of `coordination/PLAN-UI-BUSINESS-WORKFLOW-2026-10-08.md` into an independent verification strategy for UBW-02 through UBW-06. It is a plan only: no product/test files were changed, no build or test was run, no database was started, and no gate was ticked.

The plan distinguishes implementation evidence from verification evidence. The canonical plan defines `VERIFIED` for an independent run with literal output and exit code, and explicitly says the current static/offline gate does not prove browser/runtime behavior (`PLAN-UI-BUSINESS-WORKFLOW-2026-10-08.md:93`). Section 6 separately requires real HTTP/BFF and worker/queue evidence; client stubs or element-tree checks do not satisfy it (`:97-105`). Report offline/unit, disposable integration, and browser E2E results separately. A green unit suite must never be presented as proof of the full functional path.

Inputs read: the canonical plan and its Section 6 acceptance matrix, `reports/ubw-00-inventory.md`, `reports/ubw-01-ui-design.md`, `reports/ubw-02-registration.md`, `reports/ubw-03-catalog-ui.md`, `reports/ubw-04-workflow-contract.md`, and `reports/ubw-06-profile-binding.md`.

The browser harness therefore needs a separate test-only setup and an exact lease before implementation.

## Independent verification model

The verifier should derive expected outcomes from this matrix and the accepted contracts, then exercise public HTTP/BFF and browser behavior. Do not import product-private functions as the sole oracle, reuse implementer assertions as proof, or accept snapshots of component trees as live verification. Read-only SQL against the disposable test database and Redis queue inspection may supplement API assertions to prove persistence and absence of side effects.

Use three evidence layers:

1. **Offline contract and unit checks.** Strict DTO/parser and digest tests; SDK call-order, retry, and cleanup tests; graph and adapter validation tests; BFF allowlist/RBAC/method tests; deterministic UI state/component tests. These are useful, but each report must label them offline.
2. **Disposable service integration.** Start a fresh PostgreSQL 16 database and Redis, apply the complete migration set from the tested tree, and run the actual Orchestrator HTTP routes, BFF, worker SDK, and queue consumer. Keep all data disposable. Use a private internal network with no egress and no published host ports; run the harness/browser inside that network. Do not read `.env.live`, connect to a live/legacy service, or use production credentials.
3. **Browser E2E.** Serve the built Admin Web artifact and exercise real session cookies, BFF routes, API responses, and rendered controls in a browser. Use server fixtures and controlled responses only for states that cannot be induced reliably; such a state simulation proves UI rendering, not server authorization or backend conflict behavior. The happy-path business/workflow run must use the real disposable API, database, Redis queue, and SDK worker.

Pin the supported Node runtime from the package engines, record the exact runtime and container image versions, and apply migrations from an empty disposable database. Use deterministic fixture IDs/names scoped to a run ID, generated test-only identities, and deterministic action handlers. External paid providers are out of scope: the plan explicitly allows a mock only at the external transport boundary and separates paid-provider/deployment/cutover work (`PLAN-UI-BUSINESS-WORKFLOW-2026-10-08.md:105`). Keep the actual queue, worker, admission, and snapshot path real.

For the no-rebuild assertion, build Admin Web once before the test, record the built asset manifest/SHA-256 set and running image/build digest, then register a new valid business/action through the runtime API. Re-fetch the catalog and verify the new action renders from the stored manifest while the Admin Web artifact digest remains unchanged. Do not invoke a frontend build between registration and catalog read.

The workflow gate remains a hard prerequisite. While `Δ-DEV-03` is closed, test direct API and BFF attempts and confirm the server rejects them before workflow/adapter reads or operation creation. Run positive workflow and adapter scenarios only after an explicit authorized gate opening is provided and represented by the real server-side gate. Do not invent an environment override or bypass the gate in the browser. If no authority or supported test fixture exists, mark positive workflow/adapter E2E **SKIPPED — gate closed**, not passed (`ubw-04-workflow-contract.md:7-14,367-379`; `ubw-06-profile-binding.md:194,209-222`).

Run this matrix against the browser and real BFF for HTTP/auth behavior. A separate UI-only test may inject a response to make an otherwise rare state deterministic, but the receipt must label it UI simulation and must not count it as BFF or server proof. Apply the cases to Workers, Businesses/version detail, Processes, Workflows, Workflow adapters, and Runs wherever that screen/feature exists.

## Execution order and result rules

Run only after the corresponding slice is reported implemented and its exact migration/API contracts are frozen. Recommended order: offline contracts and SDK/BFF/UI tests; fresh-database migration and service integration; startup/catalog/process path; authorized workflow graph path; profile adapter admission/staleness; browser states; then the complete regression suite. The full end-to-end run should use the same working-tree revision throughout and record the revision, dirty diff hash, Node version, image digests, migration head, artifact digests, fixture IDs, exact command, literal suite/test summary, exit code, and raw stdout/stderr for each command. Store the future raw logs under `coordination/reports/raw/ubw-07/<run-id>/`. Redact credentials while preserving sentinel checks.

Use only these result labels:

- **PASS** — assertion observed through the layer named in the case, with the corresponding evidence captured.
- **FAIL** — behavior differs from the expected outcome; preserve the first literal failure and raw log. Do not rerun just to obtain a green result.
- **SKIPPED** — a named prerequisite is unavailable (for example a slice not implemented or `Δ-DEV-03` not explicitly opened); state the reason and owner. Never count skipped as pass.
- **BLOCKED** — the isolated harness cannot start or its infrastructure fails before the product assertion; preserve the logs and identify the blocking condition.
- **NOT RUN** — not attempted.

Report offline `jest.unit.config.cjs`, disposable database/Redis integration, and browser E2E in separate rows. A skipped `migrations.test.ts` under the offline Jest config is not a migration pass. Do not run or claim a production/legacy DB window. No result from this pre-plan changes `IMPLEMENTED`, `VERIFIED`, or `ACCEPTED`; a later independent verifier and coordinator must apply the repository’s gate process.

## Harness readiness gaps and handoff

- UBW-02’s persistent worker registry/read API must exist before real worker list/heartbeat assertions can run. The current stub cannot satisfy W07-S1-01/04/05.
- UBW-03’s BFF catalog/detail mappings and Admin Web screens must exist before W07-S2 and the catalog UI state cases can run.
- UBW-04 process binding, graph storage/validator, executor, and public run admission must be implemented and accepted before W07-S3/S4 positive cases. The closed-gate denial tests can run earlier once a real server gate exists.
- UBW-06 adapter API/store/admission integration and shared action-schema digest contract must be accepted before W07-S5. Until then stale-profile tests can test contract validators only, not live admission.
- The browser runner and isolated multi-service orchestration need a test-only package/config lease. The current Admin Web package has no test/browser runner; do not call component-level tests “E2E.”
- The plan’s worker-startup inventory found no production business `startWorker()` callsite outside the SDK (`ubw-02-registration.md`, source audit). Include a newly approved test fixture worker in the harness, but do not claim that it verifies an undiscovered production entrypoint.
- User/coordinator authorization to open `Δ-DEV-03` and unresolved operation wait/resume semantics are explicit prerequisites. Missing authority or semantics yields a named SKIPPED subcase, not a harness override or inferred pass.

This report defines verification work only. It does not certify implementation, browser behavior, database behavior, deployment readiness, or any gate.
