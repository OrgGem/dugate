# J04 External-Connection Capability Inventory

Read-only source characterization for ORCH-PAR-00 section 66. Scope is legacy `ExternalApiConnection` CRUD/test/invocation versus the current rework Orchestrator/Connector/Vault surfaces. No source or test files were changed; no tests/deployment were run; no gate was ticked.

## Finding

The section 66 claim is **accurate when scoped to the legacy connection resource**: the rework Orchestrator has no Admin create/list/detail/update/activate/retire/disable/delete proxy for an `ExternalApiConnection`-equivalent resource. Its `connectors` module is only a health probe; profiles persist connector ID/revision bindings; the admin-action connector verbs cover credential rotation, credential revocation, and a probe. The Admin connector revision GET is explicitly a synthetic placeholder, not a resource read.

Precision: the rework **Connector service itself** does expose connector-revision create/activate/retire/disable/test and invocation HTTP routes. Those are downstream service/revision capabilities, not an Orchestrator Admin proxy for the legacy endpoint URL/auth/prompt/response/session configuration. Likewise, Orchestrator credential rotation creates and activates a credential revision through an injected workflow; it does not create or activate the connection resource. Do not count either a profile binding or the health proxy as J04 lifecycle parity.

The legacy repository uses a Drizzle model in `lib/db/schema.ts`; I found no `schema.prisma`. The `authSecret` column is plain `text`; the ext-connections create/update paths insert the supplied trimmed value directly and do not call the AES helper. The API masks it on list/write responses, but that is not at-rest encryption. Secret storage/rotation is therefore a **SEC/Vault** responsibility in the rework, not an Orchestrator-local encryption implementation.

## Legacy model and secret boundary

`lib/db/schema.ts:72-98` defines `ExternalApiConnection` (Drizzle): identity/name/slug/description; `endpointUrl`, `httpMethod`; `authType`, `authKeyHeader`, `authSecret`; prompt/file field names and `defaultPrompt`; static form fields/extra headers; `responseContentPath`; session response path and request field; timeout; state. There are **no tenant/account columns** on this resource. `ExternalApiOverride` separately keys overrides by connection, API key, endpoint slug, and step (`lib/db/schema.ts:103-117`).

Session chaining is field-based: `sessionIdResponsePath` extracts a returned string into pipeline state, and `sessionIdFieldName` injects the saved ID into a later multipart request (`lib/pipelines/processors/external-api.ts:110-116,173-180`). `responseContentPath` selects provider output (`:164-180`; the legacy test route independently maps the dot path at `app/api/internal/ext-connections/[id]/test/route.ts:123-142`).

The `authSecret` treatment is materially different from rework Vault references: schema `text` at `lib/db/schema.ts:81`; raw trimmed insert/update at `app/api/internal/ext-connections/route.ts:93-112` and `[id]/route.ts:52-76`; direct use in provider headers at `lib/pipelines/processors/external-api.ts:119-126`. The AES-GCM helper exists at `lib/crypto.ts:23-35`, and selected AppSetting values are encrypted in `lib/settings.ts:148-151`, but the ext-connection code path does not use it. No claim is made here about underlying database/disk encryption.

Rework credential workflow instead accepts a write-only value, writes it through the Vault writer, pins a Vault version to a connector revision, and returns masked metadata (`du-rework/services/orchestrator/src/modules/connector-credentials/workflow.ts:11-30,163-198,271-349,411-433`). Its binding is derived from stored revision/platform configuration (`:200-268`); a request must not establish tenant/account trust. That is Vault/SEC credential lifecycle evidence, not an Orchestrator encryption primitive.

## Authorization and proxy boundary

- Legacy collection GET uses `requireAuth` (any signed-in role) while POST/PUT/DELETE use `requireAdmin` in `lib/auth-guard.ts:17-36` and the route lines above. `lib/rbac.ts:25-33` is the same ADMIN-only helper, but the ext-connections routes import `auth-guard.ts`.
- The legacy `/[id]/test` route has no `requireAuth`/`requireAdmin` call (imports at lines 5-9; handler starts line 11). That is a legacy exposure to characterize, not a behavior to preserve.
- Rework admin action principal types resolve platform bearer vs tenant operator from the credential (`du-rework/services/orchestrator/src/modules/admin-actions/rbac.ts:18-40`). `du-rework/services/orchestrator/src/modules/admin-actions/dispatcher.ts:114-120` allows connector rotate/revoke/test only to platform bearer and admin cookie; tenant operators are excluded. Cookie mutations use the CSRF gate in `rbac.ts:103-139`; dispatcher action authorization is centralized around `:244-309`.
- `du-rework/services/orchestrator/src/server.ts:2277-2311` mounts only credential GET/POST and returns 503 if `credentialWorkflow` is not injected (`:2286-2288`); action dispatch is mounted at `:2351-2388`. The connector base URL is platform configuration (`:265,593-597`), and the health probe is not a caller-selected arbitrary URL.
- Connector-service HTTP does contain lower-layer revision lifecycle (`services/connector/src/http/server.ts:155-188,190-271`) and invocation (`:303-311`). The Orchestrator's GET revision envelope explicitly says the platform has no connector registry/lifecycle (`services/orchestrator/src/server.ts:2512-2555`). These layers must not be conflated.

## Cutover fixture classes / sizing

The repository has offline/local credential workflow harnesses (for example `du-rework/services/orchestrator/tests/connector-revision-http-offline.functional.test.ts` and `du-rework/services/orchestrator/tests/mock-vault-harness-offline.functional.test.ts`). They support seam behavior only. This inventory did not run those tests or verify a container deployment, so neither is represented as production cutover proof.
