# LDBA-01 — Adapter bridge architecture decision

- Date: 2026-10-09
- Decision state: architecture decided; follow-up packets remain blocked by the conditions below.
- Scope: static design for `du-rework`; this ADR changes no implementation, migration, test, plan, or other documentation.
- Evidence baseline: LDBA-00 is treated as **VERIFIED** per dispatch and user direction. Its seven plan/code discrepancies are real and accepted as findings, not disputed. Mapping excerpts are in `coordination/reports/ldba-00-schema-mapping.md:20-193`.
- D1 is preserved: A1 view/read-and-compare first, then A2 backfill/cutover. No reconsideration of D1.

## 1. A1 view bridge and A2 backfill

### A1 — read-only name and shape bridge

The legacy Drizzle declarations use PascalCase names such as `Operation` and `ApiKey`; PostgreSQL treats these as quoted identifiers. The rework baseline creates the separate lowercase table `operations` at `orchestrator/services/orchestrator/migrations/0001_platform_v1.sql:36-56`. Therefore the plan example that creates an unqualified view named `operations` is unsafe in a schema where migration 0001 has already created that table: it would collide with the table name. A view does not rename or replace the legacy table. Evidence: `lib/db/schema.ts:10-64`; LDBA-00 `:20-61,177-179`.

**Decision:** create only fully qualified views in a dedicated `ldba_bridge` schema, using source-oriented names such as `ldba_bridge.operation_v1`, `ldba_bridge.api_key_v1`, and `ldba_bridge.profile_endpoint_v1`. Do not create a view named `operations`, do not change `search_path`, and do not put the bridge schema in the legacy app role search path. Before creating it, the rehearsal owner must prove that the schema and view names are unused and that the legacy app role cannot resolve or write through them. This removes the `operations` collision while preserving both the quoted legacy table and the lowercase rework table.

The views expose every source row without filtering or deduplication. They alias source fields to a stable bridge contract and retain raw values for fields requiring conversion. Unsafe casts and JSON parsing happen in a dry-run transformer over the view rows, which records a failure code per row and field rather than aborting a whole count or silently substituting null. Derived fields such as tenant key and endpoint-to-business/action mapping must be explicit; a missing mapping is a reported failure, never a guessed value. The complete source inventory is the nine-table mapping in LDBA-00 `:20-158`.

A1 is read-only with respect to source data and target data. It uses a separate read-only analysis role with SELECT only, no DML grants, no write trigger, and no `INSTEAD OF` trigger. Creating a view still changes the database catalog, so A1 requires a separately authorized rehearsal lease and catalog snapshot. The old app keeps its existing tables, role, connection string, and `search_path`. The A1 owner records the source snapshot identifier and the per-table evidence described below. This design follows the read-only/no-trigger rule in `0001_platform_v1.sql:36` and the A1 finding in LDBA-00 `:177-179`.

**Measurable A1 exit criteria:**

1. For each of the nine source tables, `source_count = bridge_view_count` under the same consistent snapshot. The views must not filter rows.
2. For every target mapping, the dry-run transformer reports `expected_target_count` by destination and source table. One-to-one mappings must have equal source and projected-target counts. Split mappings must report the exact per-destination cardinality from their documented rule; workflow duplicate-slug selection must report `winner_count + excluded_duplicate_count = source_count` and list every excluded slug. A1 does not insert these rows.
3. All conversion and referential checks report zero failures: invalid UUIDs, malformed JSON, unsupported enum/state values, unresolved tenant or business/action mappings, normalized username collisions, non-null invalid encrypted-field encodings, missing referenced rows, and unaccounted source fields. Intentional exclusions must have an approved disposition and be counted separately; no silent skip is allowed.
4. The report contains source count, view count, projected count, excluded count, and failure count for every mapping. Each `source_count = bridge_view_count`; each projected count is reproducible from the frozen snapshot and the approved transform rules.
5. The catalog and access check proves no source row was written, the legacy app search path and grants were unchanged, and the legacy app did not resolve a bridge object. Any unresolved precondition or non-zero count above keeps A1 open.

### A2 — idempotent backfill and cutover

A2 begins only after A1 satisfies every exit criterion and its report is reviewed. Before A2, require an approved migration/cutover scope, a separately approved maintenance window, a restorable backup, a rollback runbook, and a frozen source snapshot. Stop the legacy app and all writers before the final snapshot. Apply only the reviewed additive target migrations, then backfill from the frozen source into the rework tables. Never update or delete legacy rows.

The backfill is deterministic and re-runnable. Preserve valid legacy UUID values by parsing and casting them; preserve Connector text identifiers as text. Where a genuinely new UUID is required for a derived row, use UUIDv5 with a fixed namespace and the canonical tuple `source-table/source-primary-key/destination-role`; never generate a fresh random UUID on retry. For each natural key, a retry may insert the identical canonical row or confirm that an existing row has the same canonical digest; a conflicting row with different content is a hard stop, not an overwrite. Emit a report with source/projected/inserted/already-present/failed counts, FK and constraint results, and the exact pending-password-reset count.

**Measurable A2 exit criteria before cutover:** actual destination row counts equal A1 projected counts for every destination; every source row is either represented or covered by an approved, counted exclusion; parse, mapping, FK, uniqueness, and target CHECK failures are zero; rerun produces zero changed rows and zero duplicate rows; all imported tenant references match the table-specific target type; all operation and API-key monetary values reconcile in USD units; all secrets and workflow schema envelopes satisfy their storage contract. Do not route production traffic to rework until these checks and the cutover owner sign-off pass.

**Stop and rollback:** stop A1 immediately on any view/source name collision, app search-path/grant impact, source write, legacy-app error attributable to the bridge, parse/mapping failure, or source/view count mismatch. Revoke the analysis role and, under the rehearsal lease, remove only the bridge views/schema; A1 has changed no source rows. Stop A2 on any source writer still active, missing approval/backup, non-zero transform failure, target constraint failure, count mismatch, or non-identical retry conflict. Before rework accepts writes, rollback is to route back to the unchanged legacy app/database and leave the rework tables quarantined for diagnosis. After rework accepts writes, pointing back to the old app would lose those new writes; rollback then requires a separately approved lossless reconciliation/replay plan. A2 is one-way and has no automatic down-migration, consistent with the plan and `0024` contract noted at `PLAN-LEGACY-DB-ADAPTER-2026-10-09.md:148-168`.

**No direct A2 jump is permitted.** If the dedicated A1 view cannot be created or read safely, stop and resolve that blocker. A2 is not a fallback for an infeasible A1. Only a new explicit user decision could replace A1 with a different verification mechanism; that would still be an A1-equivalent gate, not a bypass to A2.

## 2. Disposition of the seven verified plan/code discrepancies

Do not add or cast tenant columns just to satisfy the disproved wording. ## 4. Gate conditions for LDBA-02 through LDBA-06

These are implementation blockers, not gate ticks. The plan permits LDBA-02 to author an additive migration file, but forbids running it against any database; actual execution belongs to a separate packet after LDBA-07 rehearsal and the stopped-app/rollback conditions. The plan also requires explicit user confirmation before an owner writes a migration onto the legacy database: `PLAN-LEGACY-DB-ADAPTER-2026-10-09.md:257-261,265-269`. This ADR authorizes no database operation.

| Packet | Must be true before implementation can be accepted or run |
|---|---|
| LDBA-02 — additive migrations | The consumer inventory must decide every proposed field; L3 callback semantics and L6 limits/timestamp policy must be resolved first. The migration proposal must preserve the real tenant types and absent-column cases in §2, must not create duplicate `webhook_url` without the separate decision, and must document table/constraint/index effects. Any migration against a legacy database waits for explicit user scope approval, an authorized window, and backup. The `0001` name collision must be avoided by the A1 schema-qualified alias, not by renaming the legacy table. |
