## 1. Shared legacy result and materialization

All 31 registered cases pass through the same operation formatter. A successful response has top-level `name`, `done`, and `metadata` (`state`, `pipeline`, `current_step`, progress fields, times, and `pipeline_steps`); `result` has `output_format`, `content`, `extracted_data`, `pipeline_steps`, `usage`, and `download_url` (`lib/pipelines/format.ts:17-50`). The failure branch returns `error` with `code`, `message`, and `failed_step`; if steps were recorded it also includes partial `pipeline_steps` and `usage` (`lib/pipelines/format.ts:53-68`). This shared envelope is the `L1` cell used in every core row below.

For core pipeline execution, the connector receives `operation.outputFormat`; each step record stores that value and a `content_preview` capped at 500 characters plus `extracted_data` (`lib/pipelines/engine.ts:339-356,365-373`). The next-step text is the connector's `content`, or JSON-stringified `extractedData` when `content` is absent (`lib/pipelines/engine.ts:388-394`). On success the engine writes `outputContent`, the last step's `extractedData`, and `stepsResultJson` to the operation (`lib/pipelines/engine.ts:397-414`). The formatter exposes a common `/api/v1/operations/{id}/download` URL; the engine's success update shown here does not set `outputFilePath` (`lib/pipelines/format.ts:35-50`; `lib/pipelines/engine.ts:397-407`). No per-variant file name or distinct file output is declared in these paths.

`output_format` registry parameters are `md`, `json`, `html`, or `csv`, default `json` (`lib/endpoints/registry.ts:39-40`). Only `ingest:parse`, `transform:convert`, `compare:diff`, and `compare:version` declare that parameter on their case (`registry.ts:76-81,244-250,344-350,361-368`). Other cases have no case-level `output_format` entry; the engine still passes and records the operation's stored format, and the common formatter echoes it (`lib/pipelines/engine.ts:349,365-370`; `lib/pipelines/format.ts:35-40`). The table distinguishes the per-case registry declaration from that shared operation field.

The worker call order for each core action is `executeRecipe` → `validateResult` → `formatResult` → write a JSON result artifact (`worker.ts:1261-1390`). The exact inner fields emitted by each action's `formatResult` are outside this slice's permitted source list; the recorded facts below distinguish the validator's provider-output shape from the manifest envelope schema.

`writeEnvelopeArtifact` JSON-serializes the formatted envelope, writes `application/json` with purpose `output`, and returns an artifact reference (`worker.ts:105-124`). The six handlers name these artifacts `ingest_result.json`, `extract_result.json`, `analyze_result.json`, `transform_result.json`, `generate_result.json`, and `compare_result.json` and return `artifact://…` references (`worker.ts:1261-1390`). `GET /api/v1/operations/{id}/result` projects the operation's opaque `result_ref` under `data.resultRef`, plus READY artifact metadata and artifact download links; it does not inline the artifact bytes (`services/orchestrator/src/server.ts:1917-1924,1926-1937,1966-1999`). `GET /api/v1/artifacts/{id}/download` serves the artifact bytes; with delivery encryption enabled it returns an encrypted JSON body, and without it streams bytes with the stored MIME type (`server.ts:2003-2083`).
