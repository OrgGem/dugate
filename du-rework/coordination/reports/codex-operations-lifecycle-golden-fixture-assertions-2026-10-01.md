# Operations lifecycle + list — golden-fixture assertion spec

**This is an executable golden-fixture SPEC, not a live-verified observation.** It is based on code reading only; no tests or live requests were run. At the time this was written, neither `127.0.0.1:2023` nor `127.0.0.1:3000` was reachable. The tables below define fixture assertions for a future harness and do not claim that either service currently passes them. They are intentionally the action/state assertion set, not a duplicate of the parallel lane's lifecycle response-shape matrix.

## Fixture and authentication discipline

For rework public-route fixtures, send only a valid raw API-key credential and seed an `ACTIVE` API-key row with its SHA-256 hash; `resolveApiKey` derives the tenant and key id by hashing the raw credential and looking up that active row (`du-rework/services/orchestrator/src/server.ts:4182-4194`). Do not use caller-supplied key-id or user-id headers as identity. The legacy operation handlers conditionally scope by the request's `x-api-key-id`, but do not resolve the raw API key themselves (`app/api/v1/operations/route.ts:35-38`; `app/api/v1/operations/[id]/route.ts:29-35`; `app/api/v1/operations/[id]/cancel/route.ts:24-30`; `app/api/v1/operations/[id]/download/route.ts:29-35`). The middleware removes inbound identity headers and injects session-derived values (`middleware.ts:32-52`); with no injected key id these route-level fences are absent. Treat this legacy optional-header behavior as a security defect, not as a fixture technique or parity target.

State pairs below are semantic fixture classes, not a claim that the state names are identical. Legacy uses `PENDING`, `RUNNING`, `WAITING_USER_INPUT`, `SUCCEEDED`, and `FAILED`; rework uses its contract state vocabulary. Rework public expectations below use API-key auth, not the separate admin-bearer path (which intentionally has a platform-principal cross-tenant read path: `server.ts:1777-1803,1815-1830`). All non-mutating actions leave the seeded state unchanged unless the assertion explicitly says otherwise.

## Pagination token assertion

| Side | More pages exist | List exhausted | Evidence |
|---|---|---|---|
| Legacy | `next_page_token` is a string equal to the id of the last item returned on this page; the query probes `page_size + 1` and uses the extra row to decide `hasMore`. | `next_page_token` is JSON `null`. | `app/api/v1/operations/route.ts:31-33,58-64,93-99,127-130`. |
| Rework | There is **no `next_page_token` field**. The response field is `nextCursor`, an opaque cursor string emitted only when the `limit + 1` probe finds another row. | `nextCursor: null`. The envelope also requires nullable `prevCursor`, numeric `total`, and `limit`. | `server.ts:3373-3390,3423-3431`; cursor encoding `server.ts:2959-2967`; contract `packages/contracts/src/public-api.ts:237-261`. |

The two names and token meanings are not interchangeable: legacy exposes the last operation id; rework exposes an encoded keyset position tied to sort/boundary. A parity fixture must assert each implementation's own field, not invent a rework `next_page_token` or require the legacy route to emit `nextCursor`.

## Negative assertions / must-not-replicate cases

1. **Cancel after terminal:** no state transition is allowed. Legacy returns 409 `Already Completed` when the row is consistently `done: true` (`cancel/route.ts:32-37`). Rework intentionally replays terminal cancellation with 200 and `replayed: true`, but must leave the terminal state unchanged (`lifecycle.ts:37-40`; `server.ts:2091-2094`). Assert unchanged state, not a new success transition. Legacy also checks `done`, not the state machine; if a terminal-state row is inconsistent with `done: false`, the handler can overwrite it to `CANCELLED` (`cancel/route.ts:32-43`) — **MUST-NOT-REPLICATE**.
2. **Download before ready/success:** legacy operation download returns 409 `Not Ready` unless `done && SUCCEEDED` (`download/route.ts:37-42`). Rework result returns 409 for non-success and 410 for `TIMED_OUT` (`server.ts:1931-1937`; `facade.ts:87-99`). At the artifact URL, use a fixture where the tenant-owned artifact is otherwise eligible for publication but its artifact state is not `READY`; the explicit state guard returns 409 `STATE_CONFLICT`. If it is not an eligible/visible artifact at all, the query returns 404 instead (`server.ts:2013-2039`). Neither path mutates operation state.
3. **Resume an already-finished operation:** legacy returns 400 with `{ error }`; rework returns 409 `STATE_CONFLICT`; state remains terminal (`resume/route.ts:31-33`; `runtime.ts:1022-1032`). Rework contract terminal states are `SUCCEEDED`, `FAILED`, `CANCELLED`, and `TIMED_OUT` (`operations.ts:29-37`). Do not create a synthetic `CANCELLED` fixture to manufacture this case: use a genuine successful or failed terminal fixture, or a cancellation produced by an independently valid lifecycle path after the direct-transition discrepancy is resolved.
4. **Cross-tenant read by operation id:** legacy's detail route returns 200 when its optional middleware-derived key-id is absent; list also omits the filter in that case. These are **MUST-NOT-REPLICATE** unauthenticated/unfenced behaviors (`[id]/route.ts:20-37`; list `route.ts:35-38,66-94`; middleware `32-52`). Rework's public API-key detail returns the same 404 for missing and foreign ids; the list SQL is tenant-filtered (`runtime.ts:1336-1340`; `server.ts:1791-1803,1832-1841`). This assertion is specifically for the public API-key path; admin-bearer behavior is a separate principal-authorized route.
5. **Direct terminal cancellation:** do not assert `RUNNING -> CANCELLED` or `WAITING_INPUT -> CANCELLED` as a legal edge. The contract allows a cancellation request state first and only then terminal cancellation (`operations.ts:73-94`), while the legacy route writes `CANCELLED` directly (`cancel/route.ts:39-45`) and the current rework lifecycle service also writes it directly (`lifecycle.ts:42-45`). Preserve the source-level response facts above, but leave the legal post-action assertion **UNRESOLVED** pending resolution of that implementation/contract mismatch; no synthetic terminal state is to be introduced to paper over it.
