# Legacy External-API Step Call Wire

All paths below are relative to the repository root. This is a source characterization of the legacy external-API processor and the rework connector contract; no source or gate state was changed, and no tests were run.

## 1. Legacy request composition

The pipeline loads each step's `ExternalApiConnection` by processor slug, makes the original files and remote file URLs available only to step zero, and passes the previous step's output as `inputText` to later steps (`lib/pipelines/engine.ts:264-269,307-359`). Before making an HTTP call, a single-file step can be handled by the internal parser; a successful native parse returns immediately without calling the configured endpoint (`lib/pipelines/processors/external-api.ts:35-66`).

When the external request is made, its body is a `FormData` multipart body; the processor does not manually set a `Content-Type` header (`lib/pipelines/processors/external-api.ts:68-81,119-134`; `lib/pipelines/processors/http-client.ts:147-153`). The endpoint and method come from `connection.endpointUrl` and `connection.httpMethod` (`lib/db/schema.ts:77-80`; `lib/pipelines/processors/external-api.ts:136-157`).

| Form part | Exact field name / value | Conditions and wire form |
|---|---|---|
| Prompt | `connection.promptFieldName`; resolved prompt string | Always appended before other parts (`lib/pipelines/processors/external-api.ts:68-71`). `_prompt` string wins, then a nonblank profile `promptOverride`, then `defaultPrompt`; the selected template is interpolated with step variables (`lib/pipelines/processors/prompt-resolver.ts:21-38`). Object variable values become JSON strings and other values use `String(value)` (`lib/pipelines/processors/prompt-resolver.ts:10-18`). |
| Configured static fields | Each configured `field.key` and `field.value` | `staticFormFields` is parsed as an array of `{key,value}` and appended as text parts; invalid JSON is logged and skipped (`lib/pipelines/processors/external-api.ts:72-81`). Per-step `_staticFormFields` can replace the connection value before the processor call (`lib/pipelines/engine.ts:324-328`). |
| Local files | `connection.fileFieldName`; Blob bytes with the supplied filename (or `file_i`) | Each local path is stat'ed, opened as a Blob, and appended as a multipart file part (`lib/pipelines/processors/external-api.ts:83-97`). The engine supplies original files only to step zero (`lib/pipelines/engine.ts:339-346`). |
| Chained inline text | Literal field name `input_content`; current step text | Added only when there are no local file paths and `ctx.inputText` is truthy (`lib/pipelines/processors/external-api.ts:98-100`). The engine also places prior output into `variables.input_content` for prompt interpolation (`lib/pipelines/engine.ts:300-305`). |
| Remote file URL | `connection.fileUrlFieldName`; each original URL string | Appended as a text part when URLs exist and this field is configured; this branch forwards URL strings rather than attaching downloaded bytes (`lib/pipelines/processors/external-api.ts:102-108`). The engine supplies these URLs only on step zero (`lib/pipelines/engine.ts:339-346`). |
| Chained session | `ctx.injectSession`, else `connection.sessionIdFieldName`; value from `pipelineState.session_id` | Appended as a text part only when both the selected field and prior state value are truthy (`lib/pipelines/processors/external-api.ts:110-117`). This is not a cookie or an HTTP session header. |

The engine can override `_extraHeaders`, `_responseContentPath`, and a positive `_timeoutSec` per step before the call (`lib/pipelines/engine.ts:329-338`). There is no automatic `pages`, `output_format`, or `language` part in the processor's form-building code; such names can only appear through configured static fields or the configured prompt/session/file fields (`lib/pipelines/processors/external-api.ts:68-117`). Prompt resolution still occurs before the internal parser shortcut, but a successful shortcut sends no prompt or file to the remote connection (`lib/pipelines/processors/external-api.ts:28-33,35-66`).

## 2. Legacy authentication matrix

`authType` is a free-text, non-null database column with default `API_KEY_HEADER`; this schema column does not declare an enum/check constraint (`lib/db/schema.ts:77-81`). The processor has exactly two explicit `authType` branches (`lib/pipelines/processors/external-api.ts:119-126`):

| `authType` value | Injected header | Notes |
|---|---|---|
| `API_KEY_HEADER` | Header named by `authKeyHeader` (default `x-api-key`) with `authSecret` as its value | The name/default and secret columns are declared at `lib/db/schema.ts:79-81`; injection is at `lib/pipelines/processors/external-api.ts:122-124`. |
| `BEARER` | `Authorization: Bearer <authSecret>` | `lib/pipelines/processors/external-api.ts:124-126`. |
| Any other string | No `authType`-driven credential header | There is no `else` branch after the two explicit values (`lib/pipelines/processors/external-api.ts:122-126`). |

The processor starts with `Accept: application/json`; parsed `extraHeaders` are merged afterward and can replace an existing header, including the configured auth header (`lib/pipelines/processors/external-api.ts:119-134`). Invalid `extraHeaders` JSON is skipped (`lib/pipelines/processors/external-api.ts:128-133`). The processor does not append `authSecret` to the endpoint query: it places the secret in a header for the two recognized auth modes, and passes the endpoint URL separately to validation and fetch (`lib/pipelines/processors/external-api.ts:120-157`).

There is no local credential preflight that suppresses the body. The prompt/static/file/text/URL/session parts are composed before the auth headers, then the request is made; if the remote target rejects credentials, the already-sent request receives a non-2xx response which the HTTP client throws (`lib/pipelines/processors/external-api.ts:68-157`; `lib/pipelines/processors/http-client.ts:148-158`). An unrecognized `authType` likewise does not prevent the request; it simply contributes no auth header (`lib/pipelines/processors/external-api.ts:119-157`).

## 3. Legacy response parsing

**Response parsing is legacy orchestrator-side.** `runExternalApiProcessor` calls `fetchWithTimeout`, receives parsed JSON, chooses `connection.responseContentPath ?? 'content'`, and calls `extractContent` in the orchestrator processor (`lib/pipelines/processors/external-api.ts:149-168`). The parser traverses a dot-separated path by successive property access; a missing/null intermediate yields `undefined` (`lib/pipelines/processors/response-parser.ts:8-17`). A string leaf is returned directly, a non-null non-string leaf is `JSON.stringify`'d, and a missing path invokes the warning callback then stringifies the entire response object (`lib/pipelines/processors/response-parser.ts:23-38`). The engine may replace `responseContentPath` from a step's `_responseContentPath` variable before the call (`lib/pipelines/engine.ts:332-334`).

The HTTP wrapper rejects non-2xx status and includes at most the first 500 response-text characters in its error (`lib/pipelines/processors/http-client.ts:155-158`). For successful status it requires a content type containing `application/json`; otherwise it throws with at most the first 200 text characters, so HTML/non-JSON is not parsed as content (`lib/pipelines/processors/http-client.ts:160-168`). A successful JSON content type with an empty or malformed body fails at `response.json()` and is propagated (`lib/pipelines/processors/http-client.ts:168-174`).

After extraction, the processor returns the full extracted content and explicitly sets `extractedData: undefined` (`lib/pipelines/processors/external-api.ts:213-222`). The engine stores at most the first 500 characters as `content_preview`, records the `extracted_data` property from that result, and records a snapshot of `pipelineState` when nonempty (`lib/pipelines/engine.ts:365-373`). The external processor's only automatic response state capture is a configured dot path (`ctx.captureSession` or `sessionIdResponsePath`) whose nonempty string value is stored as `pipelineState.session_id`; missing or non-string values only warn (`lib/pipelines/processors/external-api.ts:173-185`). The HTTP wrapper returns only `response.json()` to the processor, so this path does not capture cookies or other response headers (`lib/pipelines/processors/http-client.ts:160-168`; `lib/pipelines/processors/external-api.ts:173-185`).

The step result therefore has no parsed `extracted_data` from this processor; when the pipeline completes, the operation's top-level `extractedData` is set to JSON for a truthy last-step extracted value or `null` (`lib/pipelines/engine.ts:399-407`).

## 4. Legacy error and retry wire

The processor wraps URL validation errors as `External API URL rejected: <message>` and HTTP/client failures as `Connection Error to <slug>: <message>` (`lib/pipelines/processors/external-api.ts:136-161`). The HTTP client throws for non-2xx responses, non-JSON content types, JSON parse failures, network errors, and timeouts; abort timeout is rendered as `External API timeout after <seconds>s` (`lib/pipelines/processors/http-client.ts:155-174`). Content-path misses are not thrown; they log and fall back to stringifying the response (`lib/pipelines/processors/external-api.ts:164-168`; `lib/pipelines/processors/response-parser.ts:28-37`). A native parser failure is caught and logged, then falls through to the external API request rather than failing the step (`lib/pipelines/processors/external-api.ts:57-65`). Invalid static-fields/extra-headers JSON is also skipped rather than failing the step (`lib/pipelines/processors/external-api.ts:72-81,128-133`).

The engine catches processor errors, marks the operation `done: true`, `state: 'FAILED'`, sets `errorCode: 'PIPELINE_ERROR'`, stores the caught message in `errorMessage`, and does not rethrow from that catch (`lib/pipelines/engine.ts:450-465`). Thus a remote HTTP status is not persisted as the operation's `errorCode`; it is embedded in the `errorMessage` string under the generic pipeline code (`lib/pipelines/processors/http-client.ts:155-158`; `lib/pipelines/processors/external-api.ts:158-161`; `lib/pipelines/engine.ts:450-465`).

The processor issues one `fetchWithTimeout` call and has no processor-level retry loop (`lib/pipelines/processors/external-api.ts:149-162`). BullMQ's pipeline queue is configured for three attempts with exponential backoff starting at 5 seconds (`lib/queue/pipeline-queue.ts:25-35`), but errors caught and converted into a normal return by the engine's catch do not reject that job for BullMQ retry (`lib/pipelines/engine.ts:450-481`).

## 5. SSRF, egress, timeout, and size behavior

The external processor calls its local `assertSafeUrl` before `fetchWithTimeout` (`lib/pipelines/processors/external-api.ts:136-157`). The helper accepts only HTTP(S), rejects `localhost` and IPs matching its explicit private-address regex list, checks a single resolved address against that same list, and fails closed for DNS lookup errors (`lib/pipelines/processors/http-client.ts:43-71,82-130`). This is the listed pattern set, not a general check of every reserved address range (`lib/pipelines/processors/http-client.ts:43-63`). Its local Docker-host rewrite and `ALLOWED_PRIVATE_HOSTS` list bypass the normal private-host/DNS path (`lib/pipelines/processors/http-client.ts:96-111`). DNS is checked with one ordinary lookup, then a separate global `fetch` is used (`lib/pipelines/processors/http-client.ts:113-130,147-153`). The fetch options do not set `redirect`, so native fetch redirect behavior is used and the redirect destination is not passed back through `assertSafeUrl` (`lib/pipelines/processors/http-client.ts:137-153`). The prior egress inventory records this exact legacy external-API path as a redirect-to-private-address gap and separately identifies the one-answer DNS check/TOCTOU and private-host bypasses (`du-rework/coordination/reports/codex-egress-url-guard-inventory-2026-10-01.md:28-31`).

The timeout is `connection.timeoutSec * 1000`; schema default is 60 seconds, and the engine accepts a positive per-step `_timeoutSec` override (`lib/db/schema.ts:91`; `lib/pipelines/engine.ts:335-338`; `lib/pipelines/processors/external-api.ts:149-157`). This wrapper has no explicit request or response byte limit: it submits the multipart `FormData`, reads non-2xx text before truncating only the error string, and calls `response.json()` on the successful body (`lib/pipelines/processors/http-client.ts:137-168`). File stat size is logged but not compared with a processor limit (`lib/pipelines/processors/external-api.ts:87-93`).

The egress inventory describes rework's guarded connector-provider transport as using provider URL validation and pinned fetch in normal composition, and distinguishes that from the legacy external-API processor (`du-rework/coordination/reports/codex-egress-url-guard-inventory-2026-10-01.md:37-39,55-57`). The rework connector management module examined below is a separate readiness probe, not that action/provider transport (`du-rework/services/orchestrator/src/modules/connectors/connectors.ts:3-10,49-66`).

## 6. Rework connector contract and comparison

An action manifest connector slot has `name`, `required`, `acceptedCapabilities`, and optional `allowedModelOptions` and `promptConfigSchema` (`du-rework/packages/contracts/src/manifest.ts:14-21`). The runtime contract represents pinned connector bindings as `slot → connectorId@revision` (`du-rework/packages/contracts/src/runtime.ts:59-66`).

The connector invocation contract documents `POST /internal/v1/invocations` (`du-rework/packages/contracts/src/connector.ts:3-5`). Its JSON request schema contains `contractVersion`, `invocationId`, `grant`, `operationId`, `taskId`, `stepKey`, `bindingSlot`, `input`, optional `options` and `sessionRef`, and `deadlineAt` (`du-rework/packages/contracts/src/connector.ts:73-88`). Input can carry prompt/text/task/language, bounded artifact content, or output schema (`du-rework/packages/contracts/src/connector.ts:42-62`); the signed grant claims bind tenant, operation/task/step, invocation, input hash, connector revision, binding slot, expiry, and related artifact/model constraints (`du-rework/packages/contracts/src/connector.ts:127-169`). The DTO places `grant` in the body; these contract schemas do not specify an HTTP authentication header (`du-rework/packages/contracts/src/connector.ts:73-88,127-151`).

Within the allowed orchestrator `modules/connectors/**` source, the only live HTTP request is the management/readiness probe: a bare `GET {configured base}/health/ready` with no auth or caller headers and no request body; it consumes the response body without parsing it and decides health from status 200 (`du-rework/services/orchestrator/src/modules/connectors/connectors.ts:3-21,42-66`). That module does not contain the invocation POST call site. The contract establishes the invocation endpoint and DTO, but the actual production transport/auth-header wiring is **not found in the allowed source paths** (`du-rework/services/orchestrator/src/modules/connectors/connectors.ts:3-10,42-66`; `du-rework/packages/contracts/src/connector.ts:3-5,73-88`).

The connector response DTO is an `InvocationResponse` with `invocationId`, state, optional normalized `result` (`content`, `data`, artifact references, `sessionRef`), usage, provider request id, error `{code,message,retryable,retryAfterMs}`, and `nextPollAt` (`du-rework/packages/contracts/src/connector.ts:90-125`). The allowed orchestrator proxy does not parse this action response; it only checks readiness status (`du-rework/services/orchestrator/src/modules/connectors/connectors.ts:63-67`). The action-provider response parser implementation/owner is **not found in the allowed paths**; the contract specifies the result wire shape but does not itself prove where provider-specific parsing occurs (`du-rework/packages/contracts/src/connector.ts:99-125`; `du-rework/services/orchestrator/src/modules/connectors/connectors.ts:3-10,63-67`). This is distinct from the legacy path, whose provider JSON parsing is explicitly performed by the orchestrator at `lib/pipelines/processors/external-api.ts:149-168` and `lib/pipelines/processors/response-parser.ts:8-38`.

| Wire dimension | Legacy `ExternalApiConnection` step | Rework connector action path in the allowed source |
|---|---|---|
| 1. Request composition | Configured multipart form; dynamic prompt field, binary file part, optional inline text, static fields, remote URL fields, and session field (`lib/pipelines/processors/external-api.ts:68-117`). | Action slot/capability binding in manifest; invocation is a JSON DTO with `input`, `options`, binding and operation/task identifiers, grant, optional session reference, and deadline (`du-rework/packages/contracts/src/manifest.ts:14-21`; `du-rework/packages/contracts/src/connector.ts:73-88`). No invocation POST caller is present in the allowed orchestrator connector module (`du-rework/services/orchestrator/src/modules/connectors/connectors.ts:3-10,42-66`). |
| 2. Authentication | Recognized `API_KEY_HEADER` and `BEARER` modes inject configured secret in a header; extra headers merge afterward (`lib/pipelines/processors/external-api.ts:119-134`). | Invocation DTO carries a signed `grant` body property and bound claims; a transport auth-header name/wiring is not specified by the allowed contract/module (`du-rework/packages/contracts/src/connector.ts:73-88,127-151`; `du-rework/services/orchestrator/src/modules/connectors/connectors.ts:55-62`). |
| 3. Response parsing | Orchestrator parses JSON and applies configured dotted response-content path (`lib/pipelines/processors/external-api.ts:149-168`; `lib/pipelines/processors/response-parser.ts:8-38`). | Wire contract returns normalized result fields, but provider parser implementation/owner is not found in the allowed paths; the only module HTTP response parsing is status-only for the health probe (`du-rework/packages/contracts/src/connector.ts:99-125`; `du-rework/services/orchestrator/src/modules/connectors/connectors.ts:63-67`). |
| 4. Errors/retry | HTTP/client failures become a `Connection Error…` message and then generic `PIPELINE_ERROR`; engine catches without rethrowing. Queue has three configured attempts, but this caught path does not reject the job (`lib/pipelines/processors/external-api.ts:158-161`; `lib/pipelines/engine.ts:450-465`; `lib/queue/pipeline-queue.ts:25-35`). | Response DTO exposes state plus structured error code/message/retryability/retry-after fields; invocation transport retry count/backoff is not specified by the allowed DTO or connector probe module (`du-rework/packages/contracts/src/connector.ts:107-125`; `du-rework/services/orchestrator/src/modules/connectors/connectors.ts:42-82`). |

## MUST-NOT-REPLICATE observations

- **Raw remote URL forwarding:** when `fileUrlFieldName` is configured, the processor appends client-provided remote URLs directly to a downstream request (`lib/pipelines/processors/external-api.ts:102-107`). The egress inventory records that this branch bypasses the local file URL download guard (`du-rework/coordination/reports/codex-egress-url-guard-inventory-2026-10-01.md:29-31`).
- **Redirect and DNS gaps in external target validation:** validation and fetch are separate, DNS checks one address, private-target exceptions exist, and the subsequent global fetch does not recheck redirects (`lib/pipelines/processors/http-client.ts:96-130,147-153`; `lib/pipelines/processors/external-api.ts:136-157`; `du-rework/coordination/reports/codex-egress-url-guard-inventory-2026-10-01.md:28-30`).
- **Credential in configured endpoint query:** the processor does not put `authSecret` in the URL, but it logs the complete validated endpoint URL verbatim; therefore a secret already embedded in `endpointUrl` query parameters is exposed in that log (`lib/pipelines/processors/external-api.ts:77,120-126,139,146-147`; `lib/pipelines/processors/http-client.ts:13-24,36-37`).
