## 2. Credential lifecycle and security observations

- Legacy API keys are generated as a `dg_` prefix plus random bytes and persisted as a lowercase hex SHA-256 digest (`app/api/internal/apikeys/route.ts:48-55`, `:80-90`; unique `keyHash` column `lib/db/schema.ts:53-67`). The plaintext is returned by create/rotate only; GET does not select it, and hashing is one-way (`app/api/internal/apikeys/route.ts:20-30`, `:48-55`, `:92-96`). Rotate replaces the digest for the existing key ID (`:48-55`).
- The key schema contains `status`, `spendingLimit`, and `totalUsed` (`lib/db/schema.ts:53-64`). `GET /api/internal/auth-key` hashes the presented `x-api-key`, checks `status === "active"`, and returns `{ valid:true, apiKeyId }`; missing/invalid keys return `401`, inactive returns `403`, rate limit returns `429` (`app/api/internal/auth-key/route.ts:11-27`, `:30-50`). This route is a **test/validation** endpoint, not a rotation endpoint; rotation is the Admin `PUT /api/internal/apikeys` branch (`app/api/internal/apikeys/route.ts:38-55`).
- The submit path compares the stored `spendingLimit` and `totalUsed` and returns `402` once the configured limit is reached (`lib/pipelines/submit.ts:149-172`). The route's PUT update destructures only `id`, `note`, and `action`, so it has no status/limit mutation operation (`app/api/internal/apikeys/route.ts:42-45`). The runner's raw-key lookup selects by `keyHash` without a status predicate (`lib/endpoints/runner.ts:88-109`); the active-status check is visible in the separate `/auth-key` validation route, not this resolution step.
- The `/auth-key` rate-limit key is derived from the first 16 characters of caller-supplied `x-api-key` (`app/api/internal/auth-key/route.ts:12-18`). **MUST-NOT-REPLICATE** (`app/api/internal/auth-key/route.ts:15-18`).
- The UI and handlers use client-selected `apiKeyId` as the profile target in profile/override reads and writes (`app/profiles/page.tsx:226`, `:994-1029`; `app/api/internal/profile-endpoints/route.ts:19-28`, `:110-120`; `app/api/internal/ext-overrides/route.ts:21-35`, `:59-72`). The guarded handlers still rely on the session and assignment check, but this client-selected key/profile identity is **MUST-NOT-REPLICATE as caller authentication or as a credential selector** (`lib/auth-guard.ts:45-70`).
- The endpoint-test form also carries `__apiKeyId`; the internal handler reads it and injects it into `x-api-key-id` for the runner (`app/profiles/page.tsx:1055-1059`; `app/api/internal/test-profile-endpoint/route.ts:15-29`, `:61-81`). **MUST-NOT-REPLICATE** (`app/api/internal/test-profile-endpoint/route.ts:17-29`, `:61-64`).
- Both legacy workflow submit handlers accept `apiKeyId` from multipart form, resolve either a database ID or raw key, and fall back to the earliest API key with role `ADMIN` when absent (`app/api/v1/docs/workflows/route.ts:49-86`; `app/api/v1/docs/workflows/schema/route.ts:58-79`). **MUST-NOT-REPLICATE** (`app/api/v1/docs/workflows/route.ts:49-86`, `app/api/v1/docs/workflows/schema/route.ts:58-79`).
- Legacy `ExternalApiConnection.authSecret` is written directly from the request into the database column; the list and write responses mask it, but the handlers do not call an encryption function (`app/api/internal/ext-connections/route.ts:93-120`, `app/api/internal/ext-connections/[id]/route.ts:52-84`, `lib/db/schema.ts:72-82`). **MUST-NOT-REPLICATE** (`app/api/internal/ext-connections/route.ts:93-112`, `lib/db/schema.ts:77-82`).
- Separately, profile `fileUrlAuthConfig` is encrypted on write, while its legacy GET path tries parsing the stored value as plain JSON if decryption fails (`app/api/internal/profile-endpoints/route.ts:47-56`, `:149-167`; `lib/crypto.ts:11-21`, `:23-52`). This observed compatibility branch is **MUST-NOT-REPLICATE** (`app/api/internal/profile-endpoints/route.ts:47-56`).

## 3. Legacy user identity model

The `User` row has `username`, `password`, `role`, `provider`, `providerSub`, `email`, and `displayName` (`lib/db/schema.ts:170-181`). Local credentials use username lookup plus `bcrypt.compare`; a missing stored password is treated as SSO-only (`lib/auth.ts:11-49`). User creation/update hashes local passwords with bcrypt (`app/api/users/route.ts:65-70`, `app/api/users/[id]/route.ts:43-48`).

OIDC login is a separate NextAuth provider. Its profile yields `sub`, preferred username/email, and name (`lib/auth.ts:53-77`); sign-in links by `providerSub`, then may link an existing record by email, or JIT-creates a user with `password: ""` and `role: "VIEWER"` (`lib/auth.ts:82-145`). Subsequent logins refresh email/display name without changing the stored role (`:131-145`). Admin assigns local roles via user POST/PUT, while new OIDC identities default to Viewer (`app/api/users/route.ts:65-70`, `app/api/users/[id]/route.ts:50-52`, `lib/auth.ts:113-129`). NextAuth exposes the configured handler as both GET and POST (`app/api/auth/[...nextauth]/route.ts:1-6`).

## 4. Rework counterpart

### API keys and authentication

- Rework key rows are tenant-bound (`tenant_id`) and carry a SHA-256 `hash`, `prefix`, and lifecycle `status`; public authentication hashes presented `x-api-key` with SHA-256, and resolves only an `ACTIVE` row (`du-rework/services/orchestrator/src/server.ts:4182-4198`). The key list projection is `id`, `tenantId`, `prefix`, `maskedHint`, `status`, `createdAt`, and `updatedAt` (`du-rework/services/orchestrator/src/server.ts:4078-4086`). The shared contract declares `ACTIVE`, `REVOKING`, `REVOKED` and list query fields `tenantId`, `limit`, `cursor`, `status`, `prefix`, `sort` (`du-rework/packages/contracts/src/public-api.ts:565-590`). No `spendingLimit`/`totalUsed` fields appear in this key projection (`server.ts:4078-4093`).
- `GET /api/v1/admin/api-keys[/{keyId}]` requires a resolved admin principal, SQL-pages rows by tenant and returns the admin page envelope with grants (`du-rework/services/orchestrator/src/server.ts:2558-2610`, `:4044-4097`). `platform` bearer may read across tenants; a tenant operator is tenant-fenced (`du-rework/services/orchestrator/src/modules/admin-actions/rbac.ts:30-40`, `:54-83`).
- Mutations use `POST /api/v1/admin/actions` with `{ action, params }` and optional idempotency header; bearer or CSRF-validated shell-cookie authentication is resolved before dispatch (`du-rework/services/orchestrator/src/server.ts:2351-2392`). `apikey.issue` accepts `params.tenantId`, `params.apiKey`, optional `prefix`, hashes the value, inserts its digest, and returns `rawKey` in the create response; `apikey.revoke` accepts `params.apiKeyId`, derives the key's tenant from the database, and writes `REVOKED` (`du-rework/services/orchestrator/src/modules/admin-actions/dispatcher.ts:95-106`, `:540-617`, `:619-675`). These key mutations are platform-admin/cookie-admin actions (`:100-106`). No `apikey.rotate` action was found; issue/revoke are distinct actions (`:95-106`).
- Rework has no `/api/internal/auth-key`-style key-test endpoint in the Orchestrator route surface; public callers authenticate using their actual `x-api-key` and receive tenant resolution from the hash lookup (`du-rework/services/orchestrator/src/server.ts:4182-4198`).

### Profiles, connectors, and schema builder

- Rework profile bindings are immutable revisions mapping an API key to `(businessId, businessVersion, action)` and connector-slot revision pins; resolution is latest matching binding at submit, with no match denied once the key has bindings (`du-rework/services/orchestrator/src/modules/profiles/profiles.ts:7-18`, `:65-128`, `:132-153`). Admin creates them via `POST /api/v1/admin/profile-bindings` with `apiKey`, business/version/action, and `connectorBindings` (`du-rework/services/orchestrator/src/server.ts:2200-2275`). This is not the legacy per-endpoint `enabled`/parameters/priority/file-url-auth schema (`lib/db/schema.ts:120-137`; legacy route `app/api/internal/profile-endpoints/route.ts:110-167`).
- Connector lifecycle is primarily in the separate Connector service: `GET/POST /connectors`, revision create/activate/retire and current/detail reads are registered there (`du-rework/services/connector/src/http/server.ts:155-188`, `:190-287`); test is also a Connector service route (`:340-343`). Orchestrator's revision route returns a limited projection (`adapter:"unknown"`, disabled state, empty secret slots) rather than a legacy external-connection record (`du-rework/services/orchestrator/src/server.ts:2512-2554`). Orchestrator credential GET/POST is `/api/v1/admin/connectors/{id}/credentials`, with missing workflow failing `503` (`server.ts:2277-2310`); admin actions also expose credential rotate/revoke/test (`du-rework/services/orchestrator/src/modules/admin-actions/dispatcher.ts:114-120`, `:677-769`).
- Rework connector credentials use Vault references and write-only secret values: the Vault contract rejects plaintext secrets in revision configuration (`du-rework/packages/contracts/src/vault.ts:13-18`, `:290-319`); the credential workflow states that values are not logged/stored and responses are masked (`du-rework/services/orchestrator/src/modules/connector-credentials/workflow.ts:12-30`, `:411-434`). The Orchestrator credential route fails closed when that workflow is absent (`du-rework/services/orchestrator/src/server.ts:2282-2288`). This is server-side Vault policy/identity behavior, not a client-selectable plaintext mode.
- Rework workflow execution work does not provide the legacy schema catalog/builder/import/override admin routes in the Orchestrator surface. The ORCH-PAR plan records the shell builder route as absent and assigns schema authoring to ORCH-PAR-04 plus P9 execution (`du-rework/tasks/ORCHESTRATOR-LEGACY-FEATURE-PARITY-2026-10-01.md:20`, `du-rework/services/orchestrator/src/app/admin/shell-router.ts:465-508`). **Counterpart: not found** for `workflow-schemas` list/save/delete or pipeline-mapping override handlers in the current Orchestrator.

### User and role surface

Rework has an admin role/session surface but not the legacy `/api/users` CRUD or local `username`/bcrypt User model in Orchestrator. OIDC sessions store `issuer`, `sub`, role, and tenant (`du-rework/services/orchestrator/src/modules/auth/session-store.ts:34-47`); OIDC maps platform-admin claim to `admin`, a single tenant claim to `operator`, otherwise `viewer` (`du-rework/services/orchestrator/src/app/admin/oidc-flow.ts:122-129`). The session principal maps admin to `platform`, operator to a tenant-bound `tenant_operator`, and viewer to no admin principal (`session-store.ts:318-323`). Bearer roles likewise come from configured platform/tenant credentials, not caller-selected request fields (`du-rework/services/orchestrator/src/modules/admin-actions/rbac.ts:18-40`).

No Orchestrator `/api/users`, `/api/internal/user-profiles`, or user↔API-key assignment handler was found; the plan also records the assignment surface as absent and sends its inclusion to ORCH-PAR-05 (`du-rework/tasks/ORCHESTRATOR-LEGACY-FEATURE-PARITY-2026-10-01.md:21`, `:47`).
