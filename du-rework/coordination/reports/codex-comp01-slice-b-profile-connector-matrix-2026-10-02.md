## 1. Shared profile, parameter, and connector semantics

- `ParamSchema.required` is optional, and the registry's reusable `output_format` is the only parameter schema with an explicit default (`json`). `language` options are `vi`, `en`, `ja`, `zh`; `output_format` options are `md`, `json`, `html`, `csv`; the other declared options are listed below. No per-case parameter object sets `required: true`; the service discriminator is separate from `SubCaseDef.parameters` (`lib/endpoints/registry.ts:7-15,39-63,67-75,112-118,171-177,238-244,284-290,338-344`).
- The legacy profile key for each named case is generated as `service:case` (for example `extract:invoice`); `getAllEndpointSlugs` also exposes the service slug. Profile lookup is by `(apiKeyId, endpointSlug)` and falls back to the service-level slug when the case-specific profile is absent (`lib/endpoints/registry.ts:408-424`; `lib/endpoints/profile-resolver.ts:19-45`).
- `ProfileEndpoint.parameters` is a text column; the resolver consumes a decoded parameter map whose entries have `value` and optional `isLocked`. Profile values seed the merged variables; the allowed-key set is the union of registry parameter keys and profile keys; a profile lock takes precedence over `defaultLocked`, and otherwise registry `defaultLocked` is used, defaulting to false. A client value overwrites an unlocked profile value; a locked supplied value returns HTTP 400. This resolver path checks lock/key membership, not parameter type, option membership, or requiredness (`lib/db/schema.ts:122-137`; `lib/endpoints/profile-resolver.ts:48-93`). No case parameter in the registry sets `defaultLocked`; only the interface property is declared (`lib/endpoints/registry.ts:7-15,39-63,76-368`).
- `ProfileEndpoint.connectionsOverride` is the profile-level chain replacement field. With no override, the resolver maps each registry slug to a step; it accepts a legacy string array or a `ConnectionStep[]` with optional `stepId`, `captureSession`, and `injectSession`; malformed JSON falls back to registry defaults. A valid non-string array is returned as a `ConnectionStep[]` cast (`lib/db/schema.ts:122-137`; `lib/endpoints/profile-resolver.ts:12-17,117-141`). The profile schema also stores `enabled`, `jobPriority`, `fileUrlAuthConfig`, and `allowedFileExtensions` (`lib/db/schema.ts:122-137`).
- The separate `ExternalApiOverride` schema stores `connectionId`, `apiKeyId`, `endpointSlug`, `stepId`, and `promptOverride`, unique on connection/key/endpoint/step. `profile-resolver.ts` does not query or apply this table; this report therefore records it as a persisted prompt-override surface, not as behavior proven by that resolver (`lib/db/schema.ts:101-117`; `lib/endpoints/profile-resolver.ts:1-142`). `ExternalApiConnection` carries the concrete URL/method/auth/header/secret, prompt/file field names, default prompt, static fields/headers, response path, session paths/field, timeout, and state (`lib/db/schema.ts:72-98`).
- On rework, each action declares connector capability slots at action level, while each recipe names the slot required at its connector step. Those are capability targets, not a one-to-one reuse of legacy connection slugs. Action-level slots are: ingest optional `ocr`/`vision`; extract, analyze, and generate required `reasoning`; transform and compare optional `reasoning` (`du-rework/businesses/document-core/src/manifest/document-core.manifest.ts:26-68,71-102,104-136,138-172,174-207,209-240`). The step-key registry declares stable identifiers for the six actions (`du-rework/businesses/document-core/src/recipes/step-keys.ts:6-63`).

## 4. Mismatch ledger (registry ↔ presets ↔ profile resolver ↔ rework)

1. **Extraction preset coverage is partial and differently keyed.** The registry has six extract cases: invoice, contract, id-card, receipt, table, custom (`lib/endpoints/registry.ts:112-168`). `EXTRACT_PRESETS` supplies fields for invoice, contract, id-card, receipt, plus `po` and `payslip`; it has no `table` or `custom` entry (`lib/endpoints/presets.ts:11-41`). The custom registry schema is supplied by `fields`/`schema`, whereas presets expose a `fields` string and optional schema type but no preset sets a schema value (`lib/endpoints/registry.ts:158-167`; `lib/endpoints/presets.ts:5-9,11-41`). `po` and `payslip` have preset definitions but no corresponding member in the six-case extract registry (`presets.ts:32-41`; `registry.ts:117-168`).
2. **The resolver does not connect presets to profile values.** `profile-resolver.ts` loads a `ProfileEndpoint`, merges its parameter map, and parses `connectionsOverride`; it contains no import or lookup of `EXTRACT_PRESETS` (`lib/endpoints/profile-resolver.ts:1-7,24-45,48-93,117-141`; preset definitions `lib/endpoints/presets.ts:11-41`). Whether another caller combines presets and profiles is not established from the allowed files and is left unresolved.
3. **Reusable registry parameters are not all attached to a case.** `target_language`, `redact_patterns`, `max_words`, and `audience` are declared in `PARAMS`, but no per-case `parameters` object attaches them. In contrast, `transform:translate` describes `target_language` without listing it; `transform:redact` has no parameters; `generate` has no case exposing `max_words` or `audience` (`lib/endpoints/registry.ts:53,57,59,61,252-257,266-271,290-334`). Rework normalizer reads target-language/redaction aliases and generate maxWords/audience, and the rework manifest declares `targetLanguage` but omits `redactPatterns`; generate declares `maxWords` and `audience` (`input-normalizer.ts:228-242,270-307`; `document-core.manifest.ts:143-155,179-191`).
4. **Format surface differs.** Legacy `output_format` declares `md/json/html/csv`, default `json`; rework normalizer normalizes only `json`, `md`/`markdown`, and `text`/`txt` (unsupported values return `undefined`). Rework ingest manifest likewise enumerates `json/md/text`, while compare manifest has no `outputFormat` property even though `normalizeCompare` reads it (`lib/endpoints/registry.ts:39-40,79-81,247-250,347-350,364-367`; `input-normalizer.ts:532-539,310-329`; `document-core.manifest.ts:32-42,214-224`).
5. **Connection identifiers do not map one-to-one to rework slots.** Legacy chains name concrete connections such as `ext-classifier`, `ext-data-extractor`, and `ext-comparator`; rework recipes target action-level capabilities such as `reasoning`, `ocr`, or `vision` (`lib/endpoints/registry.ts:79-106,121-165,180-232,247-278,293-332,347-367`; `document-core.manifest.ts:54-65,92-98,126-132,162-168,197-203,230-236`; `recipe-definitions.ts:37-60,75-152,155-248,251-310,313-384,387-422`). Thus the allowed files show a capability-slot target but no concrete connection-slug crosswalk.
6. **Local versus connector execution differs for several named chains.** Legacy parse/split, transform convert, redact/template, and compare diff have a non-empty connection slug, while the corresponding rework recipe step is local-only; OCR/digitize use different rework slot names; legacy fact-check has two different connection slugs while its rework recipe uses the same `reasoning` slot for two steps (`lib/endpoints/registry.ts:79-107,247-278,347-351,206-211`; `recipe-definitions.ts:25-72,220-234,251-310,387-398`; `document-core.manifest.ts:54-65`). 7. **No dangling action-level rework slot was found among these 31 recipes.** Ingest's `ocr` and `vision` slots are referenced by its OCR and digitize recipes; every required reasoning slot for extract/analyze/generate and optional reasoning slots for transform/compare are referenced by at least one recipe (`document-core.manifest.ts:54-65,92-98,126-132,162-168,197-203,230-236`; `recipe-definitions.ts:37-60,75-248,263-286,313-384,399-422`). This is scoped to the six actions / 31 variants, not the separate workflow recipes.
8. **ExternalApiOverride application is unresolved in this slice.** The table schema records a per-step prompt override, but the permitted profile resolver does not read that table; no claim is made here about callers outside the files in scope (`lib/db/schema.ts:103-117`; `lib/endpoints/profile-resolver.ts:1-142`).
