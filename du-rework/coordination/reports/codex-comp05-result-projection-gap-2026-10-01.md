# COMP-05 — Legacy result and metadata projection gap

**Scope:** read-only characterization of the legacy operation response and the current rework operation, artifact, checkpoint, and usage paths. This report makes no source, contract, gate, or freeze changes.

## Classification

- **FULL** — the rework path has a factual source from which the legacy value can be deterministically projected. Conditional sources and their limits are called out explicitly.
- **MISSING** — no equivalent value is present in the current rework public projection or persisted source described below.
- **SYNTHETIC** — the current compatibility/facade path emits a default, placeholder, or inferred value that is not derived from the operation’s actual data. This is a gap, not parity.

The legacy reference is `lib/pipelines/format.ts:17-72`. The rework result path is `du-rework/services/orchestrator/src/server.ts:1917-1999`; its public operation view is `du-rework/services/orchestrator/src/modules/operations/facade.ts:32-50`.

Within the table, shortened `server.ts`, `modules/...`, and `compat/...` references are relative to `du-rework/services/orchestrator/src/`; `packages/contracts/...` is relative to `du-rework/`. Legacy `lib/...` and `app/...` paths are relative to the workspace root.

## Behavior behind the fields

### Progress and the zero case

Legacy initializes an operation at `0%` (`lib/pipelines/submit.ts:309-313`). The ordinary engine reports `round(i / pipeline.length * 100)` only before each processor call (`lib/pipelines/engine.ts:282-298`), so the first processor runs at `0%`; a single-step pipeline can remain there until completion/failure, and a stuck first processor leaves it there. Schema workflows use the same first-node formula (`lib/workflow-builder/run-schema.ts:42-54`). Code workflows can submit their own progress values through `workflow-engine.ts:206-214`.

Therefore legacy `0%` can be a real but coarse legacy observation. It is not a valid rework measurement: the current rework facade hard-codes zero and runtime progress reports are not persisted (`facade.ts:45`, `runtime.ts:483-492`). **Do not accept `progress_percent = 0` as parity for an in-flight operation.**

### Usage accumulation and finality

In the legacy ordinary engine, token/page/cost counters start as local zeroed accumulators (`lib/pipelines/engine.ts:252-262`), increase after completed processor calls (`:365-386`), and are written to the operation only on success (`:397-414`) or failure (`:450-465`). Between steps, only step results are persisted (`:391-394`), and the formatter emits a `result` block only for succeeded/failed terminal operations (`lib/pipelines/format.ts:35-68`). A failed result is therefore partial through the last completed processor. On retry, completed step snapshots are restored (`engine.ts:229-248`) but the local usage accumulators are initialized to zero afterward (`:252-262`); accumulated usage for skipped steps is not restored by this path, so a retried legacy total can omit earlier work.

Legacy workflows accumulate usage from completed sub-operations (`lib/pipelines/workflow-engine.ts:198-203`), save partial counters at a human-input pause (`:255-268`), and persist counters on success/failure (`:217-231,279-289`). The formatter still withholds the `result` block for the waiting state. Workflow success sets `modelUsed: null` and does not construct an ordinary-engine per-processor usage breakdown (`:217-231`).

Rework records usage separately as usage events. `usage.project()` sums only events already ingested and returns numeric zero plus `measurement: 'pending'` when there are none, or `estimated` if an event is estimated (`du-rework/services/orchestrator/src/modules/usage/usage.ts:357-376`). The success result endpoint calls that projection (`server.ts:1979-1984`); task completion itself is a separate result-ref/artifact transition (`modules/runtime/runtime.ts:494-575`). The result path does not establish that all usage events have arrived before projection. Also, the compatibility action adapter drops the measurement marker and uses `?? 0` defaults for token/cost fields (`compat/legacy-action-router.ts:315-349`). Those defaults are not evidence of finalized usage.

### MIME, `output_format`, inline content, and download links

Legacy `output_format` comes from the request form value (default `json`) and is stored on submission (`lib/endpoints/runner.ts:226-242`, `lib/pipelines/submit.ts:80,306-313`); `formatOperationResponse` copies that value (`lib/pipelines/format.ts:35-49`). It is not derived from an input or output MIME type. The legacy download route maps `html` to `.html`/`text/html`, `json` to `.json`/`application/json`, and every other format to `.md`/`text/markdown` (`app/api/v1/operations/[id]/download/route.ts:44-57,60-103`; thus `csv` also takes the fallback).

Rework retains each artifact's `mimeType` and `sizeBytes` and provides an artifact-specific download (`du-rework/services/orchestrator/src/server.ts:1966-1978,2003-2011`). The download streams artifact bytes with the artifact MIME (`:2053-2083`). No MIME-to-legacy-`output_format` mapping or `maxInlineBytes` decision point was found in the reviewed legacy formatter/download route or rework result/artifact path. Legacy success includes `content` and an operation `download_url` regardless of content size (`format.ts:35-50`); the rework result envelope keeps its opaque `resultRef` and separate artifact downloads (`server.ts:1920-1924,1979-1984`).

## Result for COMP-05

The rework path currently has faithful sources for operation identity/state/timestamps and conditional usage totals. It does not currently project legacy processor lists, numeric step/progress records, step-result payloads, inline output content/extracted data, model/pages/breakdown usage, operation-level download URL, or legacy failure detail. The hard-coded progress and adapter defaults are synthetic gaps; `{ resultRef }` cannot stand in for `result.content`.
