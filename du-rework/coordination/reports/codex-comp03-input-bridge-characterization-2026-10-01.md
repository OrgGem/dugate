# COMP-03 Legacy Input Bridge Characterization — READ ONLY

**Scope:** Compare the live legacy six-action input contract with the current rework request/artifact path. This is a source characterization, not an implementation or policy decision. Only this report was written; no source, contract, test, plan, or gate state was changed.

## Legacy field names and precedence

All six action routes are thin wrappers around `runEndpoint(action, req)` (`app/api/v1/docs/{ingest,extract,analyze,transform,generate,compare}/route.ts:5-6`). Their common file handling is therefore the same `normalizeFiles()` implementation (`lib/endpoints/runner.ts:36-53`). Route selectors and the additional registered parameter names are:

| Legacy POST route | Required discriminator and subcases | Registered snake_case input parameters by subcase |
|---|---|---|
| `/api/v1/docs/ingest` | `mode`: `parse`, `ocr`, `digitize`, `split` (`lib/endpoints/registry.ts:70-105`) | `parse`: `output_format`, `language`; `ocr`: `language`; `split`: `pages`; `digitize`: none. |
| `/api/v1/docs/extract` | `type`: `invoice`, `contract`, `id-card`, `receipt`, `table`, `custom` (`registry.ts:112-164`) | Only `custom`: `fields`, `schema`; the other variants have no registered parameters. |
| `/api/v1/docs/analyze` | `task`: `classify`, `sentiment`, `compliance`, `fact-check`, `quality`, `risk`, `summarize-eval` (`registry.ts:171-231`) | `classify`: `categories`; `compliance` and `quality`: `criteria`; `fact-check`: `reference_data`, `extract_fields`; the others have none. |
| `/api/v1/docs/transform` | `action`: `convert`, `translate`, `rewrite`, `redact`, `template` (`registry.ts:238-276`) | `convert`: `output_format`; `rewrite`: `style`, `tone`; `template`: `template`; `translate` and `redact`: none. |
| `/api/v1/docs/generate` | `task`: `summary`, `outline`, `report`, `email`, `minutes`, `qa` (`registry.ts:284-330`) | `outline` and `minutes`: `format`; `email`: `tone`; `qa`: `questions`; `summary` and `report`: none. |
| `/api/v1/docs/compare` | `mode`: `diff`, `semantic`, `version` (`registry.ts:338-365`) | `diff` and `version`: `output_format`; `semantic`: `focus`. |

Every route also recognizes these common form fields:

| Field | Legacy handling / precedence |
|---|---|
| `files[]` | Repeated file field; all non-empty `File` values are appended first, preserving `getAll()` order (`runner.ts:36-42`). |
| `source_file`, `target_file`, `file` | One value per field via `FormData.get()`; non-empty files append after `files[]`, in this exact order: `source_file`, then `target_file`, then `file` (`runner.ts:44-51`). These fields are additive; none wins over or replaces another. A compare request does not get a special source/target priority beyond this list ordering. |
| `file_urls` | JSON string containing an array of `{ url, filename?, mime_type? }` (`lib/file-url-downloader.ts:19-23`). The runner requires a valid array, allows at most 20 entries, and checks that `url` is a non-empty syntactically valid URL (`runner.ts:128-155`, `file-url-downloader.ts:40`). The declared optional fields are not validated in the runner block. |
| `output_format` | Read independently for every route; `FormData.get()` value wins and omitted value defaults to `json` (`runner.ts:225-226`). It is not limited to variants whose registry parameter object lists it. |
| `webhook_url` | Read independently with `FormData.get()` and passed to submit (`runner.ts:225-243`). It is not a file alias or a variant parameter. |
| Route discriminator | The route-specific discriminator is trimmed, then selects the matching subcase (`runner.ts:113-123`). There is no common discriminator name across routes. |

`sync=true` is a query parameter, not a multipart field (`runner.ts:228-229`); `idempotency-key` is a header (`runner.ts:228`). `source_url` is not read by the six legacy action route runner. Parameter defaults load from the selected profile first; submitted values replace them only for selected-subcase/profile-allowed keys and only when not locked (`lib/endpoints/profile-resolver.ts:48-93`). Unknown form parameter keys are ignored by that merge. Ordinary scalar reads use `FormData.get()` (first value); only `files[]` uses `getAll()`.

The normalized direct files are saved before `file_urls` are handled. For ordinary URL downloading, downloaded files are appended after the direct file list; in sync mode they download during submit, while async mode defers download to the worker (`lib/pipelines/submit.ts:186-246,248-285,335-350`). A configured first connector `fileUrlFieldName` instead changes precedence/handling: raw URLs are added as remote references after uploaded files and sent to that connector without being downloaded locally (`submit.ts:251-270`; `lib/pipelines/processors/external-api.ts:103-107`).

## Legacy admission, profile policy, and URL safety

- **Per-profile URL auth and extension policy:** `runner.ts:176-178,231-239` resolves the profile for the API key and endpoint, loads `fileUrlAuthConfig`, and passes both it and `allowedFileExtensions` to submit. The auth object supports `none`, `bearer` (`token`), custom `header` (`header_name`, `header_value`), or `query` (`query_key`, `query_value`) (`lib/file-url-downloader.ts:25-32,79-99`). `profile-resolver.ts:97-115` tries decrypt-then-JSON, then legacy plain JSON; invalid config becomes undefined. Allowed extensions override the default `.docx,.pdf` list (`lib/upload.ts:8-15,38-48,86-92`).
- **Size and MIME:** Direct files and downloaded URL bodies are capped at 300 MiB each (`lib/upload.ts:8,59-67,99-103`; URL content length and streamed bytes are independently checked at `lib/file-url-downloader.ts:174-179,217-229`). The direct-file aggregate default is 1 GiB (`lib/pipelines/submit.ts:187,233-246`), but that aggregate check runs before URL references/downloads are appended (`submit.ts:233-279`), so it does not account for `file_urls`. Direct file extension and declared MIME are checked by `validateFile()`; an empty direct MIME is allowed, otherwise it must match the extension map (`lib/upload.ts:26-57`). URL responses prefer server `Content-Type`, falling back to entry `mime_type`, and are validated against the derived/overridden filename before and after streaming (`file-url-downloader.ts:181-199,248-253`). This is metadata validation, not content sniffing.
- **Macros and paths:** `.docm` is rejected explicitly even if profile extensions might otherwise allow it (`lib/upload.ts:30-36,78-84`). Uploaded filenames are reduced with `path.basename()` and filesystem-sensitive/control characters are replaced before storage naming (`lib/upload-helper.ts:11-19,29-49`). Separately, ZIP extraction rejects NUL, absolute, drive-absolute, and traversal entry names and checks the resolved destination remains under the extraction root (`lib/archive.ts:54-70,102-145`).
- **SSRF guard call sites:** `file_urls` syntax parsing in `runner.ts:144-153` is not the SSRF control. The actual local-fetch guard is `assertSafeUrl(applyQueryAuth(entry.url, authConfig))` at `lib/file-url-downloader.ts:129-140` (call at line 137); manual redirects are re-checked through `assertSafeUrl()` at lines 102-124 (call at line 122). `lib/pipelines/processors/http-client.ts:74-125` limits schemes, private/reserved hosts, resolved private addresses, and fails closed on DNS errors. **Exception:** the legacy `fileUrlFieldName` branch at `submit.ts:251-270` skips `downloadAllFileUrls()` and forwards each raw URL to the external connector (`external-api.ts:103-107`); the local file downloader's `assertSafeUrl`, 300 MiB streaming bound, and filename/MIME validation do not run on that branch. That legacy behavior is a distinct existing path; COMP-03 must not reproduce it as an unguarded rework path.

## Rework request and artifact path today

- **No mounted six-route multipart facade:** `services/orchestrator/src/server.ts` has the canonical JSON `POST /api/v1/businesses/:id/actions/:action` route, which passes `ctx.body` directly to `submission.submit()` (`server.ts:1730-1763`). Generic ingress parses non-binary bodies as JSON or raw text (`services/orchestrator/src/http/ingress.ts:45-49,55-103`). The only raw request stream special case is `PUT /api/v1/uploads/:id[/content]` (`server.ts:728-742,764-774`). A source scan found no `legacy-action-router` import or mount in `server.ts`; the isolated compat router documents that the host must split the request and supplies `form?: unknown` (`compat/legacy-action-router.ts:10-17,183-194,360-367`). It decodes and passes `files`/`fileUrls` to an injected dispatcher (`legacy-action-router.ts:391-429`) but does not parse HTTP multipart, upload file bytes, or itself create artifacts. Thus **there is no `multipart/form-data` submit path in the current rework server**.
- **Upload/encryption surface:** With S3 and public-upload encryption configured, `server.ts` constructs a `PublicUploadGateway` with the `CryptoStorageFacade` and key configuration (`server.ts:565-576`). A tenant-authenticated `POST /api/v1/uploads` accepts JSON metadata and chooses a single init below 64 MiB + 1 byte or multipart init at/above that threshold; it returns the `artifactId` and raw-byte content URL (`server.ts:1460-1481`, `packages/contracts/src/runtime.ts:270-277`). The authenticated `PUT /api/v1/uploads/:artifactId/content` streams request bytes to the gateway (`server.ts:1442-1458`); `/part` explicitly rejects client direct-part upload with 409, while complete/abort routes remain (`server.ts:1483-1497`). This is an artifact transfer/multipart lifecycle, **not** a browser `multipart/form-data` action submission. The configured total ceiling is 8 GiB (`runtime.ts:273-275`; gateway default/validation `upload-encryption-gateway.ts:32-37,317-328`).
- **Artifact creation and encryption:** Single init generates a UUID, inserts an `input` artifact in `STAGING`, and returns that artifact ID (`upload-encryption-gateway.ts:711-818`, especially `771-781`). Larger multipart init also creates an artifact row (`modules/artifacts/multipart-service.ts:908-935`). The upload gateway checks declared and observed byte counts and digests, encrypts one-shot or with `encryptStream()`, stores ciphertext/manifest in S3, verifies them, then commits the row to `READY` (`upload-encryption-gateway.ts:430-480,514-535,678-690,821-877`). The client obtains the ID from upload init; it is not inferred from a legacy filename or URL.
- **Submission consumes references:** `SubmissionSchema` accepts canonical JSON `input`, optional `sourceUrl`, `artifacts: [{ artifactId, role }]`, output, callback, and client reference (`packages/contracts/src/operations.ts:282-294`). `submission.submit()` parses that schema, collects nested/top-level artifact IDs, and checks that they are tenant-scoped, unexpired, and `READY` before operation creation (`modules/operations/submission.ts:145-172,540-579`). A distinct `sourceUrl` is HTTPS-only, credential-free, and checked with `adjudicateUrlDestination()` (`submission.ts:368-383`); that is a guarded single-source field, not a `file_urls` array implementation.
- **Hard SSRF finding:** The public upload gateway accepts a caller-provided byte stream and metadata; its init validates MIME/name syntax and size, not a URL, extension allowlist, or MIME-to-extension policy (`upload-encryption-gateway.ts:711-732`; multipart schema `runtime.ts:286-293`). It contains no URL fetch or SSRF guard. The path assumes the uploader supplied the bytes. **If COMP-03 maps `file_urls` directly into artifact references or fetches them without a server-side URL/destination guard, it creates an SSRF bypass.** `sourceUrl` validation does not guard arbitrary `file_urls` entries.

## COMP-03 input-bridge gaps (observed requirements, no policy decision)

1. **Route and streaming parser gap:** Mount six `POST /api/v1/docs/{action}` paths and accept the legacy multipart field names above. The adapter needs bounded streaming multipart parsing; routing fields through current generic JSON ingress cannot preserve file bytes or enforce limits while streaming.
2. **File-to-artifact gap:** Preserve all direct-file inputs and their field labels/order (`files[]`, `source_file`, `target_file`, `file`), apply the resolved profile extension policy, `.docm` rejection, MIME and per-file 300 MiB checks, then upload bytes through the encrypted gateway and pass returned `READY` artifact IDs/roles to canonical submission. Enforce the combined byte budget after all file sources are materialized; the legacy 1 GiB check currently covers direct uploads only.
3. **`file_urls` SSRF gap:** Resolve the same tenant/API-key profile auth and extension settings, enforce URL destination policy before the first request and on every redirect, stream-count to the file limit, apply filename/MIME validation, and only then feed fetched bytes through the encrypted artifact gateway. Do not let the decoder's syntax-only URL check (`compat/legacy-wire-decoders.ts:403-423`) or trusted-uploader artifact path stand in for SSRF protection; that decoder also has no legacy 20-entry cap. Do not turn raw URLs into artifact references or unguarded connector forwarding.
4. **Compatibility precedence/allowlist gap:** Keep the route's discriminator, legacy parameter allowlist/profile-default/lock behavior, `output_format`, callback field, and `sync` semantics. The COMP-02 decoder accepts broader body/parameter containers, snake/camel aliases and conflict errors (`legacy-wire-decoders.ts:145-220`), and copies generic flat parameter fields into canonical input; the legacy runner ignores non-allowed parameter keys. That is a behavior delta to account for in the bridge, not silently assume exact parity.
5. **Metadata and filename policy gap:** Rework upload initialization accepts arbitrary non-empty MIME metadata and a filename up to 1024 characters with control-character rejection, but does not enforce legacy extension/MIME maps or `.docm` rules (`upload-encryption-gateway.ts:711-732`, `runtime.ts:286-293`). The bridge needs to apply legacy admission before artifact creation rather than treating init metadata as proof of file type.
