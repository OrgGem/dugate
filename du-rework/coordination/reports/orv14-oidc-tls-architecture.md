## External recipient/current-principal design

### Identity and authority

Use a new **server-generated opaque recipient/principal UUID**, uniquely bound to the exact verified `(issuer, sub)` tuple. That UUID is a directory record key, not a conversion of sub, email, username or display name. Never search admin_local_users for external sub/email or construct du-local identity. Browser may select an existing authorized opaque recipient ID, but it cannot supply issuer/subject/role/tenant to register or authorize one.

Minimal external directory stores principalId, kind OIDC, exact issuer/sub, current application enabled/revoked status, authorizationVersion, last verified role/scope facts and timestamps. A bounded safe display label may identify it in the picker, but is never an authorization key or raw token/email claim. Platform external Admin keeps tenantId null and platform scope. The tenant of a budget/alert is an explicit resource scope selected by that Admin; do not mint a tenant membership or require a tenant UUID on the identity. Retain tenant-filtered budget/delivery/inbox data. Local Admin identity/current-version validation continues through the existing local authority.

Recipients for this first-party Admin channel remain eligible Admins. An operator/viewer proof cannot self-register as Admin or receive tenant/platform alerts via an untrusted directory label. If future channels support more roles, extend an explicit grant contract, not this fallback.

Backend injects a typed directory port with `observeVerifiedLogin(identity)`, `ensureSelfRecipient(trustedSession)`, `resolveCurrentPrincipal(trustedSession)` and `revoke/disable(principalId,expectedVersion,actor)`. `observeVerifiedLogin` is invoked only after actual OIDC token/state/nonce verification, before publishing a session proof for notification use. A self-registration endpoint accepts no external identity fields: it resolves exactly one valid opaque du_session itself, checks configured trusted issuer and actual role/scope, then returns its own opaque recipient. Existing sessions may bootstrap a missing record from their trusted server-side facts; mark the original session verification time, not a new IdP verification at request time. An older session must not overwrite a newer directory role/scope observation, clear application revocation, or upgrade itself after observed downgrade. Directory disable is sticky until explicit authorized reenable; subsequent login must not silently enable it.

New external sessions carry the observed authorizationVersion in server-side session metadata, separately from local roleVersion. Notification requests compare it with current directory state plus actual session role/scope. A revoked/disabled/version-changed record denies notification binding/inbox operations and cannot be resurrected by another replica or cached client. Directory failure fails closed; no fallback to local IDs, bearer actor labels, signed legacy role-only cookie, or browser subject.

Application revoke/disable is authoritative locally: update directory/version with atomic audit, reject affected notification requests immediately, and invoke the existing exact issuer/sub shared-session revoke capability or durable revocation outbox as appropriate. Do not claim synchronous global session revocation if only a queued outbox executed; report its observed completion. Remote IdP role/disable change is observed only on a newly verified login/implemented refresh/introspection/back-channel seam or expiry. This packet adds no such remote instantaneous seam and must make no instantaneous remote revocation claim.

### Routing, immutable pins and current access

Use a discriminated recipient reference: local `{kind:'local',userId}` versus external `{kind:'oidc',principalId}`. Preserve legacy ownerUserId requests/response compatibility through an explicit local adapter; reject ambiguous/both shapes. A directory ID is never accepted as a local userId.

At binding, enqueue and delivery, resolve current recipient eligibility within the proper application transaction/lock. Store immutable recipient kind/ID, authorizationVersion or local version, budget tenant, bindingRevision and channelId/channelRevision in the alert/delivery pin. A later binding edit/role change does not retarget historical deliveries. Directory revocation/version changes block pending delivery rather than redirecting it to a new owner. Reenable/rebind creates a new binding pin for future alerts; old immutable records retain original disposition/audit.

In-app inbox reads/read acknowledgements derive the recipient from the authenticated current principal, never a caller-selected recipient/userId. External platform Admin with null identity tenant can read **its own** inbox within an explicitly selected alert tenant; another platform Admin cannot read it by changing recipient ID. Keep tenant/query/principal/limit binding on cursor. Acknowledgement is idempotent and CSRF-protected. Current-directory enabled/version and actual session role checks guard read as well as mutation; budget administration permission is not blanket ownership of every inbox.

Ordinary UI: allow trusted external Admin self-enrollment, show registered eligible recipient lookup in the selected budget tenant, label local versus external safely, display own inbox and routing error/revoked state. No raw UUID/issuer/sub entry is necessary for common setup. Only authorized Admin can assign another registered eligible owner; self-registration does not confer rights to select arbitrary unverified subjects.

## Private Compose HTTPS workflow policy and actual positive fixture

**Approve a deployment-only exact-origin policy**, proposed `WORKFLOW_PRIVATE_HTTPS_ORIGINS` parsed in document-core config. It is empty/defaultdeny. Require a bounded list of canonical HTTPS origins only: no paths/query/fragment/userinfo, wildcards, host suffixes, CIDRs, arbitrary fetch implementation, per-request boolean or browser setting. Validate at process startup, reject malformed entries rather than silently dropping them, freeze an immutable copied set. Explicit port is part of origin. Prefer literal configured service hostname/SAN and protected deployment configuration; permissions allowing workflow edits do not allow modifying this list. Existing worker runtime URL/Connector flags remain independent.

Private opt-in applies to an individual request only when BOTH conditions hold:

1. Its origin belongs to the immutable administrator-approved `LegacyWorkflowSchemaPin.approvedEgressOrigins` for this tenant/schema/revision.
2. The same canonical origin belongs to the operator-owned deployment private-HTTPS list.

Public approved origins retain normal default public-address policy. A schema containing a private-approved origin does not alone enable it; a deployment entry does not authorize a tenant schema. A revised deployment allowlist can tighten old operation egress and make its outcome a clear policy denial; it does not rewrite old schema pins or broaden them. Record deployment policy digest for safe diagnostics/receipt rather than pretending the runtime choice was in the customer input.

Implement a worker-owned **policy factory/wrapper**, not injectable arbitrary network transport from task payload. It calls `requireApprovedHttpsOrigin` first and constructs/chooses `createPinnedFetch({timeoutMs:15000,allowPrivateNetworks:privateOrigins.has(origin)})` for that authorized origin. No allowHosts/DNS override that skips adjudication. Keep one actual DNS lookup per attempted hostname, adjudicate every answer, and dial only the chosen adjudicated answer; original hostname CA validation/SNI remains mandatory. Do not fake public DNS then connect private. Mixed allowed/forbidden DNS answers fail closed. Metadata/link-local/CGNAT/multicast/unspecified/reserved bans remain enforced even for an opted-in origin, including redirects. Workflow still rejects all3xx, so no credential forwarding/following to another origin. Keep response decompression/decoded-byte cap, headers/auth restrictions, max downloads, timeout, task cancellation and extension/MIME/size checks unchanged.

Backend was assigned the now-frozen/released document-core lease: `businesses/document-core/src/{config,main,worker}.ts`, `pipelines/workflows/schema/legacy-schema-runtime.ts`, plus a small worker-only egress-policy leaf if desired. Add optional trusted runtime dependencies to both `handleLegacyWorkflowSchema` and `handleLegacyWorkflowBranch`; wire them through a definition factory or bound handler creation per worker startup rather than mutating module globals. Existing default exported definition retains empty/defaultdeny policy; concurrent workers with different config must not leak policy. Parent and branch/retry/HITL continuations use the same worker policy on both callback and file download. Shared `@du/egress` and Connector default network contract need no weakening and are outside this worker lease.

Real fixture direction: independent verifier creates a unique synthetic CA/server certificate with SAN matching an exact private hostname, an actual HTTPS callback/download listener reachable from its isolated worker/Compose network, and real private DNS resolution. Configure only the fixture origin in deployment policy and separately in its immutable tenant schema. Trust the synthetic CA using a temporary protected deployment trust bundle/standard Node CA mechanism; retain existing proxy CA trust and remove only the temporary fixture material afterward. No rejectUnauthorized false/NODE_TLS_REJECT_UNAUTHORIZED=0, SNI/checkServerIdentity override, plaintext substitute, mocked global fetch or resolver answer spoof. Actual callback emits observed method/body/status; download yields known bytes/hash/MIME through worker parse/artifact/result. Full HTTP admission→PG/outbox→Redis→actual worker→HTTPS→poll/result proof is required for T01/T02.

No public hosting capability is needed for this legitimate private-mesh product feature. A managed public synthetic HTTPS fixture remains an acceptable alternative if ownership/access is established, but inventing a public fixture URL or silently loosening runtime to reach a fixture is rejected. Existing standaloneTLS1/1 remains separate preflight only.
