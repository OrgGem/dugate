# Legacy Storage Engine, FileCache, and Rework Artifact Model

## Scope and method

This is a read-only source characterization, not a test or deployment verification. No tests were run, no production or test files were edited, and no gate or COMP row was changed; this report is the only intended write. The requested `prisma/schema.prisma` was not present in the inspected tree: the legacy schema is declared with Drizzle in `lib/db/schema.ts` and its initial SQL is in `drizzle/0000_violet_franklin_storm.sql` (`lib/db/schema.ts:1-5,150-165`; `drizzle/0000_violet_franklin_storm.sql:61-72,80-104`).

## 1. Legacy upload admission and file handling

| Concern | Observed behavior |
|---|---|
| Per-file ceiling | The validator’s operative `MAX_FILE_SIZE` is a hard-coded 300 MiB constant, enforced against `file.size`; it is not read from an environment variable or AppSetting in this path (`lib/upload.ts:8,59-67`). A distinct 100 MiB `MAX_FILE_SIZE_BYTES` exists in `lib/config.ts:7`; the upload validator shown here does not import it (`lib/upload.ts:4-8,26-67`). |
| File formats / macro rejection | Default extensions are `.docx` and `.pdf`, with corresponding MIME values; `.docm` is rejected explicitly before the extension allowlist, including when a custom extension string is supplied (`lib/upload.ts:10-15,26-48`). A non-empty supplied MIME must match the extension mapping; an empty MIME is accepted (`lib/upload.ts:50-57`). The metadata validator applies the same extension, `.docm`, MIME and size checks to remote-file metadata (`lib/upload.ts:74-106`). |
| Path traversal / names | The upload helper takes `path.basename(file.name)`, NFC-normalizes it, and replaces control and filesystem-special characters before composing an operation-scoped key (`lib/upload-helper.ts:11-19,40-42`). The local backend resolves the key under `UPLOAD_DIR` and rejects a resolved path not starting with its base directory (`lib/storage/local-backend.ts:12-19`). |
| Order of parsing, validation, and storage | The endpoint awaits `req.formData()` before passing its files onward (`lib/endpoints/runner.ts:84,125-126`). The submit loop calls `saveUploadedFile`; its validator checks the File metadata before `file.stream()` is passed to the storage backend (`lib/pipelines/submit.ts:192-195`; `lib/upload-helper.ts:29-48`). This establishes that the application-level size check follows FormData parsing and precedes the subsequent storage stream. These sources do not establish whether the web runtime internally buffers or spools the parsed File, so no stronger memory-buffering claim is made. |
| What `upload-helper.ts` adds | It performs the validation, sanitized operation-scoped key construction, and storage-backend selection; wraps `file.stream()` in a Node readable; uploads the stream; then sends the returned MD5 and canonical key through FileCache dedup and returns `path`, `s3Key`, `fileCacheId`, MD5 and bytes written (`lib/upload-helper.ts:29-60`). |

The pipeline also has an aggregate upload limit, defaulting from `MAX_TOTAL_UPLOAD_SIZE` to 1 GiB; it sums uploaded sizes after each file has already been saved and attempts to delete those keys if the aggregate limit is exceeded (`lib/pipelines/submit.ts:186-188,233-245`).

## 2. Legacy backend selection and failure behavior

Legacy storage selection is backed by the `AppSetting` values `s3_bucket`, `s3_endpoint`, access key, secret and region, with defaults in `lib/settings.ts`; it is not selected directly from an environment variable. The factory reads those settings and selects S3 when `s3_bucket` is truthy, otherwise Local; `s3_endpoint` is optional, and the selected backend is cached per process until reset (`lib/settings.ts:102-126`; `lib/storage/index.ts:14-50`). The backend comment describes S3 selection by endpoint, but the actual branch condition is the bucket (`lib/storage/index.ts:16-19,24-45`).

`S3StorageBackend` identifies itself as compatible with AWS S3, MinIO and R2. A supplied endpoint uses path-style requests; when both explicit credentials are not supplied the AWS SDK credential chain is used (`lib/storage/s3-backend.ts:1-2,20-45`). Local files are written under the resolved `UPLOAD_DIR`; S3 objects use the supplied key as the S3 `Key` (`lib/storage/local-backend.ts:12-25,49-53`; `lib/storage/s3-backend.ts:66-82`).

There is no Local fallback when an already selected S3 call fails: the S3 upload catch attempts to delete that S3 key and rethrows. The submission layer maps recognized missing-bucket/access/storage HTTP errors to 503 and other upload errors to 500 (`lib/storage/s3-backend.ts:79-87`; `lib/pipelines/submit.ts:192-219`).

## 3. Legacy FileCache deduplication and scope

The requested Prisma model is absent; the actual Drizzle `FileCache` table has: `id` primary key; `md5Hash` unique and not-null; `s3Key`, `fileName`, `mimeType`, `size`, `refCount`, `createdAt`, and `lastAccessedAt`, all not-null (with `refCount` default 1 and timestamps defaulting to current time). It has non-unique indexes on `refCount` and `lastAccessedAt`; there is no tenant or API-key column (`lib/db/schema.ts:150-165`; matching initial SQL: `drizzle/0000_violet_franklin_storm.sql:61-72,153-154`).

Each storage backend computes MD5 while streaming, then the helper calls `dedup(md5, uploadedKey, ...)` (`lib/storage/local-backend.ts:27-53`; `lib/storage/s3-backend.ts:48-82`; `lib/upload-helper.ts:44-58`). The dedup write upserts on the globally unique `md5Hash`, increments `refCount` and refreshes `lastAccessedAt` on conflict, then returns the existing canonical `s3Key` when its object exists; a unique-race path also increments by `md5Hash` (`lib/storage/dedup.ts:29-58,59-79`). The resulting canonical key and cache ID are placed in operation file metadata (`lib/upload-helper.ts:51-59`; `lib/pipelines/submit.ts:222-230`).

**MUST-NOT-REPLICATE — instance-global content-address hit can reuse another tenant’s object.** The unique cache key is only MD5, the lookup/upsert is only by MD5, and the cached canonical object key is returned into an operation’s file reference without tenant scoping (`lib/db/schema.ts:152-165`; `lib/storage/dedup.ts:29-58,63-77`; `lib/pipelines/submit.ts:222-230`).

## 4. Legacy cleanup, retention timing, and operation effects

The six-hour scheduler runs both file cleanup and FileCache cleanup once 10 seconds after startup, then every six hours (`lib/cleanup-scheduler.ts:11-32`). There are two distinct ages here; the phrase “7-day cleanup” does not describe the operation-file sweep:

| Lifecycle | Eligibility and effect |
|---|---|
| Operation-associated files | `cleanupExpiredFiles` uses a 24-hour age threshold. It selects every operation with `createdAt < cutoff`, `filesDeleted=false`, and `deletedAt IS NULL`; there is no operation-state predicate, so an old non-terminal row is in the selected set too (`lib/cleanup.ts:17,40-54`). For each selected row it recursively removes the local `OUTPUT_DIR/<operationId>` directory if present, deletes `outputFilePath` from the active storage backend, then processes the input references in `filesJson` (`lib/cleanup.ts:61-82`). |
| Uploaded input references | A cached entry decrements its FileCache `refCount`; an entry with `s3Key` but no cache reference is deleted directly through the active backend; otherwise a local `path` is removed from disk (`lib/cleanup.ts:79-108`). The operation row is not deleted or marked terminal: only `filesDeleted` becomes true (`lib/cleanup.ts:111`; operation columns include `filesJson`, output fields, `filesDeleted`, and `deletedAt` at `lib/db/schema.ts:10-42`). |
| FileCache object / row | The setting `s3_cache_ttl_hours` defaults to 168 hours (7 days). A cache row is eligible only when `refCount <= 0` and `lastAccessedAt < cutoff`; the active backend deletes the object key(s), then the matching FileCache rows are deleted (`lib/settings.ts:102-109`; `lib/cleanup.ts:127-150`). Thus seven days applies to zero-reference cache entries, not every operation’s files. |

When S3 is the configured active backend, the same cleanup calls backend `delete`/`deleteMany` for output and cache objects (and direct non-cache S3 input objects); in Local mode the backend deletes from disk. The local output-directory removal is separately performed with `fs.rm` (`lib/cleanup.ts:43-44,61-77,92-96,139-143`; local implementation `lib/storage/local-backend.ts:66-72`).

If cleanup selects an in-flight operation, it removes its underlying input object(s) but leaves `filesJson` references in the operation row and sets `filesDeleted=true`. The engine later resolves `s3Key ?? path` and calls `downloadToTempFile`; if the object is gone, that failure follows the pipeline error path, which marks the operation `FAILED` (`lib/cleanup.ts:79-111`; `lib/pipelines/engine.ts:187-210,450-465`). For an operation already terminal, cleanup does not delete its row, clear its result fields, or set `deletedAt`; a successful operation with `outputContent` continues to return that stored content through the download endpoint, while a download relying on a removed `outputFilePath` is caught as 404 (“Output file has been cleaned up”) (`lib/cleanup.ts:46-54,111`; `app/api/v1/operations/[id]/download/route.ts:20-27,37-58,60-111`).

## 5. Legacy operation file fields and stored value shapes

The legacy `Operation` table has `filesJson`, `outputContent` and `outputFilePath`; it has no `fileUrl` or `filePaths` column (`lib/db/schema.ts:10-42`). For an uploaded file, the submitted JSON entry stores the original filename, canonical backend key in both `path` and `s3Key`, MIME, byte size, FileCache ID, and MD5 (`lib/pipelines/submit.ts:222-230`). The key is constructed as `<operationId>/<sanitizedName>`; Local stores the bytes at `UPLOAD_DIR/<key>`, while S3 uses that same string as its object key. The stored input key is therefore not prefixed `file://` or `s3://` (`lib/upload-helper.ts:40-58`; `lib/storage/local-backend.ts:12-25,49-53`; `lib/storage/s3-backend.ts:66-82`).

For a URL forwarded to a connector, the JSON reference instead has `path: ""`, `url`, `isRemoteUrl: true`, and zero metadata size; downloaded URLs are added through the downloader path (`lib/pipelines/submit.ts:248-280`). The engine’s `filePaths` are runtime-local values: Local returns the resolved upload path; S3 downloads to a temp file (`lib/pipelines/engine.ts:177-210,30-38`; `lib/storage/local-backend.ts:56-64`; `lib/storage/s3-backend.ts:100-115`).

I found no non-null production assignment to `outputFilePath` in the inspected `lib/` and `app/` sources: the regular successful completion update stores `outputContent`, while external-API result construction sets `outputFilePath: undefined` (`lib/pipelines/engine.ts:397-414`; `lib/pipelines/processors/external-api.ts:50,216`; field declaration `lib/db/schema.ts:23-27`). Therefore an exact persisted output-path format per backend is **not found** in these writers. The download consumer treats a Local value as a path that must resolve under `OUTPUT_DIR`, and treats the S3 value as a backend object key; neither branch requires a URI prefix (`app/api/v1/operations/[id]/download/route.ts:60-105`).

## 6. Rework artifact model and comparison

### Storage, rows, and backend

Rework stores per-artifact metadata including tenant, operation/task references, purpose, MIME, size, SHA-256, state, token, storage key, expiry and creation time (`du-rework/services/orchestrator/migrations/0001_platform_v1.sql:128-144`). PostgreSQL `artifact_blobs` has a storage-key primary key, tenant foreign key, and `bytes bytea` (`du-rework/services/orchestrator/migrations/0003_artifacts_grants.sql:6-13`). PostgreSQL is the default storage backend; migration 0013 adds a backend field defaulted to `postgres` and constrains it to `postgres` or `s3` (`du-rework/services/orchestrator/src/server.ts:336-347,447-448`; `du-rework/services/orchestrator/migrations/0013_artifact_storage_version.sql:1-20`). The Orchestrator composes an S3 storage facade when S3 is configured (`du-rework/services/orchestrator/src/server.ts:487-545`); its S3 adapter requires versioned objects and validates artifact ID, tenant metadata, object version, size and SHA-256 (`du-rework/services/orchestrator/src/modules/artifacts/s3-storage-facade.ts:146-150,184-215`). Rework is therefore not “PostgreSQL bytea only”; it has both a PostgreSQL adapter and a configured S3 adapter, with an explicitly enabled migration dual-read window rather than an unconditional silent fallback (`du-rework/services/orchestrator/src/modules/artifacts/artifacts.ts:65-90,513-579`).

Rework creates a UUID artifact ID, derives storage key `art-<artifactId>`, stores SHA-256/integrity metadata, and does not look up a global MD5 cache (`du-rework/services/orchestrator/src/modules/artifacts/artifacts.ts:108-125,261-290`). **No rework counterpart was found for legacy MD5 deduplication, the `FileCache.refCount` model, or the legacy seven-day zero-reference cache cleanup.** The artifact table has a nullable `expires_at`, but the upload-row INSERT does not populate it; method-grant expiry is stored separately in `token_expires_at` (`du-rework/services/orchestrator/migrations/0001_platform_v1.sql:138-142`; `du-rework/services/orchestrator/src/modules/artifacts/artifacts.ts:140-146`; `du-rework/services/orchestrator/migrations/0008_artifact_grant_fencing.sql:1-8`). The inspected artifact service has no READY-artifact retention sweep. The periodic sweep found in the artifact module is specifically for expired multipart sessions: it selects expired `STAGING` rows and residual `ABORTED` multipart sessions and marks/purges those sessions, and the server wires that sweep to its recovery timer (`du-rework/services/orchestrator/src/modules/artifacts/multipart-service.ts:864-900`; `du-rework/services/orchestrator/src/server.ts:577-581,890-903`). A scoped source search of `modules/artifacts/**` and `server.ts` found no `DELETE FROM artifacts` or artifact-byte TTL query; the `DELETE FROM artifact_blobs` sites found are error/rollback cleanup, not a scheduled READY-artifact retention policy (`du-rework/services/orchestrator/src/modules/artifacts/artifacts.ts:77-84,244-258`).

### Access grants, tenant fencing, and artifact state

Rework artifact purposes are explicit contract values `input`, `output`, `intermediate`, and `session`; the purpose is persisted in artifact metadata (`du-rework/packages/contracts/src/runtime.ts:192-204`; `du-rework/services/orchestrator/src/modules/artifacts/artifacts.ts:140-146`). Legacy upload metadata has a filename and file references, but no corresponding per-file role/purpose field in the operation schema/writer (`lib/db/schema.ts:20-27`; `lib/pipelines/submit.ts:222-230`). Rework issues method-scoped upload/download grants with stored expiry (15 minutes in the artifact service) and the blob route checks token, method and expiry (`du-rework/services/orchestrator/src/modules/artifacts/artifacts.ts:30,118-125,419-425`; `du-rework/services/orchestrator/migrations/0008_artifact_grant_fencing.sql:1-8`; `du-rework/services/orchestrator/src/server.ts:1511-1532`). No comparable artifact-ID-plus-expiring-method-grant flow was found in the legacy operation download route, which looks up the operation by ID and checks success before serving output (`app/api/v1/operations/[id]/download/route.ts:15-41`).

The rework write path queries by both storage key and tenant, permits byte writes only while `STAGING`, and rejects a non-STAGING artifact as immutable; successful finalization pins size/hash/version while changing only a STAGING row to READY (`du-rework/services/orchestrator/src/modules/artifacts/artifacts.ts:462-485,271-290`). Public artifact download resolves the API key and constrains the query by artifact ID and tenant, purpose, operation/reference, and then requires READY (`du-rework/services/orchestrator/src/server.ts:2003-2039`). S3 reads also validate artifact and tenant metadata (`du-rework/services/orchestrator/src/modules/artifacts/s3-storage-facade.ts:201-215`). These are source-level observations, not deployment proof.

### Encryption path note

The public S3 upload crypto dependency is optional at composition time and documented as fail-closed when absent; upload admission routes return 503 when the encrypted-upload gateway is unavailable (`du-rework/services/orchestrator/src/server.ts:394-400,550-563,1440-1468`). When the decrypt helper is invoked, an object marked sealed without a crypto facade is rejected with 503, and its artifact/tenant metadata is checked (`du-rework/services/orchestrator/src/modules/encryption/artifact-read-decrypt.ts:167-197`). **MUST-NOT-REPLICATE — conditional raw-read bypass:** the runtime blob and public download handlers call the decrypt helper only when `artifactDecryptDeps` is non-null, then fall through to `ctx.artifacts.getBlob(...)` when it is null. Thus, if a previously sealed artifact is reachable while those dependencies are absent, these handlers do not run the helper’s sealed-marker fail-closed check and return the stored bytes through the raw path (`du-rework/services/orchestrator/src/server.ts:1540-1561,2041-2053`; helper’s refusal when invoked: `du-rework/services/orchestrator/src/modules/encryption/artifact-read-decrypt.ts:175-186`).
