# CRX-03-DESIGN — Worker Encryption Seam Decision Pack

**Verdict:** Recommend **A — Orchestrator-owned encryption gateway**, authenticated with a worker-scoped credential distinct from public API and generic platform credentials. This is an architecture recommendation, not an implementation or gate decision.

**Snapshot note:** Findings describe the working tree read for this pack, not a claim about the committed revision. At inspection time `services/orchestrator/src/server.ts`, `modules/public-api/upload-encryption-gateway.ts`, and related encryption files already had working-tree changes. This task made no source edits and ran no tests or live infrastructure.

## 1. Current State

- CRX-03 explicitly leaves the source choice open: Orchestrator encryption gateway or worker seam with a separate credential; production policy must be trusted and must not allow direct plaintext grants. It also says chunked/multipart manifest support and the `dist/main.js` + Orchestrator + S3 round-trip remain open acceptance (`du-rework/tasks/CODE-REVIEW-ADDENDUM-2026-10-01.md:11,17-19`).
- Document-core currently has no encryption policy or crypto provider in `WorkerEnvSchema` or `DocumentCoreServiceConfig`; `parseWorkerConfig` returns no such values (`du-rework/businesses/document-core/src/config.ts:4-37,41-52,58-77`). Its entrypoint forwards runtime, Redis, connector, concurrency, heartbeat, worker ID and image only (`du-rework/businesses/document-core/src/main.ts:39-51`).
- Worker SDK already accepts optional `crypto` and `encryptionEnabled`; the flag defaults to the compatibility/off behavior (`du-rework/packages/worker-sdk/src/types.ts:288-303`). The seam contains a facade and allowlisted `keyRef`, not a raw master key (`du-rework/packages/worker-sdk/src/crypto-seam.ts:29-40`).
- The existing runtime worker write path requests an artifact grant, then uploads bytes to its URL and finalizes size/digest (`du-rework/packages/worker-sdk/src/task-context.ts:684-739`; route: `du-rework/services/orchestrator/src/server.ts:1429-1447`). The worker PUT reaches `artifacts.putBlob` as raw bytes (`du-rework/services/orchestrator/src/server.ts:1580-1600`). With encryption enabled and no seam, the SDK refuses before PUT/finalize, but the grant has already been requested (`du-rework/packages/worker-sdk/src/task-context.ts:684-710`). Encrypted multipart also refuses because the server-assigned artifact ID and manifest wire path are not connected (`du-rework/packages/worker-sdk/src/task-context.ts:604-623`).
- Orchestrator already has an encrypted **public-client** upload gateway: its route authenticates with `x-api-key`, routes public upload/init/content/complete requests through `publicUploadGateway`, and derives tenant from the API key (`du-rework/services/orchestrator/src/server.ts:1499-1558`). It encrypts before S3 `PutObject` and stores/verifies a manifest (`du-rework/services/orchestrator/src/modules/public-api/upload-encryption-gateway.ts:438-459,650-717`). This is not a worker endpoint: it uses the public upload lifecycle/auth, while workers use task leases and runtime artifact routes (`du-rework/services/orchestrator/src/server.ts:1429-1447,1499-1558`). No dedicated worker encryption upload route was found in the inspected route table.
- Rework already distinguishes worker identity from platform runtime identity: per-business worker bearer tokens resolve the business, are tenant/business fenced, and must be distinct from platform credentials (`du-rework/services/orchestrator/src/modules/runtime/worker-identity.ts:4-9,40-63,79-100`; `du-rework/services/orchestrator/src/main.ts:115-123`).

## 2. Option Comparison

| Dimension | A — Orchestrator gateway | B — Local worker seam from trusted config/provider |
|---|---|---|
| Trusted source and existing pieces | Use Orchestrator's boot-resolved artifact policy, Vault provider, and S3 encryption machinery; add a worker-only authenticated streaming upload path. The current public gateway is a code/policy precedent, not a route to expose directly to workers (`du-rework/services/orchestrator/src/modules/encryption/boot-options.ts:188-223,243-283`; `services/orchestrator/src/server.ts:1499-1558`). | Extend document-core config/main to construct and pass `WorkerCryptoSeam` plus a mandatory production flag; provide a worker-side key-provider adapter using a separately scoped credential. The SDK has the facade/seam interfaces, but document-core does not currently configure them (`du-rework/businesses/document-core/src/config.ts:4-77`; `businesses/document-core/src/main.ts:39-51`; `packages/worker-sdk/src/crypto-seam.ts:29-40`). |
| Changes needed (not performed) | Orchestrator route/auth/composition and artifact persistence; Worker SDK upload transport and document-core endpoint/credential config. Keep task/lease identity and server-derived tenant/artifact/key policy; do not let request body select tenant, keyRef, or encryption mode. | Config parser, process entrypoint, worker provider adapter and `WorkerCryptoSeam` construction; wire artifact-envelope/manifest persistence and enforce the same encryption-required policy on Orchestrator write/read paths. The worker facade depends on a provider that wraps/unwraps DEKs (`du-rework/packages/worker-sdk/src/crypto-storage.ts:53-60,529-543`). |
| Safety conditions | Worker credential is distinct and narrowly scoped; Orchestrator resolves task, tenant, artifact and keyRef from authenticated server state; plaintext is accepted only over the authenticated TLS gateway and encrypted before durable S3 write; no plaintext runtime grant/PUT or downgrade; Vault, policy, manifest and storage failures reject the write. | Production boot must fail if policy requires encryption and seam/provider/keyRef is absent; credentials are not raw master keys/DEKs and are least-privilege; keyRef is allowlisted and bound to the claimed tenant/artifact; Orchestrator must reject plaintext writes and markerless reads. `encryptionEnabled` cannot silently retain its default `false` in a production S3 deployment (`du-rework/packages/worker-sdk/src/types.ts:288-303`; `services/orchestrator/src/modules/encryption/boot-options.ts:204-221`). |
| Current gap / risk | Adds an Orchestrator streaming hop and concentrates throughput/availability pressure there; plaintext traverses the worker-to-Orchestrator connection and exists in Orchestrator process memory before sealing. Must integrate with the worker's leased artifact lifecycle rather than use public API-key upload semantics (`du-rework/services/orchestrator/src/server.ts:1429-1447,1499-1558`; gateway streams/seals in `modules/public-api/upload-encryption-gateway.ts:438-470`). | Distributes provider credentials and crypto capability across worker deployments, increasing secret rotation, revocation and policy-drift surface. There is also a present protocol gap: task-context returns a `SealedArtifact`, but uploads only `sealed.encrypted.ciphertext` and finalizes only size/hash; the wrapped-DEK/envelope/manifest is not carried on this path (`du-rework/packages/worker-sdk/src/task-context.ts:262-265,711-739`; envelope type: `packages/worker-sdk/src/crypto-seam.ts:55-62`). Current encrypted multipart is refused (`packages/worker-sdk/src/task-context.ts:604-623`). |
| Complexity | **High.** New worker-authenticated gateway plus stream/backpressure, lease fencing, artifact-row commit, manifest/version storage, and matching worker client changes; can reuse the Orchestrator policy/provider and gateway mechanics. | **High.** Fewer service hops, but requires worker credential/config lifecycle plus a complete durable envelope/manifest protocol and server-side enforcement; local encryption alone does not yield readable stored artifacts. |

### Option-specific scope

- **A:** `businesses/document-core/src/config.ts`, `main.ts`; `packages/worker-sdk/src/types.ts`, `worker.ts`, `runtime-client.ts`, `task-context.ts` (and stream/multipart transport files as the wire requires); `services/orchestrator/src/server.ts`, `modules/runtime/worker-identity.ts`, and a worker-only gateway module (new or an explicitly refactored shared internal service). Include `packages/contracts/src/runtime.ts` if the worker wire contract changes, plus focused tests for worker auth, fail-closed policy, artifact commit, manifest/read round-trip and multipart. If the existing public gateway is refactored for shared crypto/storage mechanics, include `modules/public-api/upload-encryption-gateway.ts` and its tests, but do not reuse its public `x-api-key` route as worker auth.
- **B:** `businesses/document-core/src/config.ts`, `main.ts`; `packages/worker-sdk/src/types.ts`, `worker.ts`, `task-context.ts`, `crypto-seam.ts`, `crypto-storage.ts`; a document-core provider/config adapter; and the Orchestrator runtime/artifact contracts and persistence/read modules needed to carry and enforce the encrypted envelope/manifest. Focused tests must cover production boot refusal, no plaintext PUT/finalize, persisted metadata, reads, and multipart. The currently optional SDK seam alone is not a complete B implementation.

## 3. CRX-01 / CRX-02 Policy Alignment

- Orchestrator boot options provide one Vault-backed provider to distinct metadata and public-upload encryption blocks, each with its own keyRef. S3 selects both blocks, requires Transit configuration and validates the configured keyRefs; boot builds distinct encrypt/decrypt Vault identities and refuses a shared token (`du-rework/services/orchestrator/src/modules/encryption/boot-options.ts:48-58,153-160,204-223,237-283`). This is the strongest existing authoritative policy source for A; artifact and metadata key separation is intentional, not a policy disagreement.
- **CRX-01 remains an active composition mismatch.** `createSubmissionService` is created without `metadataCrypto` before `metadataCrypto` is built; `createRuntimeService` does receive it (`du-rework/services/orchestrator/src/server.ts:560-582`). Submission's `sealSubmitMetadata` returns the original value when crypto is absent (`du-rework/services/orchestrator/src/modules/operations/submission.ts:109-124`), and the ingestion consumer's `processIngestionTask` call ends without its optional `metadataCrypto` argument (`du-rework/services/orchestrator/src/modules/operations/ingestion-consumer.ts:419-431`; argument position: `modules/operations/submission.ts:500-517`). A must share the same deployment policy with those metadata writers; choosing A does not close CRX-01 by itself.
- **CRX-02 remains an active read-policy mismatch.** `artifactDecryptDeps` is composed with reader and facade but omits `encryptionRequired` (`du-rework/services/orchestrator/src/server.ts:599-612`). The option defaults to compatibility behavior (`du-rework/services/orchestrator/src/modules/encryption/artifact-read-decrypt.ts:78-86`); when the marker is absent, only `encryptionRequired === true` fails closed, otherwise stored bytes are returned (`modules/encryption/artifact-read-decrypt.ts:184-201`). A must use the same required-encryption policy on write and read; boot requiring Vault does not itself set this read flag.

## 4. Recommendation and Future Lease

Recommend **A**, subject to opening a dedicated implementation lease and keeping the worker route distinct from public upload. It best matches the existing Orchestrator-owned Vault/S3 boundary and provides one place to derive tenant/artifact/key policy for worker writes, metadata writers and artifact reads. B is technically possible, but current worker configuration has no trusted provider source and the upload path drops envelope metadata, while CRX-01/02 already depend on Orchestrator composition (`du-rework/businesses/document-core/src/config.ts:4-77`; `packages/worker-sdk/src/task-context.ts:711-739`; `services/orchestrator/src/server.ts:560-612`). A still requires explicit worker-auth streaming support; the public API-key gateway is not that support.

**Open this implementation lease for A:**

1. Worker boot/client: `du-rework/businesses/document-core/src/config.ts`, `businesses/document-core/src/main.ts`; `du-rework/packages/worker-sdk/src/types.ts`, `worker.ts`, `runtime-client.ts`, `task-context.ts`, `artifact-streams.ts`, and `artifact-multipart.ts` as required by the chosen stream protocol; focused worker-sdk and document-core tests.
2. Orchestrator worker boundary: `du-rework/services/orchestrator/src/main.ts` only if new credential/config loading is needed; `services/orchestrator/src/server.ts`; `services/orchestrator/src/modules/runtime/worker-identity.ts`; a new worker-encryption gateway module and its tests. Include `packages/contracts/src/runtime.ts` if the wire shape changes.
3. Durable artifact integration: lease the exact artifact/storage modules that own staging, ciphertext/manifest persistence, and commit (likely `services/orchestrator/src/modules/artifacts/artifacts.ts`, `s3-storage-facade.ts`, and the multipart service/storage modules if multipart is part of acceptance), with their focused tests. Include `modules/public-api/upload-encryption-gateway.ts` and its tests only if its internal encryption/storage mechanics are deliberately shared/refactored; preserve its separate public `x-api-key` surface.
4. Keep CRX-01 and CRX-02 acceptance dependencies explicit and co-owned rather than implicit: `services/orchestrator/src/server.ts`, `modules/operations/submission.ts`, `modules/operations/ingestion-consumer.ts`, and `modules/encryption/artifact-read-decrypt.ts` with their focused tests. `server.ts` is shared with the gateway lane and requires a non-overlapping/explicitly coordinated lease.

No source, contract, task row or gate was changed by this decision pack.
