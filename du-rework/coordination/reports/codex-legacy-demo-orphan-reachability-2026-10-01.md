## 2. Deployment coupling and mock-service boot dependency

- Root `package.json:6-15` starts Next (`dev`/`start`), the worker, tests, or seed; it has no mock-service start script. `mock-service/package.json:6-8` separately provides `start: node server.js` and `dev: node --watch server.js`.
- The root Compose file declares `mock-service`, builds `./mock-service`, exposes its port, and configures its environment (`docker-compose.yml:54-62`). It sets `MOCK_SERVICE_URL` for the app and worker (`docker-compose.yml:19, 83`). The mock service's own Dockerfile starts `node server.js` (`mock-service/Dockerfile:19-23`).
- The mode scripts only rewrite connector URLs and print the next command; `scripts/dev-mode.ps1:5-9` does not start the mock, and `scripts/docker-mode.ps1:5-9` does not start Compose. The root Dockerfile's command starts the app entrypoint (`Dockerfile:74-77`), not the mock. No legacy systemd unit was found in the repository file inventory.
- **The mock service is included when the documented full Compose stack is started, but the repository does not make it a hard app/worker boot dependency.** The quick-start describes running the app with the database and mock services (`README.md:43-45`), while the app and worker dependency lists name only database and Redis (`docker-compose.yml:30-35, 92-96`). `lib/db/seed.ts:8, 11` derives seeded connector URLs from `MOCK_SERVICE_URL` (defaulting to localhost), so the mock is the configured backend for seeded demo connectors; the source does not require it to start the app/worker processes.
- This is shared dev/demo connector wiring, not a dedicated deploy entry for the homepage chat, Prompt Wizard page, `doc-pipeline`, `lc-checker`, or `doc-compare`. In the matrix, deploy coupling is **Y** only where the named surface/service has explicit service start/deploy wiring; **N** means no separate deploy/start unit beyond inclusion in the shared app/worker. The connector seed dependency is recorded above.
