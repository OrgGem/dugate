# DISPATCH SPEC: PC-R01 (Explicit key mode controls fallback)

## Objective
Fix security and authorization defect PC-R01 identified in implementation review:
`LEGACY_STANDALONE` keys with no assigned profiles (empty membership or tombstone-only after revocation/rotation) must be denied authorization rather than falling back to unmanaged legacy behavior via the no-membership heuristic.

## Evidence & Problem Analysis
1. `profiles.ts`: `selectActiveRow` (around lines 530–535) queries `SELECT 1 FROM profile_api_keys WHERE api_key_id=$1 LIMIT 1`. If no membership row exists, it returns `'legacy'`.
2. Both key issue (`api-keys.ts:217`) and rotation (`api-keys.ts:339-344`) permit issuing or rotating a `LEGACY_STANDALONE` key that has zero active memberships.
3. When such a key calls an endpoint, `submission.ts:454` (`resolveGroupAdmission`) returns `null` because `key.keyMode !== 'GROUP_MANAGED'`.
4. Then `resolveAdmission` calls `profiles.resolveEffectiveProfile`, which hits `selectActiveRow`, sees 0 rows in `profile_api_keys`, and treats the key as `'legacy'` (unmanaged full access)!
5. This violates the core invariant: explicit `key_mode` must be authoritative at every admission/discovery fallback. `LEGACY_STANDALONE` with no eligible membership MUST be denied; only a verified `UNMANAGED_LEGACY` key may use unmanaged legacy behavior.

## Detailed Implementation Requirements
1. **`profiles.ts` (`selectActiveRow` / `resolveEffectiveProfile` / `resolveBinding`):**
   - Check the key's declared `key_mode` from `api_keys` (or pass it in / query it).
   - If `key_mode === 'LEGACY_STANDALONE'`:
     - If active membership for the requested business/version/action exists -> return profile row.
     - If no active membership exists (empty or tombstoned) -> return `'not-authorized'` (403/404 denial). It MUST NEVER return `'legacy'`.
   - If `key_mode === 'GROUP_MANAGED'`:
     - Must never be resolved via standalone child memberships -> return `'not-authorized'` (or fail closed).
   - Only when `key_mode === 'UNMANAGED_LEGACY'` (and key is ACTIVE) can `'legacy'` fallback be returned.
   - Any unknown, missing, or NULL `key_mode` must throw or fail closed.

2. **`api-keys.ts` (issue & rotation):**
   - When issuing a `LEGACY_STANDALONE` key without profiles or when rotating a `LEGACY_STANDALONE` key whose memberships are all revoked/tombstoned:
     - Ensure mode is strictly preserved as `LEGACY_STANDALONE`.
     - Do not infer new entitlement from missing membership history.
     - Reconcile both issue and rotation APIs to ensure `key_mode` is always explicitly set and tracked.

3. **`submission.ts` (`resolveAdmission`):**
   - In `resolveAdmission`, verify that non-group admission checks `key.keyMode`.
   - If `key.keyMode === 'LEGACY_STANDALONE'`, verify that `resolveEffectiveProfile` returns a valid profile binding, and deny if `'legacy'` is returned (or ensure `selectActiveRow` returned `'not-authorized'`).
